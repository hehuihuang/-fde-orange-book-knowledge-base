# Assembled 客服 Agent 韧性

| 项目项 | 内容 |
| --- | --- |
| 行业 | 客服运营软件 |
| 产品 | Assembled Assist |
| 参与方 | Assembled、Anthropic、企业客服团队 |
| 证据等级 | A，另含 D 级教学重构 |
| 核心课题 | 让 AI 和人工按复杂度协作，并把每次修改变成评测数据 |

## 公开结果

Anthropic 与 Assembled 的案例报告，Assist 在降低支持支出的同时把客户满意度提高 20%，升级人工的比例降低超过 50%，每小时解决案例数提高超过 30%。系统自动处理超过一半案例，同时保持 90% 以上客户满意度。[Assembled 案例](https://claude.com/customers/assembled)

这些数字是产品方与模型供应商发布的汇总结果。客户范围、基线、时间段和统计方法没有公开。案例更值得学习的是系统怎样评测、路由和故障切换。

## 人机路由

Assembled 把目标放在 Tier 2 及以上复杂问题，其中有些可以自动完成，有些更适合给人工增强。系统按案件复杂度和客户情绪在 AI 与人工之间路由。工单分类使用能适配客户分类体系的方法，不要求所有企业使用同一标签。

这个选择绕开了常见误区。高自动化率不等于所有工单都应自动关闭。身份、情绪、金额、政策例外和不可逆操作会改变责任。路由质量和升级后的上下文完整度，往往比单次回答更影响客户体验。

## 每条回复都进入评测

公开案例称每个客服 Agent 回复都会经过评测系统。人工修改 AI 回复时，系统分析变化，并把它们积累为比较用的黄金数据。某个主要客户在数百个类别上的准确率从 62% 提升到 90%。[案例原文](https://claude.com/customers/assembled)

人工修改是很好的生产信号，但不能自动当作标准答案。客服可能为了速度接受不完整内容，也可能因个人风格改写正确答案。黄金数据需要抽样复核，区分事实修正、政策修正、语气调整和无关编辑。

## 五到六小时故障怎样扛住

一次竞争模型供应商发生五到六小时故障时，Assembled 在约二十分钟内把 LLM 工作流切到 Claude。公开资料称客户没有中断。系统采用多模型架构和安全故障切换。[故障说明](https://claude.com/customers/assembled)

真正的切换能力来自接口和评测都准备过。两个模型返回格式不同、工具调用习惯不同、内容边界不同。只把模型名换掉，可能让工作流表面恢复，质量却悄悄变化。

## FDE 视角重构

以下是教学重构。

客户上线前先把工单分成查询、建议、草拟、可逆执行和不可逆执行。每类定义允许工具、金额或权限上限、人工升级和响应目标。退款、账号安全和身份盗用等高风险任务默认交人工。

评测集从历史工单抽样，按意图、语言、客户等级、情绪和政策例外切片。评分分开事实正确、政策符合、工具选择、升级判断和表达。生产中记录自动解决、再次联系、人工修改、升级和投诉。

故障切换要经过演练。备选模型使用同一套结构化输出合同，切换后先进入保守模式。系统可以提高人工路由比例、关闭不可逆工具并抽样检查，确认关键评测没有退化后再恢复自动化。

## 建议事件回放格式

```json
{
  "case_id": "support-2026-001",
  "policy_version": "refund-v7",
  "model_route": "primary",
  "tool_calls": [],
  "risk_tier": "medium",
  "agent_output": "...",
  "human_edit_type": "policy_correction",
  "resolution": "escalated",
  "repeat_contact_7d": false
}
```

真实记录应去除不必要的个人数据，并按企业保留政策处理。

## 可复制的交付资产

客户分类映射、任务风险分级、人工修改标签、全量评测管线、多模型结构化合同、故障切换演练和保守模式开关都能复用到客服 Agent。具体政策、语言和升级组织必须按客户重新配置。

## 资料没有说明什么

公开资料没有给出模型成本、评测器误差、各客户指标分布、故障切换期间的降级功能和质量变化。62% 到 90% 只对应一个主要客户，不能代表全部部署。
