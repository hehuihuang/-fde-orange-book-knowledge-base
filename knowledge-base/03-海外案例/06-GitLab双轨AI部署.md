# GitLab 双轨 AI 部署

| 项目项 | 内容 |
| --- | --- |
| 行业 | DevSecOps 与企业软件 |
| 轨道 | Claude 进入 GitLab Duo 产品，同时供员工内部使用 |
| 参与方 | GitLab、Anthropic、产品与模型评估团队 |
| 证据等级 | A，另含 D 级教学重构 |
| 核心课题 | 产品集成与内部采用使用同一模型能力，但质量、责任和指标不同 |

## 两条轨道不能混成一条

GitLab 的公开材料其实讲了两个项目。产品轨道把 Claude 接进 GitLab Duo，服务外部客户。内部轨道让员工在写作、研究、RFP、数据分析和小工具开发中使用 Claude Enterprise。两条轨道共享模型经验，但数据、风险、上线流程和成功标准不同。

供应商案例把两者放在相邻页面，读者很容易把内部效率数据当成 Duo 产品结果。本页将它们分开。

## 产品轨道

GitLab 把 AI 放进代码生成、对话、计划摘要、漏洞解释和修复等软件生命周期任务。公司建立模型评估团队，比较新供应商和新模型版本，再按任务选择模型。传统软件工程师可以借助 Anthropic 的 API 和文档参与 AI 功能开发，公开案例称已有数十人参与。[GitLab 产品案例](https://claude.com/customers/gitlab)

这条轨道最有价值的地方在模型选择机制。GitLab 没有假设一个模型适合所有软件任务。漏洞解释需要事实和安全边界，代码生成看可编译与测试，计划摘要又看覆盖和清晰。模型版本进入产品以前，需要在对应任务上比较。

## 内部轨道

内部试点覆盖 RFP 回复、内容与翻译、技术文档、脚本开发和数据分析。GitLab 使用 SSO 管理访问，并鼓励员工共享有用对话。联合案例报告 98% 的受访者满意或非常满意，并报告 25% 至 50% 的效率提升。[GitLab 企业采用案例](https://claude.com/customers/gitlab-enterprise)

这些数字来自试点参与者调查，公开页面没有给出样本量、任务口径和测量方法。它们适合说明参与者感受到明显帮助，不能代表全体员工，也不能当作 Duo 客户的产品效果。

## FDE 视角重构

以下是教学重构。

产品轨道应按任务建立模型登记表。每项记录输入、允许数据、目标模型、替代模型、评测集、延迟和成本。新模型先离线评测，再影子运行，随后对小比例用户开放。发生质量退化时能按功能回退，不要求整个平台同时切换。

漏洞相关功能应把代码、扫描结果、依赖和安全规则作为证据。模型给出解释和候选修复，静态分析、测试和人工审查仍决定是否合并。系统要记录建议被接受、修改或拒绝的原因。

内部轨道则应先建立允许数据规则和分享边界。RFP 可能包含客户保密资料，数据分析可能上传内部报告。SSO 只解决身份入口，部门仍要知道哪些数据可以进入、输出如何复核、共享链接能被谁访问。

两条轨道可以通过脱敏失败样本相互学习。内部员工发现模型不懂 GitLab 概念时，这些问题能帮助产品团队改文档和评测。产品客户的代码和隐私数据不能自动进入内部实验。

## 双轨看板

| 维度 | 产品轨道 | 内部轨道 |
| --- | --- | --- |
| 质量 | 测试通过、漏洞解释正确、建议采纳 | 输出可用、修改幅度、错误类型 |
| 采用 | 功能使用、留存、付费和关闭率 | 周活、任务覆盖和部门分布 |
| 风险 | 不安全代码、数据泄露、供应链风险 | 保密数据、错误外发、未经授权分享 |
| 价值 | 开发周期、漏洞修复、客户体验 | RFP 时间、内容周期和分析时间 |
| 回退 | 功能级模型回退 | 禁用共享工具或限制部门 |

## 可复制的交付资产

任务级模型登记表、供应商比较集、功能级灰度、代码建议采纳标签、内部允许数据清单和脱敏反馈流程都能复用。采用多模型会增加路由、监控和供应商变更成本，只有评测证明收益时才值得保留。

## 资料没有说明什么

公开页面没有给出 Duo 各功能的准确率、评测集大小、模型路由细节、成本、内部调查样本和长期留存。所谓数周完成 AI 功能开发来自联合案例概括，不能替代具体项目计划。
