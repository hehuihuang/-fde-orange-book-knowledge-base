# Morgan Stanley 金融知识与 Evals

| 项目项 | 内容 |
| --- | --- |
| 行业 | 财富管理与金融服务 |
| 产品 | AI @ Morgan Stanley Assistant 与 Debrief |
| 参与方 | Morgan Stanley、OpenAI、财务顾问与领域专家 |
| 证据等级 | A，另含 D 级教学重构 |
| 核心课题 | 让顾问安全查到内部知识，并用持续评测支持规模化采用 |

## 项目从哪三个目标开始

Morgan Stanley 的首批 AI 用例有三个明确目标。顾问要更快找到内部信息，研究材料的摘要工作可以减少，回答还要能贴合客户需要。团队没有把目标写成部署一个聊天机器人，而是落到顾问每天花时间的任务。[OpenAI 与 Morgan Stanley 案例](https://openai.com/index/morgan-stanley/)

Assistant 用 GPT-4 帮助顾问查询内部知识。公开材料称系统从能回答约 7,000 个问题，扩展到可在十万份文档的语料上处理问题。这个说法来自项目负责人，不等于十万份文档里的任意问题都能保证正确。更稳妥的理解是覆盖范围显著扩大，同时依靠评测控制质量。

## Evals 怎样进入开发

团队先为摘要建立评测。顾问和提示工程师从准确与连贯两个方向评分，结果用于改提示。随后又加入翻译评测，并与 OpenAI 调整检索方法。每个用例在上线前都要通过相应评测，生产阶段每天运行样本问题回归。

这套做法把业务规格变成可执行样本。顾问知道什么事实最关键，工程师知道检索和模型在哪一步失效。评测集也会随着文档和任务扩大，在模型、检索和内容持续变化时成为双方共同使用的质量标准。

## 从检索扩到会议工作流

第二个产品 Debrief 处理 Zoom 会议录音。客户同意后，系统把录音转成会议笔记、行动项和跟进草稿，再把结果接进 CRM。顾问在最终保存和发送前审核并修改。团队为不同会议类型建立数据集，重点检查关键行动项是否被捕获，以及系统是否引入错误。[案例原文](https://openai.com/index/morgan-stanley/)

这个流程说明人工复核的位置不能只写成一句 human in the loop。顾问在系统写入正式记录和对外沟通之前负责确认，修改结果又能成为评测和产品改进的材料。

## 信任与采用

公开材料称财富管理顾问团队采用率超过 98%，可访问文档的比例从 20% 提升到 80%。跟进从数天缩短到数小时。Morgan Stanley 还强调零数据保留安排对内部安全审查的重要性。[项目案例](https://openai.com/index/morgan-stanley/)

采用率高并非界面上线后的自然结果。知识范围、检索准确、日常回归、人工复核和数据处理承诺共同降低了顾问的使用风险。顾问愿意把工具放进客户工作，系统才有机会产生关系层面的价值。

## FDE 视角重构

以下架构是教学重构。

文档进入系统前先确定所有者、有效期、受众和权限。检索层按用户身份过滤，再召回相关段落。生成层只使用授权上下文，回答保留文档与段落引用。无法找到充分依据时，系统拒绝回答或提示顾问继续查证。

黄金集应来自真实顾问问题。样本需要覆盖高频查询、复杂产品、时效变化、相似文档冲突、权限不足和没有答案。评分至少分开证据召回、引用支持、事实正确、表达适用和拒答。一个总分会掩盖高风险错误。

Debrief 还需要单独的同意、录音状态、CRM 写入幂等和敏感信息控制。评测应按会议类型、口音、多人发言和专业术语切片。工具失败时保留原录音和草稿状态，不能重复写入客户记录。

## 生产运行看板

| 维度 | 建议观察项 |
| --- | --- |
| 质量 | 有支持引用率、拒答正确率、关键行动项漏检、顾问修改幅度 |
| 采用 | 周活跃顾问、真实任务覆盖、重复使用、退出到旧搜索的比例 |
| 运行 | 检索延迟、索引新鲜度、CRM 写入失败、模型版本回归 |
| 风险 | 权限拦截、敏感信息事件、错误对外发送、人工复核绕过 |
| 价值 | 搜索时间、会后处理时间、跟进时延和顾问可服务容量 |

## 可复制的交付资产

按身份过滤的检索适配器、文档权威度字段、顾问问题黄金集、每日回归任务、会议类型评测包和 CRM 预览确认模式都可以复用。换到法律、保险或专业服务时，领域专家、拒答规则和正式责任必须重新确定。

## 资料没有说明什么

公开案例没有披露模型和检索的具体阈值、顾问样本量、完整成本、失败率和采用率分母。20% 到 80% 的文档访问指标也没有公开计算细节。它可以证明团队用评测和控制推动了广泛采用，不能替其他金融机构给出上线标准。
