# 第四篇　FDE 技术底座

## 第 12 章　企业 AI 系统参考架构

### 12.1 七层架构

一个可维护的企业 AI 系统通常包含七层：体验层承载用户入口；编排层管理任务状态与步骤；模型层提供推理与生成；上下文层准备检索结果、历史与策略；工具层连接业务系统；控制层执行身份、权限、策略和人工确认；可观测层记录质量、时延、成本与安全事件。

这不是要求采购七个产品，而是提醒团队不要把所有责任塞进一次模型调用。任何层都可以很薄，但边界应清晰。

### 12.2 请求数据流

典型请求从身份开始：识别用户和租户，加载其权限；对输入做分类与安全检查；准备必要上下文；选择工作流或 Agent；执行模型与工具调用；校验输出；在高风险点请求人工确认；记录完整 Trace；把结果写回业务系统；最后采集用户反馈与结果指标。

### 12.3 多租户与权限继承

模型应用不能因为检索方便而绕过原系统权限。知识检索应继承文档访问控制，工具调用应代表具体用户或受限服务身份，缓存和日志也要隔离租户。对“模型看到了但不输出”的防护不能替代“模型根本不应看到”。

### 12.4 模型抽象与路由

模型路由可按任务、风险、成本、时延和数据驻留要求选择模型。抽象层应统一请求、工具、结构化输出、错误和用量记录，同时保留供应商特性。过度追求完全通用会失去能力，完全绑定又会增加迁移风险；FDE 应根据项目寿命和合规要求做有意识取舍。

## 第 13 章　数据与上下文工程

### 13.1 RAG 不是上传文件

检索增强生成包括内容采集、解析、切分、元数据、索引、查询改写、检索、重排、上下文组装、引用和反馈。任一步骤失败都可能表现为“模型胡说”。工程团队应分别测量召回、排序、上下文利用和最终答案，而不是只看端到端感觉。

### 13.2 知识治理

每个知识源都应有所有者、适用范围、更新时间、权威等级和访问策略。冲突文档应建立优先级或让系统暴露冲突，不能让模型静默选择。过期知识是企业 RAG 最常见的隐性风险之一。

### 13.3 切分与检索

切分应尊重语义结构：条款、步骤、表格、代码和 FAQ 需要不同策略。检索评测应使用用户真实查询，记录目标证据是否进入候选、是否进入最终上下文。若召回失败，提示工程无法补救。

### 13.4 上下文预算

更长上下文并不自动更好。把与任务无关的信息塞入窗口，会增加成本、时延和冲突。上下文应按指令、用户状态、任务证据、工具结果和历史记忆分区，并设定来源与截断策略。

### 13.5 数据生命周期

明确输入、输出、嵌入、日志和反馈的采集目的、存储位置、保留期、访问者和删除机制。生产日志不应默认保存完整敏感文本；可使用脱敏、哈希、字段抽取或受控采样。

## 第 14 章　Agent、工具与 MCP

### 14.1 先区分工作流与 Agent

Anthropic 的工程实践区分预定义代码路径的 workflow 与由模型动态决定步骤和工具使用的 agent。确定流程优先使用工作流：更容易测试、解释和控制。只有任务步骤无法预先枚举，且动态决策的价值超过风险与成本时，才引入更强自主性。

### 14.2 Agent 的最小循环

Agent 在目标约束下执行“计划—行动—观察—调整”，直至完成、达到预算或需要人类输入。生产实现必须有终止条件、步数与成本预算、工具白名单、状态持久化、错误处理和人工接管。

### 14.3 工具设计

工具名称和描述要说明用途、参数、返回字段、错误行为和副作用。工具应窄而清晰，返回结构化结果。对写操作提供幂等键、预览模式和回滚信息；对高风险操作拆分“准备”和“确认执行”。

### 14.4 MCP 的位置

Model Context Protocol 提供应用与数据、工具连接的标准化接口，但协议兼容不等于安全可信。FDE 仍需审查 Server 来源、权限、传输、输入验证、日志和供应链。企业中应建立 MCP 目录、所有者、风险级别和审批生命周期。

### 14.5 多 Agent 的使用门槛

多 Agent 适合可并行、可分解且结果可验证的任务，例如独立搜索多个资料域后汇总。它同时增加协调、上下文复制、成本和不可预测性。先证明单 Agent 的瓶颈，再引入分工；不要用组织结构图代替系统设计。

## 第 15 章　生产可靠性与可观测性

### 15.1 记录完整 Trace

每个任务应有相关 ID，串联用户请求、检索、模型版本、提示版本、工具调用、策略决定、人工确认、输出与最终结果。敏感字段应受控，但不能因隐私担忧而完全失去可诊断性。

### 15.2 可靠性指标

除服务可用性外，还应监控任务成功率、工具成功率、人工接管率、无效循环、P50/P95 时延、单任务成本、引用缺失、策略拦截和高风险错误。业务高峰与特定用户组应单独观察。

### 15.3 超时、重试与幂等

模型和外部工具都可能超时。只读调用可按退避策略重试；写操作必须使用幂等键或先检查状态，避免重复付款、重复发信或重复建单。长任务应持久化状态并允许从检查点恢复。

### 15.4 降级设计

降级路径包括切换备用模型、缩短上下文、关闭非关键工具、转为只读、返回可编辑草稿、交给人工队列或回退到原流程。降级不是一句“请稍后重试”，而是业务连续性设计。

### 15.5 成本工程

按任务记录输入、输出、缓存、工具与基础设施成本，并关联业务价值。通过模型路由、缓存、批处理、上下文裁剪和确定性预处理降本。不要只追求单次调用便宜；失败重试与人工返工可能使总成本更高。

## 第 16 章　安全、治理与合规

### 16.1 威胁模型从资产开始

列出系统能够读取、推断和改变的资产：个人信息、商业秘密、财务记录、源代码、权限令牌、外部通信和物理操作。再分析攻击者、入口、信任边界、最坏影响与现有控制。没有资产与影响，安全清单容易流于形式。

### 16.2 关键风险

OWASP 的 GenAI 风险体系覆盖提示词注入、敏感信息泄露、不安全输出处理、供应链、过度授权等问题。对 FDE 最重要的原则是：外部内容均视为不可信；模型输出进入解释器、数据库或业务 API 前必须验证；Agent 只获得完成当前任务所需的最小权限。

### 16.3 分级控制

- **低风险**：生成内部草稿，可撤销且不触达外部；允许自动执行并抽样审计。
- **中风险**：影响客户体验或内部记录；要求规则校验、可追溯和易回滚。
- **高风险**：财务、医疗、用工、法律、安全或外部不可逆动作；要求专门评测、审批、双人复核或限制自动化。

风险等级应决定数据、权限、评测、人工控制与监控强度。

### 16.4 治理进入研发节奏

治理不是上线前的一次会议。发现阶段确认用途和数据；设计阶段完成威胁模型；开发阶段建设控制与审计；测试阶段进行滥用和红队场景；上线后监控漂移、事件与申诉。NIST AI RMF 的 Govern、Map、Measure、Manage 可作为组织检查框架。

### 16.5 中国环境的工程提示

面向中国境内公众提供生成式 AI 服务时，应评估《生成式人工智能服务管理暂行办法》的适用性，以及个人信息、数据安全、算法备案、安全评估等要求。2025 年 9 月 1 日起施行的《人工智能生成合成内容标识办法》及 GB 45438-2025 对适用场景的显式、隐式标识提出要求。企业内部工具是否适用、如何适用，必须由合规人员结合服务对象和数据流判断。

FDE 的工程清单至少应包含：数据来源合法性、个人信息处理依据、跨境与驻留、输入输出留存、内容标识、用户协议、投诉与事件处置、供应商责任、模型与算法手续。不要把“供应商合规”误认为“本项目自动合规”。

# 第五篇　FDE 的软技能与现场判断

## 第 17 章　FDE 能力模型

### 17.1 六维能力

1. **工程实现**：能跨前后端、API、数据、云和运维交付系统。
2. **AI 系统**：理解模型行为、RAG、Agent、Evals 与安全边界。
3. **产品发现**：能观察工作、拆问题、做优先级并设计体验。
4. **业务判断**：理解价值链、指标、成本和行业约束。
5. **交付领导**：能管理范围、依赖、风险、决策和采用。
6. **沟通影响**：能对不同角色清晰表达事实、取舍与下一步。

FDE 不需要六维同时满分，但不能有与项目类型冲突的短板。高监管项目中安全和沟通是门槛；高速创业项目中工程速度与产品判断更关键。

### 17.2 T 型与梳型

初级 FDE 可先形成一条技术深度和广泛交付能力；资深 FDE 往往发展为“梳型”，在系统工程、AI、行业或组织变革中拥有两到三条深度。能力发展应由真实项目拉动，而不是无限收集工具证书。

## 第 18 章　在复杂组织中推进项目

### 18.1 用决策而不是会议管理项目

每次同步都应明确需要什么决定、谁决定、依据是什么、最晚何时决定。维护决策日志，记录选项、证据、取舍和可逆性。状态报告聚焦结果、风险、阻塞和下一里程碑，避免用活动数量代替进展。

### 18.2 对不同对象说不同语言

对管理层说明价值、风险和需要的资源；对流程负责人说明工作变化和责任；对工程团队说明接口、约束和验收；对安全法务说明数据流、权限和控制；对一线用户说明系统能做什么、不能做什么以及如何纠错。改变表达不是隐瞒，而是降低理解成本。

### 18.3 尽早传递坏消息

高质量升级包含事实、影响、已采取动作、选项、建议和决策期限。不要只报告“有风险”，也不要等到能完美解释根因才沟通。信誉来自持续准确，而不是永远乐观。

### 18.4 管理隐性阻力

阻力可能来自岗位安全感、绩效指标、历史承诺、数据所有权或额外工作量。不要把它简化为“用户不拥抱 AI”。通过调整激励、减少额外步骤、明确责任和让用户参与设计处理根因。

## 第 19 章　在不确定中做技术决策

### 19.1 可逆性优先

高不确定阶段优先做可逆决定：模块化接口、影子运行、有限权限、小范围试点。不可逆决定如大规模数据迁移、外部自动写入和深度供应商绑定，应提高证据门槛。

### 19.2 临时实现的边界

可以临时的是界面细节、手工运营、低风险数据映射；不应临时的是身份隔离、审计、不可逆写操作、关键指标和恢复能力。把“临时”写进风险台账，设定所有者与到期日。

### 19.3 决策记录

对重要选择记录背景、约束、选项、决定、理由、预期后果和复审触发条件。当模型、法规、规模或客户需求变化时，团队可以判断原决定是否仍成立。

### 19.4 FDE 的镇定

现场压力会诱发两个极端：为了取悦客户承诺一切，或以技术理由拒绝变化。成熟 FDE 先确认事实和风险，再提出最小安全前进路径。镇定不是慢，而是不把不确定性转化为混乱。
