# 第 5 章　大模型与上下文

一名采购员问某种密封圈能否替代现有物料。模型能够写出流畅的材料说明，应用仍需知道规格来源、适用工况与当前批准状态。一次回答跨过了语言生成、证据组织和业务决策三个不同过程。FDE 要把它们分别设计、分别验证。

本章对照 Transformer 论文、KV 缓存文档和长上下文研究，解释这些机制在交付现场的用途。采购、工单和参数数值均为作者原创教学设定，读者可以复算；它们没有对应的客户，也不代表某款商业模型的性能。做完本章，应能画出一次调用的数据路径，计算上下文与显存预算，并定位格式正确却业务错误的输出。

## 5.1 从条件概率理解一次生成

常见自回归语言模型把文本转成 token 序列，然后逐个预测后续 token。设输入为 x，输出为 y_1 到 y_m，一段输出的条件概率可以写成各步条件概率的乘积。

```text
P(y | x) = product over t of P(y_t | x, y_1 ... y_(t-1))
```

token 来自具体分词器，可能表示一个字、一段字符或单词的一部分。同一段中文在不同分词器下长度不同。计算预算时应使用实际模型对应的分词器或官方计数接口。用字符数乘一个固定系数，可以做粗估；超过边界附近的请求必须精确计数。

这一生成方式解释了两个工程现象。输出前面的错误会成为后续生成的条件，模型可能继续写出与错误一致的说明。另一个现象是同一问题存在多种表达，采样参数会影响选中哪条序列。降低 temperature 可以减少部分随机性，但并不提供事实保证。服务实现、并行计算和模型更新也会影响复现，不能把 temperature 为零写成绝对确定性承诺。

模型预训练参数中保存的是从训练数据学到的统计关系。企业的今天库存、用户权限和合同生效状态应由系统提供。把这些信息写进提示后，生成仍可能忽略某条约束。重要约束应同时出现在明确的数据结构与服务端检查中。例如模型可以建议物料编号，库存是否可用要查询库存服务；模型可以给出付款说明，金额和收款方必须由交易服务校验。

有些模型会在返回答案前消耗额外推理计算。部署者能观察到的是可用接口、输出、耗时和计费，通常无法逐项观察其全部内部过程。不要把模型自己生成的解释当成真实执行记录。执行记录应来自工具调用日志与服务结果，推理文本可以用于理解或调试，但两者的证据作用不同。

## 5.2 Attention 到底在计算什么

Transformer 的注意力让某个位置根据其它位置的信息更新表示。最常见的缩放点积形式如下。Q、K、V 分别由输入表示线性变换得到，d_k 是 key 向量维度。

```text
Attention(Q, K, V) = softmax(Q K^T / sqrt(d_k)) V
```

可以把一次注意力计算拆成具体动作。当前位置的 query 与各位置的 key 做点积，得到相关程度；缩放后用 softmax 得到非负权重；再按权重汇总 value。真实模型有多个注意力头、多层变换、位置编码、前馈网络和残差连接。多头使不同子空间可以形成不同的关联，这些关联没有统一的人类标签，不能直接断言某个头就是合同理解器。

以下三个数字只用于理解 softmax。假设缩放后的相关分数是 2、1、0，指数值约为 7.389、2.718、1，总和约为 11.107，权重约为 0.665、0.245、0.090。高相关位置贡献更大，其它位置仍可能影响结果。输入中一条无关但形式醒目的指令，有机会改变表示和输出，这也是后续安全设计必须把检索文本视作不可信数据的原因。

自回归解码器使用因果遮罩，生成某个位置时不能使用尚未生成的后续位置。完整输入的预填充阶段可以并行处理许多位置；输出生成阶段通常需要按顺序产生后续 token。两者的硬件利用率和性能瓶颈不同。因此“输入再增加一万 token”和“输出再增加一万 token”不能简单视作同一项时延成本。

朴素全注意力中，长度 n 的序列会形成 n×n 的相关分数，相关计算量具有二次项。高效实现可以避免把完整分数矩阵长期放在显存中，某些模型还采用滑动窗口或其它注意力结构。二次计算的分析适用于朴素全注意力，不能套到每一种架构，更不能直接用它预测托管 API 的账单。现场需要保存自己的长度与时延曲线，至少按输入长度、输出长度、并发与缓存命中分层。

## 5.3 KV 缓存、前缀缓存与业务缓存

解码每生成一个新 token 都需要参考历史位置。KV 缓存保存先前位置的 key 与 value，避免反复计算已有部分。它仍需存储状态，新 token 也仍需对历史状态做计算。长会话往往同时带来更多显存占用和更大的历史读取量。

对使用固定每层 KV 头数的解码器，可以做一个简化显存估算。L 为层数，B 为同时处理的序列数，n 为缓存长度，H_kv 为 KV 头数，d 为每头维度，s 为每个元素字节数。下面只算 KV 张量，不包括模型权重、激活、分配器开销或并行切分。

```text
KV bytes ~= 2 * L * B * n * H_kv * d * s
```

假设教学模型有 32 层，KV 头数为 8，每头 128 维，用 2 字节存一个数，单序列有 16,384 token。代入后得到 2,147,483,648 字节，约 2 GiB。若同时保持 16 条同样长的序列，KV 本身就约 32 GiB。该数值仅说明估算方法。实际模型可能采用 grouped-query attention、滑动窗口、量化缓存或跨设备分片，必须依据架构和实现修正。

KV 量化降低状态精度，可能减少占用，也可能增加量化计算和误差；把缓存转移到 CPU 可以减轻 GPU 压力，但传输成本会影响时延；PagedAttention 一类管理方法处理分配与共享问题，并不消除所有上下文成本。选择时应同时测质量、峰值内存、首 token 时延与输出吞吐，不能只记录“能否装下”。

前缀缓存与业务结果缓存服务于不同目标。前缀缓存复用相同输入前缀的计算，通常要求输入与实现约定匹配。业务结果缓存保存某次查询或回答，其正确性依赖数据版本与权限。稳定规则放在前面、动态问题放在后面可能改善前缀复用，但不能为追求命中率把租户资料混放，或省略权限过滤。

| 缓存种类 | 保存内容 | 典型失效条件 | 交付者要检查的边界 |
| --- | --- | --- | --- |
| 解码 KV | 当前生成的历史表示 | 序列结束或实现策略触发 | 内存占用与并发 |
| 输入前缀 | 重复前缀计算状态 | 前缀、模型或配置变化 | 租户隔离与计费口径 |
| 检索结果 | 文档或对象候选 | 数据或授权版本变化 | ACL、更新延迟 |
| 最终回答 | 业务问题的结果 | 事实、用户或规则变化 | 陈旧回答与个性化泄露 |

## 5.4 先分配上下文，再组织文字

设可用窗口为 W，固定指令为 I，工具描述为 T，历史为 H，证据为 D，当前问题为 Q，为生成预留 O。应用需要满足总预算，服务端可能还有独立的最大输出限制。某些接口会把推理 token 算入输出预算，具体口径要查所选服务文档。

```text
I + T + H + D + Q + O <= W
```

下面是一个 32,768 token 的原创预算。固定规则占 1,500，工具描述占 2,000，问题占 300，历史占 4,000，预留输出 3,000，余量 1,000。证据上限为 20,968。上限只解决请求是否装得下。若任务只需两个物料对象和一条批准记录，填满两万 token 可能增加无关干扰、成本与首 token 等待。

分配证据时可以依据来源可靠性、任务相关性、时效与边际信息量排序。强制保留当前授权结果、被操作对象的版本和用户明确约束；再添加解释需要的证据。多段资料表达同一个事实时，只保留主记录及必要出处，避免大量重复片段占掉重要信息。每段证据应保留稳定编号，模型引用编号，程序负责把编号映射回可核对的来源。

工具描述也是预算的一部分。把几十个相似工具全部放入请求，模型需要分辨名称和参数，选择错误机会随之增加。可以按任务先选择工具集合，再交给模型。这项选择必须使用受信任的规则或具备限制的路由，不能让未经授权的工具因模型建议而进入工具集合。工具选择带来的质量变化也需要回归评测。

长窗口研究表明，某些被测模型和任务中，相关信息的位置会影响表现，尤其需要关注中间信息的利用。该研究没有证明所有当前模型都有同样程度的偏差。本书建议在自己的评测中置换证据顺序，同时保留无关长文本干扰样本。若同一事实移到中间就频繁失败，先调整证据组织和任务分解，再判断是否需要更换模型。

## 5.5 历史压缩要保住哪些状态

聊天记录中有解释、有试探，也有用户最后确认的选择。直接截取最后若干轮可能丢失前面确认的约束；让模型摘要全部历史可能改错数量、漏掉否定条件或把候选方案写成已批准方案。压缩前应把业务状态与普通对话分开保存。

采购教学任务中，物料编号、数量、币种、单位、交付日期和批准状态保存在结构化状态中；用户为何偏好某供应商可以进入摘要；外部资料通过来源编号保留，必要时重新查询。这样压缩只缩短叙述，关键状态仍由明确字段维持。用户纠正数量后，状态版本增加，先前写入预览随之失效，不能靠最新摘要里的自然语言判断旧确认是否仍然有效。

```json
{
  "task_id": "demo-42",
  "state_version": 7,
  "material_id": "MAT-204",
  "quantity": 12,
  "unit": "piece",
  "decision": "awaiting_approval",
  "evidence_ids": ["spec-v3", "policy-v8"],
  "summary": "用户接受候选规格，尚未批准采购提交"
}
```

摘要是否有效可以做差异检查。提取压缩前后的关键字段，逐项比较；对未批准、禁止替代、仅供参考等否定和状态词设置专门测试；引用必须能回到原记录。程序保存摘要所依据的历史区间和摘要模型版本。若发现摘要遗漏，能够重建，而不用猜测何时开始丢失状态。

外部记忆需要写入政策。一次对话中的供应商偏好可以只服务当前任务，未必适合成为用户长期偏好。保存前明确作用范围、来源和失效时间。敏感信息应遵守最小保存原则。跨用户共享的企业事实，与某用户的偏好状态，采用不同的授权和更新机制。第五章的上下文预算与第十章的数据最小化在这里直接相遇。

## 5.6 结构化输出分三次验证

结构化输出可以约束字段与格式。厂商提供的受约束生成机制对支持的模型和 schema 有适用范围，还可能发生拒绝、截断或接口错误。API 调用完成后，应用首先确认响应状态，再验证结构，然后验证业务。不能只在 JSON 解析成功时显示绿色勾。

结构层回答字段是否存在、类型是否正确、额外字段是否允许。事实层检查物料编号和来源编号是否存在，规格是否来自授权数据。业务层检查数量、单位、对象状态、审批与当前版本。金额应采用明确的十进制或最小货币单位表达，避免把二进制浮点直接用于结算比较。下面是独立的教学校验片段，运行后得到标准化请求；它没有实现身份验证与完整采购逻辑。

```python runnable
from decimal import Decimal

def validate_proposal(value, allowed_materials):
    required = {"material_id", "quantity", "unit_price"}
    if set(value) != required:
        raise ValueError("unexpected fields")
    if value["material_id"] not in allowed_materials:
        raise ValueError("unknown material")
    quantity = value["quantity"]
    if type(quantity) is not int or not 1 <= quantity <= 500:
        raise ValueError("invalid quantity")
    price = Decimal(str(value["unit_price"]))
    if not price.is_finite() or price < 0:
        raise ValueError("invalid price")
    return value["material_id"], quantity, price

assert validate_proposal(
    {"material_id": "MAT-204", "quantity": 12,
     "unit_price": "3.50"}, {"MAT-204"}
)[2] == Decimal("3.50")
```

Python 中布尔值也是整数的子类型，片段特意使用 `type(quantity) is int`，防止把 true 当作数量 1。商业应用还需要币种、小数位、价格来源和有效期检查。这些细节说明结构约束与业务约束有不同责任。把所有规则塞进 schema 会遇到可读性、能力和版本限制；把所有规则留给模型，则无法保证写操作边界。

输出中保留证据编号，可以验证每条业务结论是否有所依靠。遇到信息不足，定义明确状态，如需要补问、资料冲突或暂不处理，并给出缺失字段。用户不必读懂内部状态枚举，界面可以将它们翻译成可执行提示。对高风险任务，补问与拒绝属于有效结果，不能在评测中一律当失败。

## 5.7 成本、延迟与排队分开算

一个粗略计费模型是输入 token 乘输入单价，输出 token 乘输出单价，再加缓存、检索或工具费用。以下使用假定单价进行教学计算，单位均为每百万 token，不是任何厂商当前报价。输入 6,000 token，输出 800 token，单价分别为 2 与 8 货币单位，模型部分费用是 0.0184。若任务平均尝试 1.2 次，还需要按尝试分布估算，不能只报第一次成功调用的费用。

```text
model_cost = input_tokens * input_rate / 1_000_000
           + output_tokens * output_rate / 1_000_000

end_to_end = queue + retrieval + model + tools + rendering
model_time ~= first_token_time
            + max(output_tokens - 1, 0) / decode_rate
```

模型时延公式是单请求的近似。输出速率可能随并发与长度变化，推理服务可能批处理，流式响应也会改变用户感知。排队增加时，缩短提示未必能解决延迟。应分别记录检索、模型首 token、生成、工具与总耗时，再检查同一时间的流量和重试次数。

序列任务的耗时通常沿关键路径累积，独立查询可以并行。并行降低等待的同时会增加瞬时资源需求和接口限流风险。假设三个独立读取分别需要 100、200、300 毫秒，理想并行路径约为 300 毫秒，串行约为 600 毫秒；真实系统还需算调度与网络开销。若第三步依赖第一步确定的编号，就不能无条件同时启动。

P50 是一半请求的等待位置，P95 反映慢尾。若工具故障只影响百分之三的任务，平均时延可能看着不错，少数用户却长期卡住。交付验收应同时规定正常与失败路径的等待边界，并记录取消、超时与人工接管的结果。模型成本也要按完成任务计算，失败重试和人工复核不应隐藏在另一张表中。

## 5.8 做一次有归因能力的对照实验

先固定任务集、数据快照、权限和输出校验，记录基础版本。随后只改变一个主要因素，如证据排序、摘要策略或输出长度。每个版本在相同任务上运行，保存原始响应、错误层级、token 用量和时延。若模型版本也同时变化，结果只能说明组合版本变化，不能把改善全部归给新提示。

| 观察到的问题 | 最先检查 | 对照实验 | 暂时不要下的结论 |
| --- | --- | --- | --- |
| 引用了失效条款 | 生效时间与索引快照 | 仅提供现行条款 | 模型永远不会理解日期 |
| 格式正确但编号不存在 | 来源绑定与事实校验 | 限制候选编号集合 | schema 已经保证正确 |
| 长任务越做越偏 | 状态保存与摘要差异 | 保留结构化状态 | 必须增加上下文窗口 |
| 高并发首 token 变慢 | 排队与服务限流 | 固定长度做负载对照 | 提示一定太长 |
| 成本下降、拒答上升 | 成功与拒答口径 | 比较同批可回答任务 | 新版一定更高效 |

调试时优先寻找最小失败输入。从一万字材料中逐步移除无关片段，观察错误是否仍在。移除时保留业务事实与权限条件，不能把本来困难的任务改成另一道简单题。最小复现可以提交给模型或平台团队，生产数据需经过脱敏与授权，不能直接粘到公开 issue。

## 5.9 本章工作坊与答案线索

工作坊一要求读者为 16,384 token 窗口分配预算。固定规则 900，工具 1,600，问题 200，历史 2,500，输出 2,000，安全余量 500。证据最多可以分到 8,684 token。继续回答，如果三个必要片段只占 1,200 token，是否还应补满剩余空间。答案需要回到质量对照与业务必要性，窗口余量本身不构成增加资料的理由。

工作坊二把教学 KV 参数中的头数由 8 改为 4，缓存长度和其它条件保持不变。估计值从 2 GiB 降到 1 GiB。如果真实测得峰值显存只减少很小比例，检查权重、激活与其它工作区所占份额。公式只测一个组成项，不等于整进程显存。

工作坊三让读者处理冲突证据。供应商目录写某规格可替代，企业批准表写尚待验证。输出应标记资料分歧，保留两个来源，阻止提交替代请求，提示所需批准信息。别让模型通过挑选一条听起来更权威的文字完成业务裁决。

工作坊四设计摘要回归。准备一次用户从 120 件改成 12 件的对话，保留未批准状态。摘要前后逐项比较数量、对象与批准字段，再把旧预览提交给执行服务。正确结果包括摘要字段一致和旧预览被拒绝。只测试摘要是否通顺，会漏掉真正影响采购的错误。

交付物是一张上下文预算表、一组格式与事实校验器、一份最小失败样本，以及按任务记录成本和时延的实验报告。读者可以把它们直接移到最后的项目章，替换教学参数与数据源即可。模型和硬件发生变化时，计算方法仍可使用，参数与测试结果需要重新测。
