# 第 11 章　需求发现与现场访谈

需求发现的结果应当让团队能够决定下一步验证什么。会议记录有用，但还需要任务样本、流程、基线与关键未知项。

## 请用户带来一次真实任务

访谈可以从最近完成的一次工作开始。请对方展示允许公开的输入、操作过程和最终结果。询问在哪一步需要停下来查资料，哪一步必须请同事帮忙，以及做错以后怎样发现。

不要只与项目发起人交谈。一线用户知道实际动作，流程负责人知道规则和资源，安全与 IT 人员知道接入条件，预算负责人知道项目为何值得投入。各方说法不同，往往反映了不同责任，无须急着把它们压成同一个答案。

## 观察与解释分别记录

「用户复制了三个系统的编号」是观察，「接口缺失导致工作慢」是解释。解释需要继续验证。也许存在接口，只是用户没有权限；也许编号不一致，连接接口也无法直接匹配。

访谈结束后，把事实、假设和待验证问题分栏整理。涉及个人数据或商业机密时，记录必要信息即可，不应为了完整而扩大采集范围。

## 发现阶段的出口

| 材料 | 能回答的问题 |
| --- | --- |
| 问题说明 | 谁在什么任务上遇到什么障碍 |
| 当前流程 | 人、数据和系统怎样协作 |
| 正常与失败样本 | 好坏结果怎样识别 |
| 基线记录 | 当前耗时、质量与成本怎样 |
| 依赖清单 | 权限、接口和负责人是否就绪 |
| 验证计划 | 下一步先检查哪个假设 |

如果关键数据拿不到、业务负责人不愿投入时间，或结果无法判断，团队应先解决这些条件。进入开发不会让这些问题自行消失。

## 访谈前先形成可检验的假设

本章使用 Palantir 的用例界定入口与 NIST 的风险管理材料作为公开阅读基础。下面的访谈计划、样本选择和采购任务记录均由作者设计。它们是实施方法示范，不能作为真实客户经历引用。

一个访谈可以围绕三个未知展开。用户的时间究竟花在哪里，正确结果怎样判定，以及取得必要数据与权限的代价有多大。每个未知对应证据。时间需要观察和记录，正确性需要任务结果与评分规则，接入条件需要接口、身份及负责人。提前写出证据需求，可以防止访谈结束后只留下一份意见清单。

不要在假设里偷放方案。采购人员经常寻找物料编码属于可调查的问题，必须做语义搜索属于尚未验证的选择。把后者带进访谈，会容易收集到赞成搜索功能的意见，却漏掉编码实际来自历史订单或熟人询问的证据。

| 访谈前假设 | 需要寻找的材料 | 可能推翻它的证据 |
| --- | --- | --- |
| 找编码占了主要操作时间 | 合法任务的逐步操作记录 | 主要时间耗在等待审批 |
| 描述不一致造成返工 | 原描述、最终编码及修改原因 | 返工来自价格或单位问题 |
| 现有系统无法直接查询 | 接口清单及实际身份试查 | 接口已有，问题是权限未开 |
| 用户会接受候选加证据 | 用候选页面完成真实任务 | 证据难以核对，复核更慢 |

## 访谈计划覆盖不同责任位置

先与任务操作者确认每天怎样工作，再与流程负责人确认哪些规则不能改变。数据和接口负责人帮助核对信息流，安全负责人确认采集与处理范围，预算负责人解释为什么投入。不同角色可以由同一人担任，但记录里仍要区分其判断的身份。

作者设计的四十五分钟访谈，前五分钟确认目的、记录方式和敏感范围，随后十五分钟回放最近一次允许展示的任务，十分钟讨论一次异常，再十分钟核对规则与依赖，最后五分钟共同回读结论。时间仅供安排，若异常任务涉及未授权材料，立即停止该项观察，改用已获批准的脱敏材料。

向用户提问时，优先要求描述动作。最近一条任务怎样开始，先打开哪个系统，为什么在这一步查资料，结果交给谁，做错后怎样发现。问用户最想要什么可以获得方向，但不能据此直接设计全套需求。用户对未来功能的判断需要使用测试补证据。

## 把观察做成可回读的任务记录

采购例子的任务记录可以包含触发事件、原描述、允许使用的资料、操作起止及结果状态。记录人同时写下观察与解释，避免把自己的推断混进事实列。使用演示数据时，事实只表示这次教学演示里观察到的动作。

| 观察记录 | 暂时解释 | 下一次核对 |
| --- | --- | --- |
| 操作者查询了历史订单编号 | 历史订单可能帮助确认物料 | 编号是否可靠、是否有过期规格 |
| 录入时手动换算箱与件 | 主数据缺少包装换算关系 | 是否有权威换算表 |
| 草稿完成后等待另一岗位 | 存在审批依赖 | 等待原因与可处理时段 |
| 订单被退回重新填单位 | 单位口径产生返工 | 退回规则与发生频率 |

样本应能比较正常与异常。连续取一个授权时间窗口内的任务，比挑选最适合演示的几条更容易解释。若只能取得少量样本，明示范围并把样本代表性列为风险。不能因为样本少，就补上没有发生的客户故事。

资料的采集范围要比项目功能范围更谨慎。若目标只需规格、编码和操作时间，未必需要员工姓名或供应商银行账号。标明保存位置、访问者、保留依据及使用目的。合成样本用于公开演示，原始客户材料保留在授权环境。具体数据保留要求由组织确认，本书不提供统一期限。

## 用问题说明固定已经达成的认识

一份问题说明可以写成一段普通文字，限定角色、任务、当前困难及影响。教学示例中的采购人员在限定组织内处理紧固件需求，需要把描述映射到有效编码和单位。当前缺少可核对的包装关系，造成重复查询及退回。下一步先验证数据是否支持可靠匹配，不承诺自动采购。

读者应检查段落里每一项是否有证据。重复查询来自观察，退回来自允许查看的记录，限定组织来自授权。若频率和时间未测，就不填写节省百分比。若还不知道正确物料由谁判定，项目仍缺少评分条件。

问题说明还需要列出未达成共识的部分。不同人员对同一物料是否可替代有争议时，整理原始规则与分歧，邀请拥有决定权的人确认。将两种规则平均或让模型选择，会把尚未解决的业务责任变成系统风险。

## 从发现材料选择下一项实验

选择实验时检查影响和验证代价。物料换算缺失若会使全部提交失败，就应优先核对换算数据。页面颜色意见虽易验证，却不一定影响项目可行性。每个实验记录假设、输入、负责人与看得到的结果，并说明结果如何改变方案。

| 关键未知 | 最小验证动作 | 可见结果 |
| --- | --- | --- |
| 候选能否满足规格 | 专家核对一批脱敏需求与候选 | 错误类型及未覆盖条件 |
| 身份能否限定组织 | 用两种授权身份查询同一材料 | 跨组织访问被拒绝 |
| 接口语义是否明确 | 在授权测试环境提交并查状态 | 受理与完成是否可区分 |
| 新入口是否增加工作 | 让操作者完成一次限定任务 | 操作与复核时间记录 |

发现阶段应允许停止。没有合法数据、没有结果判断者，或关键依赖在本期无法取得，都可能使当前方案无法实施。停止时保留已经核对的事实、失败原因及转向条件，使下一位团队成员能够继续判断。

## 访谈后的回读处理分歧

把记录发给对应角色核对，只提供其有权访问的内容。操作者核对动作，流程负责人核对规则，数据负责人核对字段。用一份混合文档要求所有人统一同意，可能让敏感资料和专业判断越过边界。

若采购操作者说历史订单可以确定物料，数据负责人认为旧订单规格不可靠，先列出各自的依据。选取已批准的样本检查旧编码是否仍有效，再决定历史订单可以提供候选还是可以作最终事实。两种用法有不同风险。

回读不是投票。对无法统一的问题，找拥有规则责任的人决定，同时记录证据缺口。发现报告保留实际分歧和下一步验证，读者才能看出项目尚未解决什么。没有争议的记录也需能追到来源，避免把沉默当成接受。

## 本章练习

用一次短访谈获取一个正常样本和一个异常样本。访谈后写一段不含工具名的问题说明，再请受访者修正。检查双方是否同意项目要改变的那一步工作。

提交一份事实、假设和未知三栏表，至少包含四条任务动作及一个能推翻当前方案的证据。参考答案应将操作者做了什么与为什么这样做分开，并指定下一次核对对象。最后找出一项无需采集的敏感字段，解释删去采集需求后实验为何仍能成立。
