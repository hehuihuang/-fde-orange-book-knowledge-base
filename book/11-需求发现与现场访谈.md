# 第 11 章　需求发现与现场访谈

需求发现的结果应当让团队能够决定下一步验证什么。会议记录有用，但还需要任务样本、流程、基线与关键未知项。

## 请用户带来一次真实任务

访谈可以从最近完成的一次工作开始。请对方展示允许公开的输入、操作过程和最终结果。询问在哪一步需要停下来查资料，哪一步必须请同事帮忙，以及做错以后怎样发现。

不要只与项目发起人交谈。一线用户知道实际动作，流程负责人知道规则和资源，安全与 IT 人员知道接入条件，预算负责人知道项目为何值得投入。各方说法不同，往往反映了不同责任，无须急着把它们压成同一个答案。

## 观察与解释分别记录

「用户复制了三个系统的编号」是观察，「接口缺失导致工作慢」是解释。解释需要继续验证。也许存在接口，只是用户没有权限；也许编号不一致，连接接口也无法直接匹配。

访谈结束后，把事实、假设和待验证问题分栏整理。涉及个人数据或商业机密时，记录必要信息即可，不应为了完整而扩大采集范围。

## 发现阶段的出口

| 材料 | 能回答的问题 |
| --- | --- |
| 问题说明 | 谁在什么任务上遇到什么障碍 |
| 当前流程 | 人、数据和系统怎样协作 |
| 正常与失败样本 | 好坏结果怎样识别 |
| 基线记录 | 当前耗时、质量与成本怎样 |
| 依赖清单 | 权限、接口和负责人是否就绪 |
| 验证计划 | 下一步先检查哪个假设 |

如果关键数据拿不到、业务负责人不愿投入时间，或结果无法判断，团队应先解决这些条件。进入开发不会让这些问题自行消失。

## 本章练习

用一次短访谈获取一个正常样本和一个异常样本。访谈后写一段不含工具名的问题说明，再请受访者修正。检查双方是否同意项目要改变的那一步工作。
