# 第 15 章　可观测性与故障处理

用户报告「结果不对」时，工程师需要把一次任务还原到具体步骤。可观测性提供这种还原能力，同时也要控制记录内容带来的隐私风险。

## 记录可解释的一次请求

为一次任务分配关联标识，把检索、模型调用、工具执行和人工接管联系起来。记录开始结束时间、状态、版本和必要的输入输出摘要。不要无差别保存敏感全文，也不必要求模型暴露隐藏的内部推理过程。

运行记录应使团队能够区分响应慢、请求失败、模型答错与业务处理失败。服务返回成功，并不意味着订单已正确更新或用户问题已解决。

## 监控用户能感受到的结果

Google SRE 的监控材料讨论延迟、流量、错误与饱和度。模型应用可以保留这些服务指标，再增加引用错误、工具失败、人工接管和任务完成情况。每个告警最好对应一个能采取行动的人与处理办法。

| 故障 | 保守处理方式 |
| --- | --- |
| 模型超时 | 有限重试，随后提供人工或非模型路径 |
| 写工具超时 | 先核对状态，再决定是否重试 |
| 检索不可用 | 显示限制，不编造无证据答案 |
| 费用异常 | 限制流量、检查循环与调用预算 |
| 质量突降 | 暂停高风险功能并回放失败样本 |

## 备用模型也需要验证

接口兼容不保证行为一致。备用模型的结构化输出、工具参数、拒答与政策遵守情况都需要测试。切换时可以先关闭高影响操作，提高人工参与比例，等关键指标稳定后再恢复。

事故复盘记录触发条件、时间线、影响范围、恢复动作和预防改动。重点是让相同故障更早被发现、影响更小，并留下可重复的测试。

## 一次任务怎样还原到每项依赖

本章查阅了 OpenTelemetry 的追踪概念以及 Google SRE 的监控、过载处理和事故组织材料。下面的采购日志和故障演练全部由作者设计，不代表 Assembled 或其它公司的运行记录。

一次用户任务分配稳定的 task_id，一次请求分配 request_id，跨服务步骤通过 trace_id 关联。OpenTelemetry 用 span 表示追踪中的操作及父子关系。一个任务可能有多次请求，一次请求也可能触发多个依赖。区分这些标识，可以避免把重试、用户补充及独立任务混在一起。

教学采购请求可以有身份校验、数据查询、候选匹配、字段检查和草稿保存几个步骤。每一步记录开始结束、状态、版本、必要的结果摘要以及允许的错误码。摘要应帮助排查，不应无差别保存敏感全文。生产日志的字段、访问范围及保留方式由组织批准。

```json
{
  "task_id": "teaching-task-017",
  "request_id": "teaching-request-042",
  "operation": "draft.validate",
  "status": "needs_information",
  "reason_code": "unit_conversion_missing",
  "release_id": "teaching-release-4",
  "duration_ms": 12,
  "sensitive_text_recorded": false
}
```

这个日志是机器字段示例，时间只用于说明格式，没有来自实测。缺少单位属于可解释的业务状态，不能一律记为基础设施错误。模型超时可以记录技术失败，而因授权拒绝的查询应记录预期安全行为。状态分类影响告警与后续统计。

## 从用户结果回到组件指标

Google 的监控资料提出延迟、流量、错误和饱和度等服务观察方向。模型应用还需任务与质量维度。某次草稿请求返回正常，但候选规格错误，属于业务质量问题；某次应用错误提示出现前用户已经关闭页面，后端成功指标可能仍看不见体验失败。

| 观察范围 | 教学系统的指标 | 排查时需要的切片 |
| --- | --- | --- |
| 用户任务 | 完成、放弃、转人工及复核时间 | 用户角色、任务类别及入口 |
| 服务请求 | 延迟、失败与并发 | 版本、组织及请求路径 |
| 模型依赖 | 调用、超时、格式失败及费用 | 模型标识、任务类别及配置 |
| 数据检索 | 无候选、过期及引用缺失 | 数据版本与物料类别 |
| 外部动作 | 已接受、已完成与结果未知 | 请求标识及工具版本 |

分位数不能简单平均。两个组织各自的 p95 延迟均值，不一定等于整体 p95。应保留适当的分布记录，再按一致口径汇总。任务时间也应包含等待与人工接管，不能只测模型生成。

## 告警要对应可采取的动作

先定义用户认为合格的事件，再确定测量方法和目标。教学假设允许百分之一的请求不满足某项速度要求，当一个窗口中不合格比例达到百分之十，错误预算消耗速率可写作 0.10/0.01=10。这个计算帮助理解异常程度，不意味着任何项目都应使用该目标或立刻按同一阈值告警。

短窗口适合发现突发问题，长窗口帮助避免随机波动。是否唤醒值班者，还取决于影响和能否采取动作。候选覆盖缓慢下降可能进入质量检查，越权或未知业务写入则需要及时暂停与核对。告警包括负责人、运行手册和当前影响，而不只是发送一条模型不好了。

每项告警演练至少回答三件事。接收者能否找到故障范围，能否安全停止新增影响，能否让必要业务继续办理。无人接收或无法行动的通知，会增加噪声。告警恢复也需有条件，不能只因依赖恢复联网就自动打开高风险动作。

## 超时、重试与状态未知分别处理

给一次任务设置总时间和调用预算，再向每项依赖分配较小预算。若每个步骤都单独无限重试，整条链路会超过用户能够等待的时间。重试仅用于合适的临时故障，采用有上限的次数、退避与随机扰动，防止大量请求同时再次冲击依赖。

读取超时通常可以按策略重试，写入超时需要先核对。客户端未收到响应，不能证明服务器未执行。教学采购系统保留同一幂等标识，并查询原请求状态。权限错误、字段不合法及单位缺失没有通过重试自行改善的依据，应进入相应修正或接管路径。

过载时限制新任务、减少非必要调用或进入非模型路径。长队列会让原本有价值的结果失去时效，尤其库存和价格。队列等待超过有效条件时，执行前重新检查关键事实。容量下降不应通过省略授权和校验补偿。

## 事故组织让恢复和沟通能并行

Google 的事故材料区分协调、运行处理及沟通等责任。小团队可以由少数人兼任，但要说清谁协调、谁改系统、谁通知业务。多人同时尝试切换版本而没有协调，可能使恢复动作互相覆盖。

| 事故阶段 | 动作 | 应留下的记录 |
| --- | --- | --- |
| 识别 | 核对是否真实影响任务 | 发现时间、版本及范围 |
| 控制 | 暂停相关写入或缩小范围 | 开关、执行者及生效时间 |
| 恢复 | 用已验证路径接管 | 恢复条件及未知任务列表 |
| 核对 | 比较外部状态与任务记录 | 已成功、未成功及仍未知 |
| 复盘 | 补足控制与回归 | 根因依据、改动责任及验证 |

事故报告只写已核实的影响。先通知当前已知范围和下一次更新安排，随后补证据。不要过早归因某个工程师或模型供应商。复盘寻找使错误发生、扩散和未被及时发现的条件，改动要能通过测试或演练检验。

## 日志本身也有安全边界

用户输入、工具结果和资料正文可能带个人信息、商业秘密或恶意内容。日志访问者不应自然获得所有业务数据权限。尽可能记录标识和必要摘要，保留原始材料时采用获批的独立访问控制。不能通过可观测性平台把受限内容传播到另一个未授权环境。

排查无需获取模型隐藏的内部推理。可见输入、工具调用、引用、版本及结果通常足以形成可操作证据。模型提供的解释可以辅助阅读，但不能代替真实执行记录。事故中的输出理由与日志中的动作冲突时，以真实状态与记录核对。

## 一条故障时间线怎样核对

教学时间线可以用相对时间避免伪造客户记录。零秒发起提交，两秒后台创建申请，五秒客户端超时，十秒用户重复点击，十五秒状态查询获得原申请。这五件事件说明客户端失败提示与业务成功可以同时存在。

日志核对需要把后台创建、客户端超时及重复点击关联到原任务，并确认重复点击没有创建新申请。如果只记录客户端错误，团队会误认为任务失败；只记录后台成功，又看不见用户困惑。各记录共同解释一次任务。

复盘增加一个回归输入，模拟响应丢失与重复点击，检查同一申请标识和最终用户状态。故障解释最终形成可重复测试，才便于确认修正真正生效。时间线的记录粒度以能还原决定和影响为准，不必采集所有正文。

## 本章练习

选择一个可安全模拟的依赖故障，观察系统是否在预算内停止。检查用户看到的提示、日志里的信息和人工接管材料是否一致。演练不得影响真实客户或触发未授权写入。

模拟提交响应中断但后台完成的情况，写出用户提示、日志及接管包。参考答案保留原请求标识，将状态记为未知，核对后台后更新为完成。不得直接报失败后用新标识重建。再检查日志里有没有一项可以用标识替代的敏感全文。
