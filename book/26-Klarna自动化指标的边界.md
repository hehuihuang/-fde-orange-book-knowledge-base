# 第 26 章　Klarna，自动化指标的边界

客服自动化最容易被浓缩成几个大数字。Klarna 的案例适合放在后面阅读，因为读者此时已经能够区分工作量、服务质量与财务结果。

## 公开事实与证据

2024 年的 OpenAI 客户案例报告，Klarna 助手在首月处理约 230 万次对话，约占客服聊天的三分之二；发布方将其工作量描述为相当于 700 名全职客服。页面还报告处理时间与重复咨询的改善。

证据等级为 A，属于联合发布方口径。「相当于 700 人的工作量」不能直接改写为实际裁掉 700 人。预测的财务贡献也不能与后来披露的实际成本节省混为一项数据。

## 怎样检查自动化是否有效

以下为本书分析与教学设计，证据等级为 D。一次聊天结束，不代表用户问题解决。系统可能把用户引导到别的渠道，用户也可能稍后再次联系。评测需要跨越单次对话，观察重开、重复咨询、投诉与错误操作。

| 常见指标 | 必须补问的口径 |
| --- | --- |
| 自动化率 | 哪类任务、哪个渠道、是否含转人工 |
| 处理时长 | 只看对话还是包含后续处理 |
| 解决率 | 谁确认解决、是否跟踪再次联系 |
| 满意度 | 谁回答调查、未回应者如何处理 |
| 成本节省 | 是否扣除模型、复核与支持成本 |

## 保留服务选择与接管

低风险、规则清楚的查询可以先尝试自动处理。涉及身份、争议或特殊政策的情况，需要明确的人工路径。用户不应为了获得人工帮助而反复与系统争辩。

即使低风险任务自动化效果稳定，也要监测流量变化。新的政策、产品或语言都可能改变输入分布。扩大范围之前，用新的样本检查质量，而非直接延用首月结果。

## 统计单位先于自动化率

以下的客服数据均为作者设计的合成样本。一个问题可能经历三次聊天、一封邮件和一次人工回访。按对话计数，自动系统处理了两次聊天可能得到较高自动化比例；按问题计数，任务仍可能没有解决。项目需要分别维护会话 ID、业务问题 ID 与业务对象 ID，说明怎样关联、关联不了的比例是多少。

定义解决时，还要确定确认方与观察窗口。工具执行成功、用户点击已解决和一段时间内未再次联系，证明的事情各不相同。未再次联系可能来自成功，也可能来自放弃。报告应按可观察事实命名指标，避免把聊天结束状态直接改称问题解决。

| 统计单位 | 能说明什么 | 主要误读风险 |
| --- | --- | --- |
| 消息 | 系统回复工作量 | 把多轮回复当成更多解决 |
| 会话 | 单次互动结果 | 忽略后续转渠道与重开 |
| 业务问题 | 跨会话处理结果 | 错误合并两个不同请求 |
| 客户 | 用户层面的体验 | 高频问题用户与普通用户混合 |
| 实际支出 | 财务期间成本变化 | 将预估节时当现金收益 |

## 总体改善怎样掩盖困难任务退步

在一组合成基线中，简单任务一百条解决九十条，困难任务一百条解决五十条，总体解决率为 70%。新版的数据包含简单任务二百条解决一百六十条，困难任务十条解决四条，总体约为 78.1%。总体上升，两个任务类别内部却分别从 90% 降至 80%、从 50% 降至 40%。

差异来自任务组成变化。比较版本时，应保留任务类别、渠道、语言、时间与转人工策略。可以使用相同测试集，或者按固定任务权重报告标准化结果；真正的生产流量变化也要单独报告。只发布一个总率，会让负责人错误地扩大本来退步的困难任务。

类别划分必须在看结果前确定，并记录无法分类的请求。模型自己分类可能出现误差，也可能随着版本变化；需要抽样核对分类一致性。若自动化策略让困难请求提前转给人工，它们是否仍进入总体分母，也应明确。

## 一笔带人工复核的成本账

假设一个月有一万条教学任务，基线平均每条成本为四个货币单位，总成本四万。新流程让六千条自动处理，每条模型与工具成本零点六；剩余四千条人工处理，因为任务更复杂，平均成本变为六；平台支持与质量复核共八千。新总成本为三万五千六百，实际模型下节省四千四百。

```text
baseline = 10_000 * 4 = 40_000
new_cost = 6_000 * 0.6 + 4_000 * 6 + 8_000 = 35_600
difference = 40_000 - 35_600 = 4_400
```

如果只把六千条任务乘旧平均人工成本，报告的毛额为二万四千，远高于加入实际剩余任务与运营成本后的差额。这个演算没有真实公司数据，也没有考虑一次性开发、容量闲置、错误赔付或需求变化。实际财务评价必须按企业可核对的支出与期间口径完成。

时间释放不一定立刻减少支出。人员合同、任务需求与组织安排可能使短期人力支出不变，价值表现为服务容量或等待改善。项目可以报告这些结果，但要与现金成本分开。

## 自动化范围怎样逐步扩展

作者建议教学项目先验证一类低风险、规则明确的任务，再给新任务单独形成数据集、失败条件和人工路径。原有任务通过评测不代表新语言、争议或身份问题也适用。出现严重越权或不可逆错误时，关闭相关动作，保留可用的查询与人工渠道。

用户满意度调查需要记录邀请人数、回应人数和任务类别。只邀请完成自动任务的用户，会忽略接管、失败或放弃的人。服务监控还应检查转人工之后的等待、再次联系与投诉，避免自动渠道把成本转移给其他团队。

暂停条件可以针对严重错误单独设置，而无需等平均满意度下降。条件来自组织风险承受与业务责任，不能引用本案例的首月数字作为通用验收线。

## 读者实作与复盘

用上面的两类任务复算总体与分组结果，再按基线中各占一半的权重计算新版标准化结果。答案为 60%，说明同一权重下表现下降。写一份简短报告，同时保留生产总体、分组与固定权重结果。

然后为自动处理、人工接管和用户放弃各设计一个观测事件，说明哪些事件仍不足以证明解决。最后按成本账列出遗漏的一次性和持续成本，给出需要财务团队提供的真实字段。

## 可复用的 FDE 工作包

制作一个分任务客服报告，同时显示自动处理、人工接管、再次联系与投诉。把严重错误单独列出，并为其设置暂停条件。最后把时间节省与实际支出变化分开计算。

## 资料没有说明什么

早期案例没有披露全部客户分组、长期跟踪与独立对照。它能说明发布方报告的特定阶段结果，无法支持「客服可以全部自动化」或「客服自动化必然失败」这样的结论。
