# 第 25 章　Assembled，客服系统的韧性

客服应用既要处理普通问题，也要在模型或工具故障时继续服务。Assembled 的案例把评测、人机分工与依赖切换联系起来。

## 公开事实与证据

Anthropic 的案例介绍 Assembled Assist 如何评测回复、利用人工修改改进系统，并在 AI 与人工之间安排任务。材料还报告，一次其他模型供应商故障期间，团队在约二十分钟内将工作流切换到 Claude。

证据等级为 A，属于供应商客户故事。公开说明不能证明切换后的每一种任务质量完全相同，也不能保证其他系统获得相同恢复速度。

## 人工修改怎样成为证据

以下为本书分析与教学设计，证据等级为 D。客服修改了回答，可能是在纠正事实，也可能只是改变语气。应先给修改分类，再决定是否进入标准样本。人工编辑同样可能出错，因此仍需抽样复核。

路由也需要评测。身份异常、政策例外和无法撤销的操作，应有明确接管条件。系统转交人工时，把已核实的信息与待处理事项一起交过去，减少用户重复解释。

| 要评测的对象 | 可观察的结果 |
| --- | --- |
| 回答 | 事实、政策、语气与完整性 |
| 路由 | 是否在需要时转交正确团队 |
| 工具 | 参数、权限、执行状态 |
| 接管 | 背景是否完整、是否重复询问 |
| 最终服务 | 解决、重开、再次联系与投诉 |

## 切换能力需要平时准备

备用模型应通过关键任务与工具测试。故障发生时，可以先进入保守模式，降低自动执行范围，保留人工渠道。恢复服务之后继续观察质量，不能只检查接口是否响应。

自动化比例越高，人工队列的组成也可能改变。剩下的任务更复杂时，不能拿过去平均处理时长直接评价人工团队。运行指标要反映任务难度的变化。

## 接管记录怎样避免用户重新解释

以下使用作者设计的订单客服教学流程。系统遇到争议、身份核对异常或工具结果不明确时，需要把任务转交人工。接管摘要分开记录用户主张、已经核实的事实、已执行动作与未确认事项。四类信息不能合成一段没有来源的总结。

| 接管字段 | 教学内容 | 证据来源 |
| --- | --- | --- |
| 用户请求 | 希望确认订单是否可取消 | 当前会话 |
| 已核实事实 | 订单当前状态与版本 | 权威订单工具 |
| 已执行动作 | 仅查询，未取消 | 工具回执 |
| 待处理事项 | 政策例外需要人工判断 | 规则与异常代码 |
| 接管对象 | 有权处理该类争议的队列 | 可信路由配置 |
| 身份与范围 | 已完成哪些核对 | 授权服务状态 |

摘要告诉人工哪些事实可以依赖，人工仍需有权访问原始记录。摘要中的“用户说已付款”不能被提升为“付款已核实”。如果工具结果显示支付待确认，接管记录应保留两种来源及冲突，而非选择更流畅的说法。

用户选择人工服务时，可以立即触发路由，无需先证明模型连续失败。系统显示接管状态与预期等待，不再同时开启另一条自动执行路径。否则人工与自动系统可能重复操作同一订单。

## 写工具超时后怎样恢复

客服模型生成的文字可以重试，业务动作则可能已经发生。教学场景中，取消工具返回超时有三种可能。请求未到达，请求已经失败，或取消成功但回执丢失。应用应查询权威动作状态或使用稳定幂等键重试，不能仅因为没有收到响应就向用户保证未取消。

```text
task_id -> stable action_key
action_key -> accepted / completed / failed / unknown
unknown -> reconcile with authoritative service
completed -> return existing receipt
failed -> explain verified failure or hand off
```

动作键的含义由业务服务约定。同一动作重复提交复用键，用户真正发起不同动作需要新的键。把整个会话 ID 当作所有动作的幂等键，会使第二次合法动作被误当成重复。把每次重试都生成新键，则失去去重作用。

切换模型时，任务状态留在应用服务中，不依赖模型自行记住已发生什么。备用模型只接收必要状态、已验证证据与可用工具。原模型尚在执行的动作需要明确交接，不能让两个模型同时重做未确认写操作。

## 故障时缩小自动化范围

作者为教学设定三种运行模式。正常模式按已验收范围运行；降级模式只允许已验证的读取和草稿，关闭未通过备用模型评测的写动作；人工模式保留路由与背景传递。模式切换记录负责人、时间、原因和受影响功能。恢复时先核对未完成任务，再逐项开放动作。

备用服务还可能遇到限流。若原流量一口气全部转移，会耗尽备用配额并引发连续重试。可以保留任务优先级、入口节流、有限重试与人工排队。具体容量需要实测，客户故事里的二十分钟不构成其他部署的恢复承诺。

| 演练故障 | 需要观察 | 不合格结果 |
| --- | --- | --- |
| 模型不可用 | 模式切换与人工入口 | 用户循环等待无提示 |
| 写工具回执丢失 | 动作核对与幂等回执 | 生成新动作重复执行 |
| 备用模型格式不同 | 格式与业务校验 | 解析失败被当成成功 |
| 人工队列拥堵 | 任务年龄与优先级 | 只展示平均等待 |
| 主服务恢复 | 未完成任务对账 | 自动重新发送全部请求 |

## 人工修改怎样进入评测集

修改分类可以包含事实纠正、政策限制、语气调整和补充用户新信息。只把确实需要模型正确处理的部分变成回归样本。人工加入的新资料需要注明来源与时间，不能要求模型从旧输入里预测它。

数据集从生产反馈形成后，还要检查客户、语言与任务覆盖。反馈多的用户不一定代表总体，人工修改较少也可能是用户放弃了任务。评测集需要主动加入权限异常、争议、工具超时与不应自动处理的样本，不能只收集成功回复。

## 读者实作与复盘

构造一次取消请求回执丢失，写出系统记录、用户提示与人工接管摘要。再假设备用模型未通过写动作测试，说明切换后哪些功能还能用。

答案应保留结果未知状态，并安排权威对账，不宣称成功或失败；备用模式可以提供只读查询与草稿，但关闭未验收写动作。把服务恢复与自动化范围恢复分开，是这项练习的核心。

## 可复用的 FDE 工作包

准备人工修改标签、路由评测集、接管摘要格式和依赖故障演练。对同一批高风险样本比较主模型与备用模型，写下差异以及切换时必须关闭的功能。

## 资料没有说明什么

公开材料未给出全部评测器误差、客户分布、切换过程中的功能限制和成本。某客户的结果不能直接代表所有部署。
