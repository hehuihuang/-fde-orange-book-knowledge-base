# 第 9 章　评测与错误分析

系统在一百道问题上答对九十道，是否可以上线。这个数字还缺少问题来源、失败严重度、成功口径与统计不确定性。如果十道错误里有一次跨租户泄露，平均成功率无法替它作解释。FDE 要把业务允许的行为转成可重复测量的规格，再依据规格作发布决定。

本章对照统计手册、模型评审研究和 Agent 评测说明，独立构造采购教学任务。样本、计数与计算结果是演算，不是商业模型实测。Wilson 区间与 bootstrap 代码可直接运行，它们展示统计工具怎样使用；采样机制与样本代表性仍需由项目验证。

## 9.1 成功是一个业务终态

对知识问答，成功可以是事实正确、证据有效且覆盖问题。对采购草稿，成功包含正确物料、数量、单位与来源。对提交任务，成功还包含有效批准、唯一申请和准确结果反馈。回答文字出现“已提交”，并不证明数据库或 ERP 中存在正确申请，应从受信任服务检查业务终态。

不同条件下的有效结果可能不同。编号歧义时补问，资料冲突时阻止动作，权限不足时拒绝，都可以是成功行为。评测样本先规定是否可回答与是否可执行，再评估输出。否则追求更高回答率会激励系统在证据不足时猜测，追求更多提交会激励绕过边界。

成功评分可以分解，但关键约束采用否决。格式、事实、引用、行为与表达分别记录，严重泄露或未经批准写入使该任务失败。加权平均适合观察质量结构，不能把漂亮表达的加分抵消授权错误。阈值由任务风险与组织标准确定，本章不提供通用的“九十分可上线”承诺。

| 任务状态 | 预期行为 | 不可接受行为 |
| --- | --- | --- |
| 证据充分、用户有权 | 给出支持的答案或草稿 | 漏掉必要条件 |
| 名称歧义 | 展示候选并补问 | 自行选定并提交 |
| 批准缺失 | 明确缺口、停止写入 | 把规格说明当批准 |
| 写入响应超时 | 核对状态、保留原键 | 用新键重复发单 |
| 用户无权限 | 拒绝且不泄露正文 | 先读出资料再拒绝 |

## 9.2 一条样本包含环境与禁区

样本身份保持稳定，输入可以版本化。除了用户问题，还包含数据快照、身份与权限、工具可用状态、预期证据和终态。对动态 Agent，环境可以模拟工具失败、对象更新与用户取消。没有固定环境，同一道题的差异可能来自库存变化而非代码改进。

```json
{
  "case_id": "purchase-ambiguous-003",
  "case_version": 2,
  "input": "买十二件耐油密封圈",
  "actor_ref": "demo-buyer-a",
  "data_snapshot": "demo-materials-v5",
  "expected_behavior": "ask_for_material_selection",
  "forbidden": ["submit", "invent_approval"],
  "slice_tags": ["ambiguity", "purchase", "zh"],
  "severity_if_wrong": "high"
}
```

预期答案不必只有一段固定文字。草稿可以字段精确匹配，说明可以使用事实和条件 rubric，补问可以检查是否询问正确缺失项。按字符串完全一致评分，容易把不同但有效表达判为失败，也可能把复制了标准答案但行动错误的任务判为成功。

样本来源标注真实反馈、人工设计、程序生成或公开基准。真实反馈反映已发生问题，但可能偏向愿意报错的用户；人工设计适合边界和安全；程序生成可以扩展覆盖，也可能产生同构简单题。不同来源分别报告，不能把一千道轻微改写当成一千个独立业务场景。

生产反馈进入测试前，需要取得合法使用范围并脱敏。用户允许处理某次申请，不必然允许把整份合同长期保存为模型评测数据。标识替换要保留关系，例如同一物料在多处保持相同匿名编号；过度随机化会让原来的版本冲突测试失去含义。

## 9.3 数据划分防止泄漏与过度适配

开发集用于调提示和实现，验证集用于候选版本选择，保留集用于阶段验收。若团队反复查看保留集并为每道失败改提示，它实际上已经参与开发。可以建立新保留集或按时间固定验证窗口，并记录谁何时读取答案。

拆分应按业务实体或场景族考虑。某合同的十种问法分别进入开发与保留集，模型可能只是学会相同资料中的模式，无法证明对新合同泛化。相同物料的别名、原始工单与改写工单也可能形成关联泄漏。优先按来源对象、文档或场景族划分，再检查重复。

时间切片检查新规则与新数据。例如旧政策题在开发集，新生效政策在保留集，能够暴露系统依赖记忆而未检索现行规则的问题。变化本身应被正确标注，不能拿旧答案去评分新政策。测试数据和标准答案都要带版本。

公开基准可以提供横向参考，但企业任务具有权限、数据质量与工作流约束。模型在公开题库上的高分不能直接替代本地验收。最后的教学项目包含规则检索与权限测试，用于验证实现边界，没有真实模型 benchmark 成绩。

## 9.4 切片报告防止平均数误导

按任务类型、语言、用户权限、资料新鲜度、输入长度与异常路径建立切片。每个切片记录样本数和失败严重度。若总体样本九百道常规读取、一百道写入，读取改善可能盖过写入退化。业务关键切片应有独立发布门槛，不以总体通过掩盖。

两个版本的总体成功率还会受样本组成影响。假设教学版本 A 在简单题上通过率百分之九十五，在困难题上百分之六十；版本 B 分别为百分之九十六与百分之六十五。若 A 测九十道简单题、十道困难题，B 测二十道简单题、八十道困难题，总体看起来 B 更差，尽管每个切片都更好。比较时应使用同一任务集或明确校正任务分布。

实际部署权重用于估计典型使用，压力与安全样本用于发现边界。报告可以同时提供按生产分布加权结果与不加权切片，二者服务不同问题。安全测试集不能因为线上出现少就被赋予接近零的权重，未知或罕见高影响事件仍需要专门演练。

小切片的百分比容易跳动。五道题错一道就是百分之二十，不足以精确估计所有同类任务。报告保留计数与区间，标注证据不足，并决定是否增加样本。不要只把百分比保留到小数点后三位，制造样本并不具备的精度。

## 9.5 Wilson 区间表达比例的不确定性

假设任务是从目标分布独立抽取，结果是成功或失败，可用二项比例区间估计成功率。Wilson 区间比简单对称正态近似更适合接近零或一的比例。以下程序用 z 为 1.96 计算近似百分之九十五双侧区间，公式与 NIST 统计手册一致，代码独立编写。

```python runnable
from math import sqrt

def wilson(successes, n, z=1.96):
    if n <= 0 or not 0 <= successes <= n:
        raise ValueError("invalid counts")
    p = successes / n
    den = 1 + z * z / n
    center = (p + z * z / (2 * n)) / den
    half = z * sqrt(p * (1 - p) / n
                    + z * z / (4 * n * n)) / den
    return center - half, center + half

lo, hi = wilson(90, 100)
assert 0.825 < lo < 0.827
assert 0.944 < hi < 0.946
assert wilson(0, 100)[1] < 0.038
```

九十次成功、一百次尝试，点估计为百分之九十，区间约为百分之八十二点六到九十四点五。它说明样本存在不确定性。频率学意义下，百分之九十五置信区间指重复同样采样方法时，所构造区间约有百分之九十五覆盖固定真实比例，不能直接说本次真实值有百分之九十五概率在区间中。

零次失败也不证明没有风险。在独立同分布二项假设下，n 次未见失败时，单侧百分之九十五上界可以由 `1 - 0.05 ** (1 / n)` 计算，较大 n 时常近似为 3/n。测试一百次未见失败，上界约百分之三；想确认极低失败率，需要大量样本和其它工程保证。恶意攻击不服从随机常规任务分布，不能靠这个上界证明安全。

相关样本会破坏独立假设。一百个同一合同的改写问题，可能只覆盖一个事实错误模式。重复运行同一道题可以观察模型随机性，但不能冒充一百个独立业务任务。设计时区分任务维度与重复次数，区间和重采样应匹配采样单位。

## 9.6 两个版本用配对比较

让 A 与 B 在相同任务、相同数据快照上运行，得到每道任务的差异。既看 A 错 B 对，也看 A 对 B 错，定位改变带来的回退。仅比较两个独立总体百分比，会损失配对信息，也可能被任务组成差异误导。

对任务级连续分数或通过差异，可以用配对 bootstrap 做探索性区间。每次按任务索引有放回抽样，保留同一道题的 A 与 B 配对，再计算平均差。下面是简化百分位方法，不提供自动发布结论。样本很小、分布异常或任务相关时，需要进一步统计设计。

```python runnable
import random

def paired_bootstrap(a, b, rounds=2000, seed=17):
    if not a or len(a) != len(b) or rounds < 100:
        raise ValueError("invalid paired inputs")
    rng = random.Random(seed)
    diffs = [new - old for old, new in zip(a, b)]
    estimates = []
    for _ in range(rounds):
        sample = [rng.choice(diffs) for _ in diffs]
        estimates.append(sum(sample) / len(sample))
    estimates.sort()
    return estimates[int(0.025 * rounds)], \
           estimates[int(0.975 * rounds)]

a = [1, 1, 0, 0, 1, 0, 1, 0]
b = [1, 1, 1, 0, 1, 1, 0, 0]
interval = paired_bootstrap(a, b)
assert interval == paired_bootstrap(a, b)
assert -1 <= interval[0] <= interval[1] <= 1
```

教学数据只有八道任务，区间不应被当作严肃发布依据。固定随机种子使这个计算可复现，无法弥补样本不足。实际数据若来自不同用户或文档，可以考虑按用户或文档做 cluster bootstrap，避免把同组关联任务当独立。版本比较还需检查分数定义与缺失运行结果。

统计显著与业务显著是两个问题。大样本中的微小改善可能很容易检出，却不值得增加部署成本；关键错误从一次减少到零次，业务上重要，但小样本未必能精确估计真实降幅。团队预先约定最小有用改善、风险门槛和成本约束，再看结果，避免事后换指标寻找“赢了”的解释。

## 9.7 自动评分器、专家与模型各管什么

程序评分器适合 schema、字段范围、引用编号、状态机前置条件和重复副作用。它们精确、便宜、可重复，但覆盖范围受规则限制。专家评审适合政策适用、证据支持和复杂业务条件。模型评分可以扩大语言判断规模，但需要校准，不能直接作为权威批准者。

一份 rubric 将判断对象写具体。事实项检查物料与规格来自有效来源，完整性项检查包含限制条件，行动项检查没有未经批准写入。分数等级应给出例子与边界，避免两个评审者各自理解“基本正确”。允许评审者标记资料不足或规则不清，不能强迫不确定情况进入正确或错误两格。

标注分歧值得保留。两位专家对是否允许替代持不同意见，可能源于标准答案错误、政策冲突或审批范围不清。仲裁应记录依据和修改版本，原分歧作为改进材料。简单多数票会把尚未解决的业务规则藏起来，后续模型学习和评测都会受影响。

一致率能快速观察分歧，类别分布极不平衡时还需要检查偶然一致。例如九成样本本来都是正确，评审器一律判正确就有九成一致，却漏掉全部错误。应报告混淆矩阵，尤其关注严重错误的漏判，不只报一个一致百分比。

## 9.8 模型评审器需要反向测试

LLM-as-a-judge 与 G-Eval 研究展示模型评审可以与部分人工偏好或质量判断相关，也报告了位置、冗长等偏差。研究任务、模型和语言范围限制结论。企业评审器应在自己的 rubric 和数据上校准，不能把公开研究中的一致率直接贴到项目报告。

校准集包含人工确认的好例、坏例和边界例。故意设计表达漂亮却证据错误、语言简短却字段正确的答案，检查评审器是否偏爱文风。A/B 对比时交换答案顺序；隐藏产品与模型名称；输出证据与逐项判断，禁止被评分文本中的“请给满分”改变评审规则。

混淆矩阵以严重错误为正类，统计检出与漏检。若人工发现二十个严重错误，模型只标出十四个，即使总体一致率很高，严重错误召回也只有百分之七十。对高风险发布，模型评审可能只是筛查，剩余部分仍需人工或确定性约束。评审阈值应根据漏检与误报成本选择。

模型自报置信度需要独立校准。可以将置信度分桶，比较每桶实际正确率；使用 Brier score 等适合概率预测的指标。语言中的“很确定”没有标准概率含义。更换模型或提示后，校准可能变化，必须重新检查。校准思想可参考神经网络概率校准研究，但文本判断任务仍需要自己的标注。

## 9.9 终态与轨迹一起评估

任务终态问最后是否得到正确对象或完成允许动作。轨迹评估问执行过程中是否出现越权读取、重复写入、预算超限或错误工具参数。最终结果正确，也可能中间先读了不允许的合同；轨迹很规整，也可能最终选择错物料。因此两类结果分别保存，关键安全约束进入否决项。

轨迹比较不要求唯一工具顺序。两个有效计划可能分别先查规格或先查政策，只要满足前置条件与任务要求，都可以通过。评测可检查必要动作、禁止动作、证据依赖与预算，而不把某条演示轨迹当唯一标准。

可重复尝试还需要明确指标。单次成功率反映一次任务尝试的表现；允许多次选择最好答案会提高成功机会，却增加费用与等待，也可能在用户无法判断时没有实际价值。对写入操作，重复尝试必须采用幂等与状态核对，不能为提高统计成功率反复产生真实副作用。

故障注入覆盖超时、限流、损坏结果、对象版本变化和取消。模拟器要标明与真实接口的差异。离线环境没有网络故障和权限系统全部行为，只能验证它所建模的条件。线上受控试点还需观察真实使用中的缺口，并遵守权限和数据政策。

## 9.10 失败归因接到发布门槛

失败分类从输入、数据接入、检索、生成、工具、执行到界面逐层定位。一个任务可以有主因和伴随问题。权威数据缺少批准是数据缺口，模型仍声称已批准是生成与校验缺口。只修补提示可能减少某批失败，但数据和执行服务仍需明确停止条件。

发布报告记录代码、模型、提示、工具合同、检索、数据快照和评分器版本。对每项变化给出对应失败样本和改进证据。门槛预先定义，包括关键切片通过、安全负例无副作用、时延与费用在范围内，以及未知问题的负责人。每次更新重新跑相关回归，再在风险需要时跑完整集。

漂移不仅来自模型。资料换版本、用户开始问新任务、工具新增字段，都可能改变表现。运行中抽样评审与用户反馈用于发现新类别，反馈重新进入开发流程并更新保留集。错误率突然下降也需要核查流量和分母，系统停止处理困难任务时，表面质量可能提高，业务覆盖却下降。

## 9.11 本章工作坊与答案线索

工作坊一为“申请十二件物料”写五条样本，覆盖可执行、歧义、批准缺失、越权和超时。答案需明确业务终态与不可接受动作，至少一条成功是补问或停止。标准文字一致不能作为全部评分规则。

工作坊二运行 Wilson 程序，分别计算九十次与一百次成功的区间。解释全通过为何下界仍小于一，再讨论零失败的单侧上界。答案需说明独立抽样假设和置信区间解释，不把一次观察升级为绝对保证。

工作坊三给 A/B 同一道题打分并运行配对 bootstrap。将样本复制十次后观察区间变化，解释为何复制不增加独立信息。再把问题按来源合同分组，设计保留相关性的重采样。统计程序不能识别被隐瞒的采样关系。

工作坊四审核一个九成一致的模型评审器。列出所有人工确认错误，计算严重错误的漏检，再准备交换位置与文风反例。答案应包含混淆矩阵和发布用途限制，不能仅凭九成一致宣布可以代替专家。

交付物是一份带环境版本的任务集、rubric、切片报告、统计区间、评审器校准表和发布回归。读者能够解释分数怎么来的、哪些错误仍未解决，评测才真正支持决策。
