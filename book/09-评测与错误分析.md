# 第 9 章　评测与错误分析

评测让「这个结果可不可以用」变成能够重复检查的问题。它需要业务人员参与，因为工程师未必知道哪些错误只影响表达，哪些会导致实际损失。

## 从样本写出规格

一条评测样本包含输入、必要上下文、期望行为、不可接受行为和评分规则。答案不一定只有一种写法，因此可以按事实、完整性、行动和风险分别评分。

样本应覆盖高频任务、边界情况和历史失败。开发集用于调试，保留集用于检查是否只适应了已见过的问题。生产反馈可以补充样本，但需要去除不必要的个人信息，并遵守数据使用授权。

## 评分器各有适用范围

格式、必填字段和参数范围可以用程序检查。事实是否正确、政策是否适用，可能需要专家判断。模型评分适合扩大检查规模，但应与人工标注比较，确认它会漏掉哪些错误。

仅看平均分会掩盖少数高风险问题。把不同语言、任务类型、权限级别与异常条件分开报告。当总体成绩提高但高风险任务退化时，团队应按预先约定的规则决定是否发布。

## 先找到错误发生的位置

| 错误类别 | 可能的工程动作 |
| --- | --- |
| 输入缺信息 | 补问或改变数据采集 |
| 证据未检索到 | 修复索引、查询或权限 |
| 模型误用证据 | 改提示、样例与证据展示 |
| 工具参数错误 | 强化接口约束和参数校验 |
| 写入重复 | 幂等处理与状态核对 |
| 用户误解结果 | 调整界面、标签和确认步骤 |

换模型可以作为实验，但应先有错误分类。否则更好的总分可能只是暂时掩盖了数据或接口问题。

## 把评测接入发布

模型、提示、工具定义、检索配置和政策变更都可能影响结果。发布报告应保留这些版本，并与上一版比较质量、延迟和成本。失败样本可以链接到具体修改，方便后来的人理解取舍。

Morgan Stanley 的公开案例把领域评测放进开发过程。它说明企业应用能够将专家标准转成持续测试，但其具体样本与阈值不能直接套到另一家公司。

## 本章交付物

建立一个小型测试集，故意放入至少一种严重错误。用程序检查与人工检查各跑一遍，比较二者差异。报告不仅列总分，还应能定位每个失败以及它对应的修复动作。
