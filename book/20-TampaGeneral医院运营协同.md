# 第 20 章　Tampa General，医院运营协同

医院的床位安排涉及清洁、人员、设备与患者流转。优化一个局部步骤以后，其他条件仍可能限制整条流程。这个案例适合练习怎样界定业务指标。

## 公开事实与证据

Tampa General Hospital 在 2024 年 6 月的公告中介绍了与 Palantir 扩大合作，以及连通照护协调的计划。公告报告病床分配速度提高 83%、术后恢复区域的停留时间减少 28% 等结果。

证据等级为 A，属于医院发布方报告。公开公告没有提供完整样本、同期对照与各项指标的计算过程。这些数字不应被改写为 AI 单独导致的临床效果。

## 从局部速度走到完整流程

病床安排更快，不必然意味着患者已经更快进入病房。房间可能等待清洁，人员或设备可能尚未就绪。流程测量需要区分申请、匹配、准备、转运与实际到达等事件。

以下属于本书分析与教学设计，证据等级为 D。类似项目可以先建立状态字典，明确每个时间戳由哪个系统产生。对于缺失或延迟更新的状态，系统应显示不确定性，避免把过期记录当成当前事实。

| 需要测量的阶段 | 要分清的情况 |
| --- | --- |
| 提交申请到匹配 | 是否真正找到符合条件的床位 |
| 匹配到准备完成 | 清洁、设备与人员是否就绪 |
| 准备到转运 | 是否存在其他流程等待 |
| 到达后核对 | 系统记录与实际状态是否一致 |

## 让专业人员保留决定权

流程建议可能涉及患者隔离、监护和其他专业要求。系统应将约束作为明确规则，并把无法满足条件的情况交给获授权人员。自动选择一个看起来可用的床位，不代表它满足临床需要。

对状态变化频繁的场景，还要检查并发。两位操作人员同时接受同一资源建议时，最终分配必须由可信系统核对，不能只依赖界面显示。

## 把时间戳拆成可解释的等待

以下是作者设计的资源流转教学数据，不包含患者信息。用相对分钟表示时间，申请在第零分钟提交，第八分钟完成匹配，第十八分钟资源就绪，第四十分钟完成转运。端到端用时为四十分钟，其中匹配八分钟、准备十分钟、转运等待与执行二十二分钟。即使把匹配压到两分钟，其余环节保持不变，总用时仍为三十四分钟。

这个演算只说明局部优化的上限，不能替代真实流程研究。实际各阶段会重叠，提前匹配也可能推动准备工作。测量前先确认事件之间的依赖关系。若准备时间戳晚传，表面上的转运等待可能包含未记录的准备过程，应把时间戳质量纳入报告。

| 教学状态 | 能进入的下一状态 | 转移前的检查 |
| --- | --- | --- |
| 申请已接收 | 待匹配 | 需求字段齐全且有授权 |
| 待匹配 | 资源已建议 | 明确适用约束及数据新鲜度 |
| 资源已建议 | 已保留、建议失效 | 服务端复核版本与占用 |
| 已保留 | 已分配、保留释放 | 人员确认及实际准备状态 |
| 已分配 | 实际完成、异常接管 | 最终行动回执与状态核对 |

状态机允许建议失效、保留释放和异常接管，便于解释失败。一个只展示成功路径的界面会把这些状态压成“处理中”，负责人难以判断是继续等待还是立即处理。

## 资源争用与过期建议

假设两名操作者同时查看空闲资源 R-03，均获得版本号七的建议。第一人确认后，服务端将资源变成已保留并更新版本。第二人的确认携带旧版本，必须失败，并显示需要重新匹配。系统在权威存储中检查版本与状态，界面上禁用按钮只能减少误点，无法保证并发正确。

概念上的条件更新可以写成下面的形式。它是通用数据库教学片段，与医院实际系统无关。

```sql
UPDATE resource
SET status = 'reserved', version = version + 1
WHERE id = :resource_id
  AND status = 'available'
  AND version = :observed_version;
```

应用需要检查受影响的行数。零行表示状态或版本已变化，不能当成成功。完整实现还要把预约回执、权限检查和审计放进相应事务，并考虑保留超时后谁能释放资源。数据库隔离级别、行锁与重试方式应按具体产品验证，不能直接把示意片段接入生产。

## 约束不能通过排序悄悄放宽

硬约束确定可行集合，排序用于在可行集合内选择。专业人员制定的资源适配条件若不满足，系统应返回无法匹配与原因。把不满足条件的资源排在后面，会使它仍有机会被选中，改变了约束含义。

约束记录还要有版本、生效时间和维护负责人。运行中的规则更新之后，既有建议是否需要重审，应提前约定。对于专业处置问题，技术团队不自行推断临床优先级；本书的状态与数据库设计只讨论一般资源系统。

## 观察队列时同时观察容量

资源准备团队忙于处理已有请求时，增加建议数量会增加等待。运行报告应同时给出待处理数、进入速度、完成速度和任务年龄。队列长度短但最老请求等待很久，说明平均数可能掩盖特殊条件任务。可按已定义的运营类别切片，但涉及患者与临床优先级的口径必须由机构专业团队批准。

还要为数据中断准备人工模式。状态来源停止更新后，系统标出最后更新时间，停止自动确认依赖实时状态的动作，保留人工核对渠道。恢复以后对比权威记录与系统记录，明确哪些预约仍有效，避免一次恢复造成重复安排。

## 读者实作与复盘

使用四项通用资源与六条合成请求，构造一次双人竞争、一次状态晚传、一次规则变更。为每条失败写出用户可理解的提示和下一步。答案应该让旧版本确认失败，让晚传状态降低自动化范围，并让规则版本变化触发复核。若设计允许绕过硬约束，需要重新划定授权边界。

最后比较匹配时长与端到端时长。分别说明改进哪一步需要数据治理、哪一步需要人员容量调整。这个区分可以防止技术方案承担它无法改变的运营瓶颈。

## 可复用的 FDE 工作包

制作事件时间轴、状态定义、资源约束和异常接管表。用合成数据重放流程，比较局部用时与端到端用时。项目涉及医疗机构时，需要该机构的临床、信息与隐私团队审核；本书不提供患者处置建议。

## 资料没有说明什么

公告没有披露完整架构、各环节成本和对照方法。不能由运营指标推导患者层面的医疗结论，也不能把这里的效果阈值用于其他医院验收。
