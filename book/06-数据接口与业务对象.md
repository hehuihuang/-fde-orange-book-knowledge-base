# 第 6 章　数据、接口与业务对象

模型应用进入企业后，经常先遇到数据问题。同一个客户有多个编号，同一项金额有不同计算口径，历史记录缺少状态。连接成功只是第一步，理解数据含义才决定后续结果是否可信。

## 先定义业务对象

订单、设备、工单、合同都可以成为业务对象。每个对象有身份、属性、状态和关系。订单关联客户与商品，工单关联订单与处理人。把这些关系写清楚，比先选择数据库更有帮助。

Palantir 的 Ontology 是把数据与业务对象、操作相联系的一种平台实现。学习时可以借此理解对象建模，但不应把特定产品的概念当成所有系统必须采用的架构。

| 数据问题 | 进入模型前的处理 |
| --- | --- |
| 名称不同但对象相同 | 建立标识映射与别名 |
| 单位或时区不一致 | 统一表示并保留原始值 |
| 历史规则已失效 | 记录生效时间与版本 |
| 资料缺失 | 标出缺失，不擅自补全 |
| 用户看不到部分记录 | 查询时执行访问控制 |

## API 是一份行为约定

接口需要说明输入、输出、错误和副作用。一个「更新订单」工具若同时改状态、发通知和触发财务操作，模型或调用者就难以判断影响。尽量把高风险动作拆成语义清晰、权限独立的接口。

读取接口和写入接口应分开设计。读取失败通常可以重试，写入超时则可能存在「已经成功但响应丢失」的情况。再次提交前需要通过业务流水号或幂等标识核对，避免重复扣款、退款或发单。

## 身份应沿请求传递

应用知道用户是谁，并不代表下游服务知道用户能做什么。把所有请求交给一个全权限账户执行，会使用户权限失去意义。服务端应根据受信任的身份信息检查租户、对象和动作权限，不能接受模型自填的用户身份作为授权依据。

日志也属于数据系统。它可能记录客户输入、检索片段和工具参数，因此同样需要访问权限、保留期限和脱敏处理。

## 本章交付物

选一个业务对象，完成字段字典与接口说明。每个字段写清来源、类型、允许值、更新时间和访问范围。再为每个写操作列出副作用、重复提交的处理办法及人工核对方式。
