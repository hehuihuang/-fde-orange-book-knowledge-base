# 第 6 章　数据、接口与业务对象

本章把一个自然语言请求改写成系统能检查的对象与动作。教学请求是“给 A 工厂申购 12 件密封圈”。在任何模型调用前，团队需要确认 A 工厂的租户、密封圈的唯一编号、件与箱的换算、当前批准版本，以及申购会触发的后续行为。语言理解完成之后，这些问题仍要由数据与服务回答。

作者对照了 PostgreSQL 的隔离与行级权限文档、SQLite 的事务说明、Debezium 的 outbox 文档，再设计下面的采购教学模型。表结构、编号与演算均为原创。代码片段采用注明的数据库语法，只说明局部机制；最后项目章提供完整的离线示例。本章不假定某家客户使用这些表，也不把某一平台的对象模型作为行业标准。

## 6.1 对象有身份，名称只是属性

物料名称用于交流，物料编号用于识别。两个名称相同的密封圈可能具有不同尺寸与材质，同一物料也可能存在中文名、英文名、旧编号和供应商编号。把名称作为主键，会让改名变成身份变化，也容易将不同规格合并。应使用稳定标识，并把别名映射到标识，映射关系保留来源与审核状态。

对象还具有状态和关系。物料可以待审、已批准、停用，采购申请可以草拟、待批准、已提交。供应商与物料的供货关系可能有适用地区与有效期。程序通过状态机限制动作。已停用物料可以出现在历史解释里，但不得进入新采购候选；读到一张旧申请，不代表允许按其中的供应商重新发单。

| 对象 | 稳定身份 | 重要属性 | 关系 | 关键动作 |
| --- | --- | --- | --- | --- |
| 物料 | 租户加物料编号 | 规格、基础单位、版本 | 别名与供应商 | 查询、批准、停用 |
| 申请 | 租户加申请编号 | 数量、状态、申请人 | 物料与工厂 | 草拟、送审、提交 |
| 供货条件 | 独立条件编号 | 币种、价格、有效期 | 物料与供应商 | 查看、更新 |
| 批准记录 | 独立批准编号 | 审批人、对象版本 | 申请与规则版本 | 核对、撤销授权 |

Palantir Ontology 是连接数据、对象与操作的一种平台实现，适合帮助读者理解这类建模。跨平台设计仍需写出自己的身份、状态、关系和操作规则。可移植的交付物是字段字典与行为合同，而非对某个产品术语的记忆。

在业务方看来，物料只是一个屏幕上的条目；在数据团队看来，它可能由 ERP 主数据、供应商目录和质量批准表共同组成。FDE 应为每个字段指定权威来源。价格来自生效供货条件，批准状态来自质量系统，库存来自库存服务。把不同表拼成一个对象，并不让拼接结果自动成为权威记录。

## 6.2 版本与时间需要两种视角

对象版本用于判断记录有没有变化。生效时间用于判断这条规则在业务上适用于哪个时期。某供应商价目表 9 月 18 日入库，价格从 10 月 1 日开始生效，入库时间与生效时间不能混用。如果问题询问 9 月的报价，应选择当期有效的条件；如果解释过去某次申请，应使用当时的条件和批准记录。

更严格的历史建模可以同时保存业务有效区间与系统记录区间，即常说的双时间视角。它使团队能够回答“当时实际适用什么”和“当时系统知道什么”。本书的离线项目不实现完整双时间数据库，但仍保存版本、生效时间与创建时间，避免把当前状态直接当成过去状态。

```text
valid_from / valid_to    业务适用时间区间
recorded_at             系统收到记录的时间
object_version          当前对象更新版本
source_version          上游来源版本
```

时间字段应带明确时区或采用约定的 UTC 表示，界面再转为用户本地时间。日期型规则与精确时间戳具有不同含义，如合同“10 月 1 日生效”需要明确适用地区与日期解释。数值单位也要明确，12 件与 12 箱都符合整数类型，却具有不同业务结果。单位换算应来自可审核规则，保持原始数值与换算后数值，不能由模型临时猜。

对象版本还用于执行前的并发核对。用户预览时看到版本 7，另一个人把物料改为停用并增加到版本 8，执行服务应拒绝版本 7 的申请，重新取得状态。版本检查与动作规则共同防止陈旧决策，第十章会把它与批准内容绑定。

## 6.3 数据合同写到错误处理

一份字段字典至少列出类型、允许值、单位、来源、是否可空、更新方式与访问范围。空值要解释。价格为空可能表示未报价、尚未同步或用户无权查看，三者需要不同后续动作。把它们都转成零，会让模型误认为免费；把它们全写成未知，则丢失可修复的原因。

接口合同还应规定错误语义。找不到对象与无权查看对象有时需要对外使用相同提示，避免枚举敏感对象；内部日志可以通过受控错误码区分。同步延迟需要返回数据截至时间，让用户知道结果的新鲜程度。部分来源不可用时，接口应明确哪些字段有效，不能把部分结果包装成完整快照。

```json
{
  "material_id": "MAT-204",
  "tenant_id": "TEN-A",
  "status": "approved",
  "version": 7,
  "base_unit": "piece",
  "price": null,
  "price_state": "not_quoted",
  "as_of": "2026-09-18T10:00:00Z",
  "source_ref": "erp-demo-v12"
}
```

数据合同必须有变更方法。新增可选字段通常比改变旧字段含义风险低。若把 quantity 从基础单位改为包装单位，即使类型仍是整数，也属于语义破坏。版本升级时先让消费者支持新旧表示，验证读取和写入，再切换来源；旧数据是否迁移由组织的保留政策决定，本书不建议为了升级而自动清除用户文件。

可自动检查的合同进入测试。范围检查可以阻止负数量，唯一性检查可以识别重复身份，关联检查可以发现不存在的供应商。完整性和新鲜度检查要按来源区分。若 ERP 每五分钟同步，不能要求所有记录实时；若执行涉及最后一件库存，则需要在动作位置直接查询并锁定或采用服务支持的预留机制。

## 6.4 SQL 查询先保证含义与边界

自然语言到 SQL 的任务应限制可访问的视图、字段和动作。只读账号可以缩小副作用风险，但仍可能读取过多敏感记录。查询需限制租户、行数、耗时与允许连接的对象，复杂查询在只读副本或专门服务中执行。查询结果仍需要权限检查，数据库错误也不能把整个 schema 暴露给用户。

下面是 SQLite 可运行的内存教学片段。它使用参数绑定查询物料，租户来自服务端受信任的请求上下文。示例把租户变量直接设为常量，只演示查询机制，真实身份应由认证系统取得。

```python runnable
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("""
CREATE TABLE materials (
  tenant_id TEXT NOT NULL,
  material_id TEXT NOT NULL,
  status TEXT NOT NULL,
  version INTEGER NOT NULL,
  PRIMARY KEY (tenant_id, material_id)
)
""")
db.execute("INSERT INTO materials VALUES (?, ?, ?, ?)",
           ("TEN-A", "MAT-204", "approved", 7))
trusted_tenant = "TEN-A"
row = db.execute(
    "SELECT status, version FROM materials "
    "WHERE tenant_id = ? AND material_id = ?",
    (trusted_tenant, "MAT-204"),
).fetchone()
assert row == ("approved", 7)
```

参数绑定用于区分 SQL 语句与值。拼接用户字符串会让引号和控制字符改变查询含义。表名与列名通常不能通过普通值参数绑定，应从服务端允许列表选择，不能直接采用模型输出。用户提供物料编号“MAT-204”，可以进入参数；用户提供一整段 SQL，是否允许执行应由任务和权限设计决定。

聚合也可能泄露信息。即使单条记录被隐藏，连续查询小范围统计可能推断出敏感数据。统计任务应设置适当的分组与小样本展示规则，并交由数据与安全团队审核。所谓只读，不等同于可以随意读。

## 6.5 事务保证什么，没保证什么

事务把多个数据库操作组织成一次提交或回滚。以申请和审计事件为例，申请写成功但事件未写入，会破坏追踪；二者放在同一事务中，可以使本地提交保持一致。不过事务的隔离级别决定并发读写能够出现哪些现象。业务检查先做、稍后再写，中间仍可能发生状态变化。

PostgreSQL 的 Read Committed 为每条语句取已提交快照，同一事务中的两次普通读取可以看到不同状态。Repeatable Read 采用更稳定的快照，但仍需关注序列化异常；Serializable 对结果提供更强的事务间保证，应用必须准备重试可能出现的序列化失败。数据库的具体实现影响细节，不能只依据隔离级别名称写跨数据库承诺。

SQLite 允许多个读取者，同一时刻只有一个写入事务。教学项目可用 SQLite 处理本地事务，并通过测试观察重复提交与状态冲突。不能据此直接推断其适合高吞吐的多服务写入场景。换成网络数据库时，应重新测锁等待、冲突、连接池与故障恢复。

以下是 PostgreSQL 的乐观并发写法。输入 expected_version 来自先前预览。匹配行数为零时，要区分无权限、状态不符或版本已变，界面只显示用户可以知道的信息。执行服务不能忽略零行更新继续产生后续事件。

```sql
UPDATE purchase_requests
SET state = 'submitted', version = version + 1
WHERE tenant_id = $1
  AND request_id = $2
  AND version = $3
  AND state = 'approved'
RETURNING request_id, version;
```

这一查询仅修改一个对象。若业务限制是“同一工厂的已提交总额不得超过额度”，涉及多行的约束需要额外设计。两个事务分别看见尚有额度，然后各提交一笔，可能一起超过限额。解决方案可以采用额度对象上的串行化更新、适当锁或可重试的 Serializable 事务，由业务模型和性能要求决定。给每个申请增加独立版本，无法自动解决跨对象约束。

事务范围要短，避免在持锁时等待模型输出或用户点击。先收集建议与批准，进入短事务后重新核对对象和授权，完成写入与事件记录，然后提交。外部支付、邮件和 ERP API 一般不在同一数据库事务中，它们的协调需要下一节机制。

## 6.6 Outbox 与 CDC 处理双写裂缝

一种危险流程是先更新数据库，再发消息。数据库提交后消息服务失败，消费者不知道变化；反过来先发消息再提交数据库，也可能发出最终未生效的状态。把本地业务变更和 outbox 事件写入同一个事务，可以使事件意图随业务状态一起提交。

```text
业务服务
  -> 同一事务写申请与 outbox 事件
  -> 提交
事件发布器或 CDC
  -> 读取已提交事件
  -> 发布到消费者
消费者
  -> 校验事件身份与对象版本
  -> 更新派生索引或启动下游处理
```

CDC 从数据库变更流观察已提交变化，outbox 用业务事件表达变化意图。二者可以配合，但目的不同。原始表变化可能包含内部字段与实现细节，消费者直接依赖这些细节会增加耦合。事件合同需要稳定事件类型、唯一事件标识、对象身份、版本和时间。Debezium 的 outbox router 提供具体实现与约定，团队使用其它实现时仍需设计相同的业务语义。

消息发布通常需要应对重复。发布器把事件发出后崩溃，没来得及更新发布状态，恢复后可能再次发出。消费者应按事件标识去重，并将去重记录与本地业务效果尽可能放在同一个事务中。不能只在内存集合中记已处理事件，重启后会失去记录。

顺序也需要明确。对象版本 9 的事件先到，版本 8 后到，派生索引不能把对象退回旧状态。可以按对象键分区并检查版本，遇到跳号时查询权威快照或进入补偿流程。分区内顺序不等于跨对象的全局业务顺序。申请与额度跨对象关联时，需要额外状态核对。

Outbox 保证的是本地意图一致性，加上消费者去重可以改善可恢复性。它不会自动提供跨系统原子提交，也不会让所有外部副作用只发生一次。若外部系统不支持幂等查询与提交，交付者应明确残余风险和人工核对流程，不能宣称实现了普遍的 exactly-once。

## 6.7 幂等键绑定操作内容

幂等的业务含义是重复同一个请求，不再产生第二份业务效果。写入请求需要一个稳定幂等键，作用域至少区分租户与动作。服务端保存首次请求摘要、处理状态和结果。同一个键再次出现时，内容相同则返回已保存结果；内容不同则拒绝，不能把 12 件和 120 件视作同一请求。

```text
idempotency scope = tenant + action + key
stored fields     = payload_hash + state + result_ref

same key, same hash, completed   -> return stored result
same key, different hash         -> reject conflict
same key, running                -> report current status
new key                         -> claim and execute
```

请求摘要采用明确的标准化规则。字段顺序不同不应导致语义相同请求的 hash 不同，12.0 与 12 是否相同则由字段类型和业务合同决定。JSON 排序序列化可以处理部分问题，但跨语言金额、时区、Unicode 与默认值仍需约定。摘要使用受信任的服务端实现，不能直接相信调用者提交的 hash。

并发重复提交必须由数据库唯一约束或具备相同保证的服务处理。两个请求同时查不到键，随后一起执行，普通“先查再写”会失效。先通过唯一键争取执行权，再在同一事务中完成本地效果，是常见实现路径。处于 running 状态的请求还需要超时与恢复策略，恢复者必须核对外部系统实际状态。

当写入调用超时，客户端只知道没有及时得到结果。此时结果可能未发生，也可能已经提交。重试前先查状态，或按同一个幂等键重试支持幂等的接口。给每次重试生成新键会把网络故障变成重复申请。错误表应区分明确失败、状态未知和已完成，不应把所有超时都标为失败并自动再次提交。

## 6.8 数据质量变成可处置的队列

建立数据质量规则时，先找会影响决策的缺陷。物料重复、基础单位缺失、版本交叉生效、批准记录无审核人，具有不同严重度与修复归属。把所有异常合成一个质量分数，业务方很难知道先处理哪项。质量报告应包含问题类型、对象编号、来源、首次发现时间、影响动作和责任人。

| 检查 | 教学规则 | 失败时的行为 |
| --- | --- | --- |
| 完整性 | 已批准物料必须有基础单位 | 暂停该物料申购 |
| 唯一性 | 租户与物料编号唯一 | 阻止歧义身份进入模型 |
| 关联性 | 申请引用存在的物料 | 返回可核查错误 |
| 时效性 | 库存必须在约定新鲜度内 | 展示截至时间或重新查询 |
| 语义一致 | 价格单位等于换算规则单位 | 转人工核对 |
| 权限 | 所有候选通过对象授权 | 不进入模型上下文 |

质量修复不能由生成模型静默覆盖权威数据。模型可以发现可疑字段，提出候选映射或解释，审核通过后由数据流程写回。原始值、提议值、审核者与规则版本应可追踪。一次名称相似匹配不等于两个物料实际可替代，规格与批准需要另外核查。

监控同步延迟时，记录源端事件时间、接收时间、索引可见时间与查询截至时间。这样能够判断慢在源、传输还是索引。如果只记录最后一次任务运行成功，任务可能成功处理了很旧的数据，绿色状态会误导操作者。

## 6.9 权限要穿过所有数据路径

服务端的用户身份经过认证后，转换为租户、角色和对象动作策略。模型参数可以包含申请的对象编号，但 tenant_id 和 actor_id 应由受信任上下文注入，不能让模型代填。读取、检索、缓存命中、引用展开与写入都应使用同一授权语义。只在首页拦一次登录，会留下大量下游缺口。

PostgreSQL 的行级安全策略可以作为多层防护的一部分。数据库表拥有者、超级用户和具备 BYPASSRLS 的角色具有特殊行为，部署时必须核实应用账号。开启 RLS 后却用绕过策略的账号访问，会使预期隔离失效。安全测试应实际用生产等价角色运行，不能只验证策略 SQL 存在。

连接池也有状态污染风险。若通过会话参数传递租户，连接交还后必须避免把上一个用户的上下文留给下一个用户。可采用事务局部上下文等受支持机制，并验证异常路径。日志需记录用于授权的主体与策略版本，敏感正文根据保留政策脱敏或限制保存。

## 6.10 本章工作坊与答案线索

工作坊一给两个供应商都提供的“耐油密封圈”建模。答案需要独立稳定编号、尺寸与材质字段、供应商别名映射，以及可替代关系的批准来源。仅以名称合并会丢失身份。再增加“价格按箱报价，采购按件申请”的条件，明确换算规则来源、包装数量与有效版本。

工作坊二在纸上模拟双写故障。数据库已经提交，消息发送失败；发布器已发送，状态记录失败；消费者已更新索引，确认消息丢失。答案分别使用 outbox 重发、稳定事件标识与持久化去重。最后说明哪个机制仍不能证明外部 ERP 只执行一次。

工作坊三模拟两个人同时提交同一幂等键。画出“先查再写”如何让两者都进入执行，再增加唯一约束和事务。重复键携带不同数量时，应明确拒绝内容冲突。服务超时以后，客户端使用原键查状态或重试，不以新键再发一笔。

工作坊四设计历史解释。某采购申请 9 月 30 日提交，10 月 1 日价目表变更。答案要区分当前报价与当时生效报价，保留申请所用版本，并提示账务校验范围。不能把最新表连接到所有历史申请后重新计算过去金额。

交付物包括对象关系图、字段字典、读写接口合同、并发与超时测试，以及数据质量处置表。实现选型可以变化，身份、单位、版本、授权和副作用这些语义必须稳定。
