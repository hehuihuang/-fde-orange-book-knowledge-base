# 第 16 章　用户采用与运营交接

系统上线之后，用户仍可能回到旧办法。要判断原因，需要观察实际工作中增加和减少了哪些动作。

## 使用入口影响采用成本

如果用户必须离开原系统、重新输入上下文，再把答案复制回去，节省的时间可能被这些动作抵消。尽量复用已有身份与工作入口，同时保持结果来源和当前状态可见。

信任来自持续可用的结果，也来自用户知道系统何时会失败。展示证据、标明信息缺口、允许修改与申诉，都有助于形成合理预期。用宣传替代质量，只会使下一次错误更难处理。

## 用真实任务判断采用

登录数能说明接触范围，不能证明工作改变。观察完成了多少任务、多少结果被修改、用户在哪里放弃，以及复核耗时是否下降。可以按部门、岗位和任务类型分开比较。

试点用户应包含愿意指出问题的人。他们可以帮助解释使用方法，但不应承担全部技术支持。身份异常、权限变化、模型故障和政策更新需要正式处理渠道。

## 把维护能力交给客户

| 交接对象 | 应能独立完成的工作 |
| --- | --- |
| 业务负责人 | 判断质量、调整允许任务、决定暂停 |
| 内容负责人 | 更新资料、处理冲突、撤回过期内容 |
| 技术负责人 | 查看运行状态、发布、恢复与排查 |
| 支持人员 | 收集问题、分类、升级并反馈结果 |

交接应通过一次实际演练检验。让维护人完成更新与回退，让支持人员处理一个模拟问题。说明文档能够被找到、读懂并用起来，才算真正交付。

## 采用从一次真实任务开始测量

本章回读 BBVA 的公开采用案例与 Google SRE 的值班和运维材料。Datawhale 的项目报告作为社区阅读入口，其效果数字属于发布方自述。下面的采用漏斗、采购培训和交接安排均为作者设计的教学方法，没有真实客户数据。

先说明有资格使用系统的人数，再看他们是否进入任务、完成任务及持续返回。仅记录已经登录的人，会漏掉身份障碍和不适用用户。仅记录最终完成的人，会漏掉中途放弃。漏斗需要以同一用户和时间口径计算，并将任务结果与用户人数分开。

教学假设有一百名获授权且任务适用的用户，八十名打开过入口，五十名发起任务，四十名完成任务，三十五名在后续窗口再次完成。首次完成占适用用户的百分之四十，发起后完成占百分之八十。两项说明不同问题。没有任务的用户未必抗拒系统，他可能尚未在观察窗口碰到该任务。

| 采用阶段 | 要观察的证据 | 常见障碍 |
| --- | --- | --- |
| 有资格使用 | 身份、岗位及适用任务 | 权限、组织与任务范围不一致 |
| 找到入口 | 入口访问及任务来源 | 链接难找或需切换工作环境 |
| 发起真实任务 | 任务标识与有效输入 | 需重复录入、缺少必要字段 |
| 完成并使用结果 | 合格终态及后续动作 | 证据难核对或结果不能回填 |
| 持续完成 | 后续窗口的有效任务 | 质量不稳、支持慢或数据过期 |

## 新系统减少和增加了哪些动作

采购教学流程中，搜索候选可能更快，但用户还需核对单位、检查价格并确认草稿。把这些操作加起来，才能比较新旧总时间。一个合格结果也可能被复制到原系统，复制本身就是额外工作，需要记录。

尽量将入口放在已有合法工作路径中，复用允许的身份与任务信息。集成并不意味着自动扩大数据访问。原系统知道一个员工是谁，本应用仍需获得明确的组织与动作权限。回填结果需要保存当前状态及版本，避免用户复制过期草稿。

当系统要求人工复核，界面指出要核对的字段和依据。单位关系、适用价格与缺失规格分别展示，比只给一个总置信度更有帮助。用户的接受不能替代服务端校验，培训也不能承担本应由系统阻止的越权。

## 培训围绕正常、异常和接管

培训目标是让用户在限定任务中正确使用与停止。作者设计的采购培训使用三条合成任务。字段完整的任务可以生成草稿，另一条缺少包装关系，最后一条模拟提交状态未知。用户应会完成正常草稿，向数据负责人反馈缺失关系，并在未知状态下找到原请求而不另建申请。

| 训练任务 | 用户应表现的动作 | 验证方式 |
| --- | --- | --- |
| 完整物料需求 | 核对规格、单位与价格再接受 | 用评分表观察操作 |
| 包装关系缺失 | 保留任务并寻求权威信息 | 不把猜测填成事实 |
| 权限不允许 | 使用正式申请渠道 | 不借他人身份或扩大权限 |
| 提交状态未知 | 保留请求并联系支持 | 支持能核对原申请 |

培训材料同时写明允许范围和已知限制。用户可以知道哪些任务不适用，不必通过一次失败才发现边界。课程完成不代表采用成立，后续仍观察任务完成、纠错和复核时间。

## 反馈有分类，也有正式去处

用户报告不准时，支持者先取得允许采集的任务标识和现象，再决定是事实、规则、表达、权限或依赖问题。事实错误进入评测与数据核对，规则争议交业务负责人，技术故障进入运行排查。严重错误先控制影响，不等待完整复盘。

试点代表用户可以帮助说明日常使用，但不应成为没有保障的唯一支持者。设定服务入口、响应安排、升级对象及状态回告。支持者不必重问已经记录的信息，任务上下文在授权范围内一次接续即可。

反馈处理结束时，记录采取的动作及验证结果。用户偏好不一定进入全局提示，某个错误也不应只通过临时改文本遮掩。把有效修正加入相应回归测试，下一次发布重新检查。

## 交接是能力转移的验收

交接清单覆盖业务规则、数据更新、技术运行和支持。每位接受者明确自己会做什么，哪些情况要升级，以及目前不能独立处理什么。有人收到一份文档，不能直接算作维护能力已经转移。

| 交接包 | 接受者 | 最小演练 |
| --- | --- | --- |
| 任务范围与质量规则 | 业务负责人 | 判断正常及严重错误样本 |
| 数据字典与更新办法 | 内容或数据负责人 | 更新一项材料并核对新旧引用 |
| 发布与恢复记录 | 技术负责人 | 暂停草稿、核对状态并安全恢复 |
| 问题分类与升级路径 | 支持人员 | 处理一条单位缺失与一条未知提交 |
| 费用及支持安排 | 项目负责人 | 核对月任务成本和维护容量 |

演练时由未参与实现的人操作，原开发者只观察。记录他在哪一步停住、找不到哪个入口、哪个词不清楚。改完后重演关键步骤，直到接受者能独立完成。第 14、15 章提供发布与故障工件，可以一起交接。

## 运营需要持续检查变化

数据来源更新、政策调整、权限撤销和用户岗位变化会改变系统条件。确定谁发起更新，谁审查，谁验证生效，谁观察异常。原维护人离开后，责任需显式转移，不能默认系统永远由最初开发者支持。

按任务和用户群比较采用，寻找具体限制。某部门不再返回可能因为任务减少，另一部门放弃可能因为资料过期。记录到足够解释变化就采取下一项实验，不要把所有低采用都归因培训不足。宣传活动带来的访问变化，也需与持续完成任务区分。

## 知识更新也做一次交接验证

作者设计的演练让数据负责人更新一个包装关系，保留材料来源、审批与生效时间。技术维护人确认新版本进入索引，用户再次处理相同教学输入并核对引用。旧草稿仍显示旧版本，不能悄悄用新单位改变已确认内容。

更新以后对受影响任务运行回归。若价格适用范围依赖包装数量，连价格检查也重测。交接者不应只知道上传文件，还需理解哪种变化会影响哪些规则。对于冲突和来源失效，文档明确升级对象。

演练结束时，业务、数据及技术接受者分别确认自己的工作完成。原作者记录无法独立操作的步骤并改说明。知识更新、运行恢复和用户支持各有具体证据，交接才覆盖持续运营。

## 本章练习

记录用户完成一项任务的全部操作，计算新系统额外增加了哪些步骤。再让一位未参与开发的人按运行手册处理一个小故障，补齐他无法继续的地方。

为本章漏斗写出两个不同分母的完成率，再给三项任务演练各列一个通过条件。参考答案区分适用用户中的完成与发起者中的完成。交接通过条件需要具体动作与可见状态，不能只写用户理解了。
