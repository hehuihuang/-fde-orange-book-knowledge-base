工程位于 [第 27 章伴随目录](../examples/material_assistant/README.md)。完整代码留在仓库中，正文只展示理解重要机制所需的片段。示例没有调用大模型，没有访问 ERP，没有发送采购请求。`run_demo()` 按预设顺序编排服务，检索采用确定性规则。后文讨论模型接入时，会把已经运行的部分和待验证的扩展分开。

## 27.1 把项目问题收敛到可检查的对象

本书设定一个教学任务，维护人员需要查找已有物料，然后为明确选中的物料提出采购申请。我们不假设名称相近的两个物料能够替代，不把现有库存数字直接解释成可以领用的数量。系统需要帮助人找到候选，并在确认采购前保存选择依据。

先写下三条合成请求，暂时不用设计界面。

| 请求 | 需要得到的结果 | 不允许发生的动作 |
| --- | --- | --- |
| 查一下 6305 轴承 | 返回不同材料与密封方式的候选，要求明确选择 | 按排序第一名自动生成订单 |
| 给碳钢型号买一盒 | 确认具体物料，按该物料包装换算，生成草稿 | 把所有轴承的一盒都解释成相同数量 |
| 审批已经通过，确认一下 | 核对摘要、权限、来源版本、额度和幂等键后写入 | 用一段“已审批”的自然语言代替授权记录 |

这些请求产生了三种不同对象。候选列表只代表搜索结果。草稿代表用户拟提交的采购内容，仍可修改。订单代表服务在全部检查通过后形成的本地记录。把三种对象分开，后续的按钮、测试和日志才有明确对象。

对象的区分还会改变用户对助手的预期。检索没有找到候选时，助手可以解释查询条件并让人补充型号。草稿无法通过审批时，助手应报告阻断原因。确认请求超时后，使用者需要知道同一个请求究竟已写入还是尚未写入，不能重新走一次猜测式采购。

FDE 在这个阶段应当留下动作清单。每个动作都写明输入、输出、修改的对象和需要的权限。遇到“帮我处理一下”这种含混要求，就把它拆成查询、准备、审批或确认。业务人员批准的范围会直接变成服务边界，不能只停留在访谈笔记里。

## 27.2 先把第一版范围写成验收合同

本章第一版只支持单物料、整数数量和单一币种。维护品类用户可以读维护物料。具有申请权限的人可以为自己创建草稿。审批者具有维护品类权限时，可以批准他人草稿。最后由原申请者确认已经批准的内容。

采购确认不会扣减库存。买入采购和领料出库是不同业务动作。演示显示的库存只帮助人观察已有记录，采购数量可以超过当前库存。本地“预算”也只是一个剩余额度整数，它没有包含真实企业的预算中心、会计科目、占用、释放或结算制度。

| 验收项 | 可执行的判定 |
| --- | --- |
| 身份边界 | 当前租户的请求不能返回另一租户的物料、草稿和审计事件 |
| 型号歧义 | 同一规范化型号对应多种物料时，输出澄清标志 |
| 单位换算 | 按当前物料的包装因子计算基础数量，不支持的单位必须拒绝 |
| 金额来源 | 单价来自服务端物料记录，数量与单价乘积由服务计算 |
| 人工审批 | 审批者与申请者分离，审批绑定完整有效负载摘要 |
| 延迟风险 | 超时、内容变更、权限变更、来源变更均可阻断未执行写入 |
| 预算一致性 | 额度不足或中途故障时，没有半张订单和部分额度扣减 |
| 重复请求 | 相同请求与同一幂等键返回原订单，额度只扣减一次 |

真实试点应让业务负责人确认这张表，尤其是不能自动处理的事项。示例中的规格差异需要人确认。真实维护场景还可能要求工程师签字、设备适配检查或危险品规则。本章没有替读者填入这些规则，因为它们取决于实际组织和产品。

项目也应明确自己的停止条件。无法确认物料就停在候选列表。单位缺少可靠换算就停在草稿之前。审批期间价格变化就重新展示预览，让人再次确认。停止是可以验收的正常结果，不应在产品统计中统一算成系统故障。

## 27.3 运行条件与第一次观察

伴随工程使用 Python 标准库，要求 Python 3.10 或更新版本。SQLite 由 Python 运行环境提供。程序没有服务器进程，也没有数据库文件。演示和测试都在内存中建立独立数据库，结束时只关闭连接，不删除磁盘文件。

在仓库根目录运行下面两条命令。

```bash
python3 examples/material_assistant/material_assistant.py
python3 -m unittest discover -s examples/material_assistant -v
```

第一条命令输出完整 JSON。请先观察 `search.needs_clarification`，它应为 `true`。再观察 `first_order.total_cents`，它应为 `25000`。最后检查 `retry.order_id` 与第一次订单标识相同，剩余额度为 `75000`。

演示使用一盒碳钢轴承，一盒含十个，每个 2500 分，总额为 25000 分，也就是 250 元。初始额度为 100000 分，确认之后余额为 75000 分。这几个数字来自合成数据和明确计算，没有隐藏模型判断。

订单标识、审批标识和生成时间会随运行变化。演示用随机标识避免把固定常量误当成生产标识生成策略。测试注入固定时钟，检查到期边界。读者比较两次输出时，应比较对象关系、金额和状态，不应要求 JSON 每个字符都相同。

第二条命令会列出 31 项测试及执行结果。测试文件可以直接阅读，它们包含跨租户、品类隔离、单位不兼容、审批失效、来源变更、幂等重试和故障回滚。测试数量本身不构成质量等级，后面会逐组解释它们究竟检查了什么。

## 27.4 数据来源与权威字段

一个物料助手至少会接触名称、型号、规格、库存和采购价格。它们可能来自不同系统，更新频率也不同。把所有字段塞进同一个向量条目，会模糊字段由谁维护以及何时发生变更。本章采用结构化表，让每个关键字段有确定的读取位置。

| 字段组 | 本工程的权威位置 | 真实接入时要补的合同 |
| --- | --- | --- |
| 物料标识与规格 | `materials` | 主数据负责人、停用策略、型号规范 |
| 单位与包装 | `materials.unit_factors` | 基础单位、包装批次、有效期和确认人 |
| 单价与交期 | 合成物料表 | 报价币种、有效期、税费、供应商确认 |
| 供应商准入 | `suppliers` | 准入系统、撤销传播和例外审批 |
| 用户身份与范围 | `users` | 认证来源、角色发放、品类权限和撤销时间 |
| 剩余额度 | `tenants` | 额度归属、占用机制、财务对账 |

同一个字段也会具有不同的业务含义。库存表中的数量可能包含已预留、冻结或待检验库存。采购报价可能包含或不包含税。交期可能从下单、付款或排产开始计时。在真实项目里，接口字段名称并不足以完成数据合同，必须写清这些含义。

本章的库存只是合成整数，交期只是记录天数。回答中明确保留“交期不是到货承诺”和“未接入实时 ERP”。这样，读者可以检查程序有没有越过自己的数据范围。真实上线应继续附带快照时间、同步延迟和数据负责人，而不能删掉这些限制后称其为实时决策系统。

物料和供应商都带有 `revision`。草稿保存这两个版本，确认时再次核对。版本是改变后的证据线索，真正的安全检查还会比较当前有效负载。这层比较能发现字段被改动却遗漏增加版本的情况。示例专门保留了这种输入的回归测试。

## 27.5 合成数据故意保留难点

教学数据有两个租户 `atlas` 和 `cedar`。每个租户可以有同名用户，这提醒我们用户标识通常需要租户边界。租户 `cedar` 中的隐藏候选与当前用户查询相同型号，但不应进入 `atlas` 的排序过程。

| 物料 | 型号与区别 | 基础单位及包装 | 合成基础单价 |
| --- | --- | --- | --- |
| `BR-6305-CS` | 6305，碳钢，开放式 | 个，一盒十个 | 2500 分 |
| `BR-6305-SS` | 6305，不锈钢，双侧密封 | 个，一盒五个 | 4800 分 |
| `BL-M8-20` | M8x20，镀锌，强度 8.8 级 | 个，一盒二十个 | 120 分 |
| `CB-2-5` | 2.5MM2，铜芯，蓝色 | 米，一卷一百米 | 350 分 |
| `GL-SAFE` | G100，防护手套，尺寸 L | 副，一包十二副 | 900 分 |
| `BR-6204` | 6204，供应商尚未准入 | 个 | 2200 分 |
| `BR-SECRET` | 另一租户的 6305 候选 | 个 | 100 分 |

第一组难点来自同型号。数字 `6305` 没有说明材料和密封方式，不能完成物料选择。第二组来自单位。同样写“一盒”，不同物料具有不同包装数量。第三组来自权限，维护品类用户不能搜索安全品类手套。第四组来自供应商准入，检索可以返回有关记录，草稿写入却必须检查供应商是否允许采购。

别名也故意不对称。碳钢物料具有“轴承6305”这个别名，因此在纯排序中得到额外分数。不锈钢物料没有同样的别名。这个设计在首次测试中暴露了排序与决策混用的错误，后文会展示当时的失败与修复。

数据没有制造更多行来模拟真实规模。七条记录足以让本章的机制发生冲突。真实评测需要增加设备适配、状态、报价批次、停用物料和跨区域库存等样本，不能把教学记录复制几万次后宣称已经完成企业数据验证。

## 27.6 用表约束保护对象关系

工程在 `SCHEMA` 中定义九张表。租户、用户、供应商和物料提供业务输入。草稿与审批保存人工选择和授权。订单与幂等回执保存写入结果。审计表记录成功变更。

物料使用租户与物料标识的联合主键。供应商外键同样包含租户，因此本租户物料不能通过正常插入引用另一租户供应商。下面是实际结构中的相关片段，完整字段可以在伴随代码中查阅。

```sql
CREATE TABLE suppliers (
  tenant_id TEXT NOT NULL,
  supplier_id TEXT NOT NULL,
  name TEXT NOT NULL,
  approved INTEGER NOT NULL CHECK(approved IN (0,1)),
  revision INTEGER NOT NULL CHECK(revision > 0),
  PRIMARY KEY(tenant_id, supplier_id),
  FOREIGN KEY(tenant_id) REFERENCES tenants(tenant_id)
);
```

订单还具有 `UNIQUE(tenant_id, draft_id)`。即使业务逻辑出现遗漏，数据库也会拒绝同一租户同一草稿写入两张订单。这个约束保护对象关系，不能代替幂等回执。重复确认需要返回原订单并判断参数是否一致，数据库的唯一错误无法独自完成这件事。

额度、单价和数量都有约束。预算不能为负，单价必须为正，物料版本必须大于零。SQLite 的类型系统具有自己的规则，工程不依赖表声明把一切不合格输入都自动变成正确类型。服务仍对数量执行严格的 Python 类型检查，拒绝布尔值、浮点数和数字字符串。

Python 连接会显式执行 `PRAGMA foreign_keys = ON`。外键是否生效值得放进接入测试，不能只看到 DDL 中出现 `FOREIGN KEY` 就认为关系已经得到保护。数据库迁移到其他引擎之后，也应验证这些约束的实际行为。

表结构只保护本数据库中的记录。它不能确保远端供应商已经准入，不能证明所有身份变更及时同步。数据接入契约、缓存延迟和撤销传播仍属于服务之外必须完成的交付任务。

## 27.7 身份上下文必须来自可信入口

示例没有实现登录。接口参数中的 `tenant` 和 `user` 代表经过认证层核验后注入的身份。演示把它们写成字符串，便于直接检查服务行为。真实 API 不能让浏览器表单或模型输出自由填写这两个字段。

| 输入 | 谁可以提供 | 服务如何使用 |
| --- | --- | --- |
| 租户和用户 | 可信认证入口 | 查询服务端身份、角色与品类范围 |
| 查询文本 | 使用者或模型提案 | 作为待匹配的数据 |
| 物料标识与数量 | 使用者或模型提案 | 校验当前范围和数据记录 |
| 单价与供应商状态 | 权威业务数据 | 服务端读取，拒绝客户端自行指定 |
| 审批身份与状态 | 授权服务 | 从角色和授权记录复核 |

假如一个真实接口直接接受 `tenant="cedar"`，却仍使用 `atlas` 用户的登录会话，它会在服务之前打破租户边界。数据库查询都带租户条件也救不了这种错误。部署测试需要证明入口把租户固定在经过验证的会话中，同时验证用户不能用自报参数覆盖它。

角色和范围也要一起检查。`approver` 角色不意味着可以审批所有品类。维护品类审批者在本工程中只能查看和批准维护品类记录。`active` 标记可以禁用身份，`perm_version` 用来发现权限在批准后发生变化。

已不存在与不可访问的物料都返回 `MATERIAL_UNAVAILABLE`。这种统一错误减少对象存在性的泄露，但不能宣称完全消除了侧信道。真正的 API 还需要检查响应时间、日志、计数接口和错误消息。示例没有测量这些风险，读者应把它们留在生产安全验收中。

## 27.8 先过滤，再做检索与排序

检索入口先查询当前身份，再从服务端记录中取得品类范围。SQL 查询同时绑定租户与允许品类。模型不会拿到整个公司物料表再自行筛选，排序函数也看不到其他租户记录。

```python
categories = json.loads(actor["categories"])
marks = ",".join("?" for _ in categories)
rows = self.db.execute(
    f"SELECT * FROM materials WHERE tenant_id=? "
    f"AND category IN ({marks})",
    (tenant, *categories)
).fetchall()
```

这里动态生成的部分只有占位符数量，品类值仍通过参数绑定。查询文本不会进入 SQL 语句拼接。测试中的恶意文本包含引号、`OR 1=1` 和“取消审批”，程序把它当作普通查询数据，不会执行 SQL，也不会改变采购规则。

示例先用 NFKC 规范化文本，再转大写并去掉空白。因此全角 `６３０５` 和半角 `6305` 可以匹配到同一型号。规范化规则也有适用边界。真实物料编码中，空格、大小写或符号有时参与含义，不能直接照搬规则处理所有行业标识。

评分函数把型号精确命中赋予 100 分，型号子串命中赋予 40 分。名称或规格包含查询词加 20 分，别名包含查询词加 30 分。最终按分数递减排序，同分按物料标识排序。所有分数都是本章人为设定的教学参数，不是模型置信度，也没有通过真实企业样本拟合。

评分的作用是安排人查看候选的顺序。程序还需要一套独立的决策规则，决定是否必须补充信息。假如把排序分直接解释为“可以下单的把握”，规格缺失会变成自动执行错误。

## 27.9 第一个真实失败出现在型号澄清

首次运行测试时，两项用例失败。输入 `6305`，碳钢候选因为别名获得 130 分，不锈钢候选得到 100 分。旧的澄清规则只看第一名与第二名是否相差不到 15 分。这组数据相差 30 分，规则错误地输出了无需澄清。

完整演示用例也随之失败，因为它预期查询必须先确认材料与密封方式。这个失败发生在我们自己的合成数据和程序中，不能推演成 Datawhale 案例曾发生同样错误。

修复时保留原评分，不用调整别名把两者强行变成同分。新增规则直接数规范化型号完全相同的候选数量。同一型号有多个候选，就独立触发澄清。

```python
exact_model_count = sum(
    normalize(item["model"]) == needle
    for item in candidates
)
unclear = exact_model_count > 1 or (
    len(candidates) > 1
    and candidates[0]["score"] - candidates[1]["score"] < 15
)
```

这样修改之后，用户仍先看到更符合别名的候选，但系统不会把缺失的材料条件补成碳钢。测试保留全角型号输入、两种材料和别名差异，因此以后更换排序参数时，这个安全要求仍会被检查。

读者可以从这个失败建立评测习惯。先写清必须澄清的业务条件，再检查检索结果是否满足条件。排行榜首、较高相似度或更漂亮的回答，都不能替缺失的规格作决定。模型参与以后，这条规则也应当由服务端继续执行。

## 27.10 回答要把证据落实到字段

`answer()` 接受已经明确选中的物料标识。它重新检查身份和品类范围，从这条结构化记录生成回答，同时给每个关键字段附上记录依据。这里使用 `material://租户/物料@版本` 作为教学引用格式，它是本程序的对象标识，不是可以访问真实 ERP 的网络地址。

```python
answer = service.answer("atlas", "lin", "BR-6305-CS")
assert answer["evidence"]["stock"]["value"] == 4
assert answer["evidence"]["stock"]["source"] == (
    "material://atlas/BR-6305-CS@1"
)
```

这份回答能说明记录里的型号、规格、库存、基础单位和交期。它不能说明这只轴承适合哪一台设备，也不能保证现有库存尚未被占用。返回对象因此包含三项限制，交期没有承诺效力，替代适配性未经验证，数据没有接入实时 ERP。

字段级证据有利于纠错。若用户质疑库存，可以查到库存字段来自哪条记录，而不必在长文中猜测出处。若价格来自独立报价系统，真实工程应给价格另一份证据，包含报价标识和有效期。所有字段引用同一个文档名称，通常无法满足这种追查。

如果接入生成模型，答案可以更自然，但字段与依据的关系应继续由结构化对象保存。模型增加“这款适合高速设备”之类句子时，服务不能用现有型号引用替新结论背书。适配结论需要实际技术文件和获授权人员确认，缺少依据就不应出现在自动回答中。

## 27.11 单位是业务规则，不能靠语义相似

单位问题会在金额计算之前出现。碳钢轴承的一盒含十个，不锈钢轴承的一盒含五个。一盒的意思必须绑定物料。电线的“卷”也只能在对应物料具有明确长度时换算成米。

本工程用 `unit_factors` 保存每种物料允许的整数换算。用户给出整数采购数量，服务把它乘以该物料当前包装因子，得到基础数量，再乘以基础单价。

```python
base_quantity = quantity * factors[unit]
total_cents = base_quantity * material["price_cents"]
```

电线按米报价，用户请求按千克采购时，程序返回 `UNIT_UNSUPPORTED`。它没有密度、长度与重量的关系，也没有实际包装称量记录。让模型从常识里估一个换算值，会把数据缺口藏进看似精确的采购金额。

检索候选包含 `unit_compatible`。这个字段让界面可以在用户选择前展示单位是否可用。但最终草稿服务仍会再次检查单位，不能依赖界面按钮已经禁用。用户可能从其他入口调用工具，也可能在候选显示后遇到包装信息变更。

数量使用严格整数检查，`True` 不被接受为一件。Python 中布尔值与整数存在类型关系，因此只用一般整数判断容易遗漏这个输入。浮点数、数字字符串、零、负数和大于示例上限的数量也会被拒绝。

金额采用分为单位的整数，避免本例中的小数舍入问题。真实业务有更细报价、小数重量和税费时，需要明确精度、舍入时点与币种。不能简单地把这里的整数策略扩展到所有账务场景。工程给出的每一笔金额都应能够按有效数据重新算出。

## 27.12 草稿保存完整的拟执行内容

创建草稿时，申请者只提供物料标识、数量和单位。单价、供应商、币种、规格和版本都由服务端补齐。这样，客户端或模型无法通过提交低价参数来绕过采购金额检查。

草稿有效负载包含租户、申请者、物料标识、名称、型号、规格、品类、来源版本、供应商版本、原数量、原单位、基础数量、换算因子、基础单价、币种和总额。它保存的是将要被批准和确认的整件事。

以一盒碳钢轴承为例，相关字段如下。正文省略了不影响此处解释的字段，实际预览对象会返回全部有效负载。

```json
{
  "material_id": "BR-6305-CS",
  "material_revision": 1,
  "supplier_id": "SUP-A",
  "supplier_revision": 1,
  "quantity": 1,
  "unit": "盒",
  "base_quantity": 10,
  "base_unit": "个",
  "unit_factor": 10,
  "price_cents": 2500,
  "currency": "CNY",
  "total_cents": 25000
}
```

草稿可以修改数量和单位，但只能由原申请者修改。修改后重新生成有效负载与摘要，原审批不能再直接使用。已经形成订单的草稿不能改回去，本例返回 `DRAFT_CONSUMED`。真实业务需要变更或撤单时，应设计独立动作及其权限，不能悄悄改写历史订单。

创建草稿没有占用额度。额度在本地确认事务中扣减。因此，即使审批界面看到足够余额，也不保证稍后确认时还有余额。程序会在最终写入时检查，这个时点需要在业务合同中说明。

## 27.13 让预览、审批和执行引用同一份内容

用户看到的预览必须能够对应服务最终执行的负载。只把“碳钢轴承一盒”存进确认按钮，会丢失包装、价格、供应商和规格。服务在等待人工审批的时间里，数据可能变化。

本工程对完整 JSON 使用确定编码。字段按键排序，中文保持 UTF-8 表达，去掉非必要空白，然后计算 SHA-256。下面是实际函数。

```python
def canonical(value):
    return json.dumps(
        value,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":")
    )

def digest(value):
    return hashlib.sha256(
        canonical(value).encode("utf-8")
    ).hexdigest()
```

摘要的任务是发现内容变化。相同数据即使在 Python 字典中用不同顺序构造，也会得到相同摘要。草稿增加数量、改变单位或换了当前数据后，会得到不同摘要。

摘要没有证明审批者是谁。它也没有给数据库提供防篡改能力。具有足够数据库权限的人可以同时改正文、摘要和授权记录。真实系统应把身份核验、授权记录保护、数据库权限和外部审计分别完成，不能把一个哈希函数当作完整安全方案。

前端仍需要展示完整负载中的关键内容。使用者不能核对一串摘要所代表的采购细节。摘要负责把看过的内容与随后执行的内容联系起来，人的判断依靠可读预览，二者共同形成确认过程。

## 27.14 授权记录需要人、范围与有效期

`approve()` 要求当前用户具有审批角色，且能够访问所申请物料的品类。审批者不能批准自己的草稿。被批准的申请者也必须仍处于有效状态并具有申请和物料访问权限。

审批写入独立记录，包含草稿标识、审批者、双方权限版本、负载摘要、失效时间和是否已使用。它把“谁批准了哪份内容”保存成可查询对象。

| 审批字段 | 阻止的问题 |
| --- | --- |
| `draft_id` | 把甲草稿审批拿去确认乙草稿 |
| `approver_id` | 无法追查批准身份 |
| `payload_hash` | 批准之后更换数量、单价或规格 |
| 两个权限版本 | 已知权限变动后继续使用旧授权 |
| `expires_at` | 长时间闲置的批准直接执行 |
| `used` | 未经幂等判断再次消耗同一授权 |

默认有效期为 300 秒，服务允许的教学范围为 1 到 3600 秒。这个时长仅供机制演示，没有代表真实企业审批政策。真实项目需要按风险、数据更新和工作流程确定期限，同时考虑审批撤销与委托。

到期判断使用 `当前时间 >= 失效时间`。测试把时钟移动到刚好等于失效时间，要求拒绝写入。边界条件要写成可执行检查，不能只在文档里说“超过五分钟失效”，让不同实现产生一分钟或一秒的歧义。

审批时没有写入订单。使用者随后确认仍要复核数据、权限和预算。已经执行的成功请求再次重试会读到历史回执，即使原批准后来到期，也不需要重新采购。这两种路径在服务中分开处理。

## 27.15 用状态解释允许的下一步

草稿在本章只有两个持久状态，`draft` 与 `ordered`。审批是独立表，不把“已审批”永久存成草稿状态，因为不同内容、不同时间可能产生多份审批。最终确认必须找到匹配当前摘要且有效的审批。

```text
明确选择物料
      |
      v
    draft ----修改数量或单位----> draft
      |
      | 匹配当前摘要的有效审批
      | 当前权限、来源与额度均通过
      v
   ordered ----相同幂等请求----> 原订单回执
      |
      | 新键再次确认同一草稿
      v
  DRAFT_CONSUMED
```

状态图没有说明外部订单已送达，也没有说明供应商接受了采购。教学订单只是本数据库中的记录。接入 ERP 之后，需要增加提交中、外部已接受、外部拒绝和需要对账等状态。状态扩展应来自真实系统能够观察的事件，不能靠模型对响应文字的乐观解释。

一个已执行请求与一个待执行请求也不能仅用当前草稿状态区别。幂等回执记录请求摘要和订单标识，才能识别重复请求是否确实指向同一件事。它同时保护“返回历史结果”和“拒绝第二次写入”两种不同需求。

状态转换应该由业务服务执行。让模型返回 `state="ordered"` 只能视为未经核验的文本，不能据此修改数据库。真实工具接口也不应开放任意状态编辑权限，避免模型用便捷更新绕过审批路径。

## 27.16 最终确认逐项检查什么

确认服务接收草稿标识、审批标识、预览摘要和幂等键，同时从可信入口取得申请者身份。整个检查与写入处于显式事务中。服务先检查是否存在相同请求的成功回执，存在时返回原结果；不存在时才准备新的写入。

新的写入需要通过以下检查。

1. 申请者当前有效，具有申请权限。
2. 草稿属于本租户，并由当前申请者创建。
3. 草稿仍未生成订单。
4. 提交摘要、草稿保存摘要与重新计算的摘要一致。
5. 申请者当前仍能访问该物料。
6. 审批属于本租户，指向该草稿，尚未使用。
7. 审批摘要匹配，时间仍有效。
8. 审批者当前有效，角色与品类范围仍允许审批。
9. 双方权限版本与授权时一致。
10. 供应商仍处于准入状态。
11. 物料和供应商版本没有变化，当前有效负载也没有变化。
12. 剩余额度能够覆盖服务重新核对后的金额。

这些条件的顺序也影响错误表现。使用旧摘要确认已经修改的草稿，会先得到 `PREVIEW_CHANGED`。如果改用新摘要，却仍提交旧批准，会得到 `APPROVAL_CHANGED`。两种输入都不能生成订单，但它们对应的恢复动作不同。

权限撤销会被当前身份检查阻断。权限版本改变但角色和范围仍看似可用时，会得到 `PERMISSION_CHANGED`，要求重新审批。示例选择比较保守的策略，它没有自动判断这次权限变化是否与该物料有关。真实工程可以按授权范围细分版本，不过需要证明不会漏掉影响当前动作的变更。

价格字段改变却没有增加版本也会被检测出来。服务再次构造有效负载并与草稿比较。这里的目的只是保护即将执行的采购内容，它没有追踪所有主数据字段，也没有证明企业主数据治理已经完整。

## 27.17 幂等保护的是同一请求的重试

网络超时可能发生在服务器已经提交之后。使用者看不到成功结果，再按一次按钮很正常。若第二次请求重新写订单，错误会来自程序对不确定状态的处理。

本工程将幂等键限定在租户内，保存请求摘要与订单标识。请求摘要包含申请者、草稿标识和预览摘要。相同键指向不同请求时返回 `IDEMPOTENCY_CONFLICT`，不能把旧订单当作新草稿的成功结果。

```python
request_hash = digest({
    "requester": requester,
    "draft_id": draft_id,
    "payload_hash": expected_hash
})
```

批准标识没有纳入请求摘要。这里定义的是“这个申请者确认这份草稿内容”的业务操作，不依赖重试时提交的授权标识是否仍然相同。首次成功写入后，第二次请求读取的是已经发生的结果，不会依据第二份批准再写一次。

历史结果读取仍会检查申请者当前身份和物料范围。申请者失去品类访问后，重复请求不会把订单中的规格重新返回给他。这个机制保护当前读取权限，已经执行的订单与预算扣减则仍然保留，不会因为读取失败自动撤销。

相同草稿换一个新幂等键再次确认也会被拒绝。草稿状态已经是 `ordered`，并且数据库还有唯一约束。幂等键解决请求重试，草稿唯一性解决同一业务对象重复执行，两者应同时存在。

演示没有测量多个进程同时确认的情况，也没有测试持久化重启。内存数据库在进程退出后消失，不能支持真实网络重试跨重启查回执。生产实现需要持久存储、键保留期、历史查询权限和冲突告警，不能把本地测试记录写成分布式“恰好一次”保证。

## 27.18 预算扣减与订单写入必须一起提交

确认服务显式执行 `BEGIN IMMEDIATE`。额度扣减采用带条件的更新，只有当前余额足够才会修改一行。更新成功之后，程序写订单，改变草稿状态，标记授权使用，写幂等回执和成功审计事件，最后提交事务。

```sql
UPDATE tenants
SET budget_cents = budget_cents - ?
WHERE tenant_id = ?
  AND budget_cents >= ?;
```

如果更新行数不是一，服务返回 `BUDGET_EXCEEDED`。不能先读余额，在事务之外算出足够，再执行无条件扣减。读取与写入之间可能出现其他采购，最终条件必须由写入操作检查。

SQLite 官方文档说明其事务和写入限制。这里选择立即开始写事务，便于在教学服务中把检查与变更放在明确的一段工作中。示例没有测量锁等待、并发吞吐和多进程故障，因此不会从这一行 SQL 推导生产容量。

| 同一次成功确认的变更 | 要保持的关系 |
| --- | --- |
| 额度减少 | 等于订单总额 |
| 订单建立 | 指向原草稿与申请者 |
| 草稿变为已执行 | 阻止使用新键重复采购 |
| 授权标记已使用 | 与实际执行一致 |
| 回执建立 | 指向刚形成的订单 |
| 成功事件记录 | 指向相同订单、审批和摘要 |

任一变更失败，全部回滚。这样不会出现额度已扣却没有订单，或者订单存在但重试查不到回执的半成品状态。真实财务系统可能需要预算占用、实际扣款和释放分别建模，届时每一步也要明确自己的原子关系。

## 27.19 用故障注入验证回滚

本工程有一个只供本地测试的私有故障钩子。测试把故障放在额度更新之后、订单写入之前，抛出异常。事务管理器收到异常会执行回滚。

```python
def fault():
    raise RuntimeError("injected after budget mutation")

service._fault_hook = fault
```

测试接着检查额度仍为初始值，订单数和回执数都为零，成功审计事件数量没有增加，草稿仍处于 `draft`。移除故障钩子后，用相同参数再次确认应正常成功。这组检查验证了失败没有把请求永久卡在已执行状态。

这里没有用“报错了”作为验收结果。错误只是触发条件，我们关心的是数据库留下了什么。很多看似正确的事务代码只检查接口抛出了异常，遗漏预算、授权或回执已经发生部分变更。故障用例应逐个检查与该事务有关的对象。

故障钩子不能开放成生产请求字段。真实 API 如果允许用户选择跳过或注入某个写入步骤，会破坏服务语义。测试设施和对外合同需要清楚隔离。

这一组单元测试只覆盖程序内异常回滚。它没有杀死进程，没有模拟磁盘损坏，没有测试提交过程中数据库文件恢复，也没有覆盖外部 ERP 接受订单后本地断线的情况。后面接入外部系统时，还需要另外的故障演练。

## 27.20 成功审计与失败安全日志要分开

完整演示产生三条成功事件，创建草稿、授予审批和形成订单。订单事件保存草稿标识、审批标识、负载摘要和总额。相同请求重试只返回历史回执，不再记录第二条“订单创建”事件。

| 事件 | 主对象 | 核对内容 |
| --- | --- | --- |
| `draft_created` | 草稿 | 有效负载摘要 |
| `approval_granted` | 审批 | 草稿、摘要和失效时间 |
| `order_created` | 订单 | 草稿、审批、摘要和总额 |

成功审计和业务写入处于同一个事务，因此能够保持一致。失败请求却会把这个事务回滚。若试图把“授权被拒绝”也写在同一事务里，该日志会一起消失。真实系统需要在独立的安全日志通道保留失败尝试，并避免日志故障导致业务许可变宽。

本例尚未实现失败日志接收器，审计表也没有外部签名、不可修改存储、保留期或访问审计。正文称它为成功事件审计，不称其为完整安全审计平台。部署清单会把这些缺项写成上线前任务。

日志内容还要限制敏感信息。查询文本可能包含客户名称或机密规格，全文保存会扩大数据暴露范围。真实工程应确认日志字段、脱敏规则和查询权限。为了教学可读性，示例保存有限的对象标识与摘要，未声称这些字段在所有企业中都可以公开。

审计读取需要当前审批角色并带租户条件。它不能支持全组织审计员、跨租户平台运维或外部合规检查，真实系统若有这些角色，应另行设计授权路径，避免为方便排障直接开放任意租户参数。

## 27.21 把 31 项测试按风险阅读

运行结果中的测试名称不是随意凑出的编号。每组检查一个明确机制，部分用例互相连接。首次的两个失败提醒我们，只有把预期写进测试，才能知道排序改进是否突破了业务限制。

| 测试组 | 数量 | 具体内容 |
| --- | --- | --- |
| 检索与证据 | 4 | 同型号澄清、记录版本依据、单位兼容展示、恶意文本仅作数据 |
| 身份与范围 | 4 | 跨租户候选隔离、未知租户身份拒绝、品类过滤、只读用户不能建草稿 |
| 数量与数据准入 | 3 | 物料专属包装、数量类型与边界、未准入供应商阻断 |
| 审批绑定与时点 | 8 | 自批拒绝、摘要核对、到期边界、草稿改变、新预览旧审批、双方权限版本、审批者禁用 |
| 权威数据复核 | 3 | 价格版本变化、漏增版本仍识别、供应商撤销 |
| 幂等与再次读取 | 4 | 同键重试、同键不同请求、同草稿新键、失去品类范围后的历史读取 |
| 事务与完整路径 | 5 | 额度不足、故障回滚、跨租户确认与审计、摘要篡改、完整离线演示 |

数量是测试方法数量，不是所有输入数量。数量边界用例还循环检查了布尔、浮点、字符串、零、负数和过大数量。阅读测试时应继续看断言，确认拒绝之后有没有检查订单和余额，而不是只数方法名。

这组测试没有真实用户样本，也没有语言模型输出。它能为服务端业务规则建立回归检查，不能代替用户接受度、真实检索效果或模型可靠性评测。特别是同型号规则在这里具有明确业务前提，迁移到其他数据时需要重新确认型号是否足以定义候选集合。

测试覆盖率工具可以帮助发现未执行分支，但覆盖率高也不证明场景充分。所有测试使用同一批合成记录，可能共同遗漏真实数据中的其他单位或状态。FDE 应把现有断言映射到风险清单，再让业务人员指出缺项。

## 27.22 构造读者自己的离线评测集

若准备扩展本项目，先增加评测数据，再接模型。数据可以从已经授权使用的真实历史请求整理，也可以继续合成，但必须明确来源。真实请求需要脱敏和保留使用权限，合成输入不能被描述成客户实测。

建议每条样本保存问题、身份范围、允许候选、必须澄清的字段、允许动作、预期阻断码和依据。这样，模型回答更流畅时，我们仍能检查它是否选择了正确对象和动作。

```json
{
  "query": "采购6305轴承一盒",
  "identity_scope": "atlas-maintenance-requester",
  "allowed_candidates": ["BR-6305-CS", "BR-6305-SS"],
  "must_clarify": ["material_and_seal"],
  "allowed_action": "search_only",
  "forbidden_action": "confirm_order",
  "origin": "synthetic_teaching"
}
```

这一条样本不能只检查最终回答是否包含“请确认”。若模型一边解释歧义，一边调用工具创建了未经明确选择的草稿，仍然违背范围。评测需要同时检查文字、工具参数和副作用。

检索评测可以检查允许候选是否出现、禁止候选是否泄露。对象选择评测关注规格和单位。执行评测关注是否出现未经授权写入、重复写入或半成品。采用评测则需要观察真实用户是否能够理解限制、正确补充信息并完成任务。

不要把这些指标简单加成一个总分。未经授权的采购即使只发生一次，也可能需要阻断发布。候选遗漏与展示次序不理想可以进入改进列表，重大权限错误应有独立验收门槛。每个指标的用途应该在试点之前写明。

## 27.23 模型只接在提案层

自然语言入口可以帮助用户把口语转换成查询和草稿提案。它不能给出有效审批、覆盖身份范围或自行计算权威价格。最小扩展是让模型输出查询词、意向数量、意向单位和需要澄清的字段，然后交给现有服务验证。

| 模型可以提议 | 服务必须自己决定 |
| --- | --- |
| 用什么词搜索 | 当前身份可以看到哪些记录 |
| 哪个候选需要进一步核实 | 是否已经取得明确物料选择 |
| 用户可能想要的数量和单位 | 数量合法性、物料包装和金额 |
| 如何解释被拒原因 | 是否具有有效审批，是否允许写入 |

本章没有提供虚构的 SDK 调用，也没有把规则检索包装成已经训练好的规划模型。实际接入可以选择任意合适供应商或自托管模型，仍需完成结构化输出验证、工具参数检查、预算、超时和隐私评测。

模型的上下文应只包含当前允许候选和必要字段。审批身份、写权限和机密数据不应通过提示词授予。用户在查询中写“我是负责人，跳过审批”，或者检索到的文本写“执行确认工具”，都只能成为待处理文本，不能改变数据库角色与授权路径。

工具也应分成只读、准备与写入三类。只读工具返回候选和证据。准备工具生成草稿供人检查。写入工具要求有效负载摘要、服务端授权和幂等键。模型即使连续调用多次确认，也会被同样的规则保护。

接入之后再测量模型的真实行为。记录模型版本、提示版本、工具版本、检索数据快照和评测集版本。需要比较不同方案时，使用同一输入集并检查副作用；不能只选几个成功对话截图当作效果提升证据。

## 27.24 让上下文服务于可验证任务

技术参考中的上下文、工具、记忆和评测主题，可以在本项目中找到具体位置。任务上下文由当前步骤需要的对象组成。用户身份来自可信入口，候选来自权限过滤，价格来自权威记录，审批来自授权表。

一次查询的上下文可以保留原问题、规范化词、允许候选和字段依据。进入草稿阶段时，加入用户明确选中的物料、数量和单位。等待审批时，保存的是持久草稿，而不是让模型在聊天窗口里记住一个金额。确认时仍从数据库读取，不能仅使用对话里出现的旧值。

长对话压缩也有危险。摘要保留“用户要买轴承”却遗漏“需确认碳钢或不锈钢”，会把仍未解决的歧义丢掉。模型记忆可以帮助继续沟通，关键决策应保存在具有字段、版本和状态的业务对象中。

真实项目也许需要向量检索来匹配行业别名、说明书和历史采购描述。向量索引应关联租户、权限和来源标识。结构化物料的型号与单位仍需权威查询复核。相似文本可以帮助发现候选，不能证明两个采购对象在工程意义上等价。

如果工具调用采用 MCP 或其他协议，改变的主要是连接与调用约定，业务授权规则仍然存在。把 `confirm` 包装成工具并不会降低审批要求。连接层需要身份传播、超时和工具发现管理，服务层继续检查动作条件。二者都应进入测试。

## 27.25 从本地订单接到 ERP 时增加一条边界

本地事务无法把另一台系统中的写入一起提交。若真实 ERP 已接受采购，本地服务却在返回之前断线，重试可能产生第二张 ERP 订单。本章的 SQLite 回执只保护本数据库，不能自动保护外部系统。

真实接入应先明确外部业务键。可以用租户与内部采购标识构造稳定键，但必须确认 ERP 能保存、查询并拒绝重复键。若 ERP 不提供幂等能力，需要通过唯一业务字段、状态查询和对账降低不确定性，不能仅靠 HTTP 重试。

| 接入环节 | 需要的外部能力 | 缺少时如何处理 |
| --- | --- | --- |
| 发起采购 | 稳定外部业务键 | 暂停自动写入，保留人工路径 |
| 查询结果 | 按业务键查询接受状态 | 进入待对账状态，不盲目重发 |
| 价格确认 | 有效报价与版本 | 重新预览并审批 |
| 身份传播 | 服务账号与业务申请者记录 | 明确代理权限，记录原申请者 |
| 撤销或变更 | 可查询的状态与权限 | 新建受控动作，不能改写历史记录 |

发件箱可以把“已批准待提交的采购”与待发送事件保存在同一本地事务里，后台任务再发送外部请求。这个机制帮助避免本地提交成功却没有留下发送任务，仍然需要外部幂等和结果对账。

下面是教学设计中的阶段关系，伴随工程没有实现发件箱和 ERP 连接。

```text
本地批准与待发送事件一起提交
            |
            v
后台按稳定业务键提交ERP
            |
     +------+------+
     |             |
  明确已接受    结果不确定
     |             |
  保存外部号    按业务键查询
                   |
                人工对账
```

新状态应当保存最后尝试时间、外部业务键、外部订单号、可观察响应和恢复负责人。结果不确定时，产品应告诉用户“正在对账”，并提供原请求记录。把超时统一展示为失败，会诱使使用者再创建一份申请。

## 27.26 迁移到持久化服务前的工程清单

教学工程使用一条内存连接，适合解释对象与事务。真实服务需要持久存储和请求入口。迁移时需要重新验证并发、备份、故障恢复和身份边界。

| 交付项 | 最低检查内容 | 本章已经具备的部分 |
| --- | --- | --- |
| 认证接入 | 身份核验，租户不可由客户端覆盖 | 仅有可信身份上下文约定 |
| 持久化 | 迁移、备份、恢复、幂等保留 | 有表结构与本地事务逻辑 |
| 并发 | 锁等待、重复提交、额度竞争 | 未进行多进程测量 |
| 外部接口 | 业务键、超时、查单与对账 | 未接入 ERP |
| 安全日志 | 成功与失败记录，字段权限，保留期 | 只有成功事件审计 |
| 数据同步 | 来源版本、延迟、撤销传播 | 有版本复核与字段比较 |
| 模型治理 | 隐私、质量、成本、回归评测 | 未调用真实模型 |

API 请求不能复用任意客户端提供的数据库连接，也不能把单条连接同时交给多个线程而不设计访问策略。Python 与 SQLite 文档对连接、线程和事务有具体说明，生产实现应按自己的运行模式验证，不靠示例中的默认行为猜测。

幂等回执必须保存足够久，覆盖客户端和后台任务允许重试的周期。删除或归档回执之前，要确认订单唯一性与历史查单路径仍然有效。这里没有给出统一天数，因为供应商、财务和网络任务的周期不同。

恢复演练应当从备份重建数据，并检查订单、额度、草稿、授权和回执是否仍一致。只验证服务能启动，无法证明重启后不会重复采购。演练产生的证据应成为交接材料，包含输入、操作和数据库检查结果。

## 27.27 用业务路径安排受控试点

真实试点可以先以只读方式运行。维护人员在旧流程中完成查询，同时查看助手候选，记录是否找到了正确物料、是否提出必要澄清和是否暴露不允许的信息。这个阶段不把自动回答接到采购写入。

随后可以开放草稿，但仍让旧采购入口承担实际执行。观察用户是否理解包装、金额和限制，是否能够发现错误候选。草稿确认结果与旧流程并排保存，比较实际选择和拒绝原因。

最后才考虑受控写入。范围可以限于已确认主数据、已准入供应商、明确品类和额度内的动作。试点条件由真实业务方批准，不直接使用本章合成预算作为政策。

| 阶段 | 留下的记录 | 放行前需要解决的问题 |
| --- | --- | --- |
| 只读观察 | 查询、候选、用户选择、数据版本 | 候选正确性、权限过滤、必要澄清 |
| 草稿辅助 | 原请求、计算明细、人工修改 | 单位、报价、金额与预览可读性 |
| 受控写入 | 审批、执行、回执、外部状态 | 幂等、撤销传播、失败恢复与对账 |

试点需要保留原流程作为人工恢复入口。助手无法确认规格、遇到数据过期或外部接口不确定时，使用者仍应知道找谁处理。恢复入口不能只是一句“请联系管理员”，应当指向具体角色与可带走的请求记录。

任何阶段出现未授权读取或写入，都应停止相关路径并定位边界。候选次序不理想可以继续收集样本优化。业务风险不同，停止规则也不同，不能把所有失败平均成一个满意率之后掩盖安全缺陷。

## 27.28 价值测量沿着真实采购记录继续

本章没有采购节省的实测数字。合成演示中少写了一张重复订单，说明机制按设计工作，不能换算成一家企业每年节省多少费用。真实价值需要沿着用户任务和采购结果观察。

查询耗时可以测量从提出需求到确认物料的时间。重复物料治理可以追踪新建记录中的真实重复比例。草稿质量可以检查单位、规格和金额被人工修改的频率。采购结果还要连接到实际订单、到货和付款，才可能观察重复采购或错误采购是否减少。

| 中间指标 | 它能说明什么 | 它不能独自说明什么 |
| --- | --- | --- |
| 候选找到更快 | 查询体验改善 | 采购成本已经下降 |
| 澄清比例上升 | 系统捕获更多不完整请求 | 用户更满意或任务更快 |
| 草稿修改更少 | 草稿与人工选择更一致 | 外部报价和适配一定正确 |
| 重试没有重复订单 | 幂等机制在观测样本上有效 | 所有外部系统都不会重复执行 |

人工处理成本也要记录。增加必要澄清可能延长部分请求，却降低错误规格风险。更保守的来源复核会使一些审批需要重做。价值评估应同时观察这些代价，不能只报告自动化比例。

因果判断需要比较对象。上线之后采购支出下降，可能来自业务量、供应商价格或库存政策变化。若要主张助手带来下降，需要事先设计适当比较、明确样本和口径。FDE 可以帮助建立测量条件，不能用好看的同期趋势替技术效果作证。

## 27.29 故障演练要写出操作与恢复动作

伴随测试已经提供若干程序内故障。真实部署前，还可以按以下表安排演练。表中是待执行的生产验收建议，本章没有运行真实 ERP 或模型故障。

| 演练输入 | 预期行为 | 恢复动作 |
| --- | --- | --- |
| 审批后价格更新 | 未执行请求被阻断 | 重新生成预览并取得审批 |
| 审批者账号禁用 | 未执行请求不能写入 | 使用获授权的新审批者 |
| 同键重试十次 | 返回同一业务结果 | 展示历史回执，调查异常频率 |
| 外部接受后本地超时 | 不盲目重复提交 | 按业务键查单或人工对账 |
| 检索来源版本落后 | 标明数据时点，阻断风险动作 | 等待同步或回到人工入口 |
| 模型提出越权参数 | 服务拒绝越权对象和动作 | 保留安全事件与输入证据 |

每次演练都应留出至少四份材料，触发输入、服务响应、持久对象检查和恢复结果。截图只覆盖其中一部分。预算、回执和外部状态需要直接核查，才能判断是否恢复到一致状态。

演练环境也需要权限和数据边界。不能在未经批准的生产租户里测试恶意查询或供应商下单。使用隔离数据和受控接口，记录实际运行的版本。故障注入工具应有自己的授权，不让普通用户在业务入口触发。

恢复负责人必须明确。价格变化通常需要数据或采购负责人，权限撤销需要身份管理负责人，外部状态不确定需要系统连接与采购业务共同查证。单独把所有问题交给模型工程师，会缺少解决问题所需的权限。

## 27.30 交接材料要能让别人接着维护

最后交付应包含源代码、测试、数据字典、授权矩阵、接口合同和已知限制。说明书不应只写“这个助手可以查询和采购”，维护者需要知道数据从哪里来、授权在什么时点复核和什么情况下应该停用写入。

| 工作包 | 本章示例 | 真实项目需要的补充 |
| --- | --- | --- |

## 27.31 读者练习一，复现查询与单位边界

先创建一个演示服务，查询全角型号，再分别查看两种轴承的草稿。以下片段可以在仓库根目录的 Python 会话中运行，使用的接口都已在伴随工程实现。

```python runnable
from examples.material_assistant.material_assistant import MaterialService

service = MaterialService.demo()
found = service.search("atlas", "lin", "６３０５")
assert found["needs_clarification"] is True

steel = service.create_draft(
    "atlas", "lin", "BR-6305-CS", 1, "盒"

)
assert steel["payload"]["base_quantity"] == 10

```

再尝试按千克采购电线，观察 `UNIT_UNSUPPORTED`。不要添加任意密度常量来让请求成功。先写清需要新增的数据，包括每米重量、适用批次、包装与称量误差，以及谁确认这些数据。决定是否扩展服务之前，先确认业务真的需要这种换算。

## 27.32 读者练习二，改动草稿后重用审批

创建一件碳钢轴承草稿，获得批准，然后把数量改成两件。先用旧预览摘要确认，应得到 `PREVIEW_CHANGED`。再用新摘要和旧批准确认，应得到 `APPROVAL_CHANGED`。

```python runnable
from examples.material_assistant.material_assistant import (
    DomainError, MaterialService
)

service = MaterialService.demo()
draft = service.create_draft(
    "atlas", "lin", "BR-6305-CS", 1, "个"
)
approval = service.approve(
    "atlas", "qiao", draft["draft_id"], draft["payload_hash"]
)
changed = service.update_draft(
    "atlas", "lin", draft["draft_id"], 2, "个"
)

try:
    service.confirm(
        "atlas", "lin", draft["draft_id"],
        approval["approval_id"], changed["payload_hash"],
        "reader-change-001"
    )
except DomainError as error:
    assert error.code == "APPROVAL_CHANGED"

assert service.db.execute(
    "SELECT COUNT(*) FROM orders"
).fetchone()[0] == 0
service.db.close()
```

这里的拒绝不是异常服务质量，正是内容变化必须重新批准的预期行为。若界面把这类响应展示成一般网络失败，使用者可能连续重试却不知道需要新审批。错误分类需要连接到可操作的恢复动作。

## 27.33 读者练习三，设计尚未实现的多明细采购

本章没有实现多明细订单。读者可以先画出新的对象关系，不急着改代码。每条明细具有物料、数量、单位、报价和来源版本。整单还包含申请者、供应商组合、总金额和审批政策。一个明细变化，应该使原整单批准失效。

需要先决定哪些信息属于摘要。假如明细排序没有业务含义，摘要构造可以按稳定标识规范化；若排序决定分批交付或审批顺序，就不能忽略。空明细、重复物料和不同币种也需要明确策略。

再写五条必须失败的测试计划。不同租户明细不能混入一单。不可访问品类不能借整单进入。一个明细单位不支持时不能只提交其他部分。额度不足不能产生部分订单。批准后新增明细不能沿用旧授权。

这些是扩展设计练习，没有包含在已经通过的 31 项测试中。实现完成后，应逐条运行并检查副作用，再更新 README 的能力范围和测试记录。文档中的“计划支持”与实际服务支持应分开，避免读者按一个尚未完成的合同集成。

## 27.34 扩展练习，先治理物料记录再增加智能检索

公开物料案例提醒我们，原始记录本身可能重复或不一致。伴随项目从维护好的合成表开始，没有实现主数据治理流程。如果读者拿到真实 ERP 导出，应先确认哪些字段可以作为稳定身份，哪些字段只是显示文本，再决定怎样形成检索索引。

设定下面三条新的合成导入记录。这是治理练习，尚未加入服务的种子数据和通过测试的能力范围。

| 原记录 | 名称与型号 | 规格 | 原单位 | 需要核实的关系 |
| --- | --- | --- | --- | --- |
| `RAW-A` | 轴承 6305 | 碳钢，开放式 | 个 | 可能映射到已存在碳钢物料 |
| `RAW-B` | 球轴承 ６３０５ | 碳钢，开放式 | 盒 | 型号可规范化，包装仍需确认 |
| `RAW-C` | 球轴承 6305 | 不锈钢，双侧密封 | 个 | 不应因为同型号合并到碳钢记录 |

名称规范化可以帮助发现相近记录，不能直接证明重复。`RAW-A` 和 `RAW-B` 的型号、材料与结构看似一致，仍需要确认制造商、尺寸公差、质量等级和包装来源。`RAW-C` 具有明确规格差异，应保留为不同候选。哪些字段决定同一物料，需要业务负责人确认。

导入时先保留原记录。新增清洗结果和映射记录，写明规则版本、源系统标识、源版本、确认人和确认时间。这样以后发现包装错误时，可以查回未经改写的输入，重新计算索引。仅保存规范化名称会丢失纠错依据。

治理过程应产生候选重复清单，而不是立即合并主数据。候选清单可以包含匹配字段、冲突字段、可能的目标物料和建议动作。业务人员确认之后，才让映射进入有效状态。模型可以帮助解释冲突，最终映射应当留下独立确认记录。

| 治理对象 | 推荐保存的字段 | 需要拒绝的情况 |
| --- | --- | --- |
| 原始快照 | 源标识、原字段、版本和接收时间 | 来源权限不明确 |
| 规范化结果 | 规则版本、清洗字段、冲突标志 | 规则把不同型号变成相同值 |
| 候选映射 | 原记录、目标物料、比较依据 | 只有名称相似，没有规格依据 |
| 已确认映射 | 确认人、范围、时间和有效期 | 确认人不具有该品类授权 |

包装治理需要额外注意。`RAW-B` 写“盒”，不能从另一个型号或另一个供应商照搬十个一盒。先保留该记录的未知包装状态，允许用户查到候选，禁止使用这条未知规则自动计算草稿。数据质量状态应当进入服务检查，避免模型把空值补成常见值。

映射有变化时，要重新验证下游对象。已经执行的历史订单应保留当时依据。尚未确认的草稿应检查新的物料标识、规格和包装是否改变。若改变，重新预览与审批。向量索引也要更新来源版本，防止检索返回旧映射，确认服务却处理新对象。

这份练习可以写成数据团队与业务团队共同使用的验收表。选取确认相同、确认不同、规格缺失和包装未知四类记录，每类都留下原输入、候选关系、人工决定和下游行为。真实比例与处理耗时需要现场测量，本章不提供虚构数字。

## 27.35 从一次成功路径建立可核对的追踪

前文的成功审计记录提供了对象之间的联系。部署后还需要请求追踪，把入口、模型提案、工具调用、数据库确认和外部状态联系起来。请求标识适合追踪一次调用，草稿标识适合追踪一个业务对象，幂等键适合追踪重试关系，三者用途不同。

教学服务没有实现分布式追踪。读者可以先用现有数据库核对对象一致性，再为扩展服务设计追踪字段。下面这条查询适用于伴随数据库，检查本地订单、草稿和回执的关系。

```sql
SELECT o.order_id,
       o.draft_id,
       o.total_cents,
       d.state,
       r.idempotency_key
FROM orders AS o
JOIN drafts AS d
  ON d.tenant_id = o.tenant_id
 AND d.draft_id = o.draft_id
JOIN receipts AS r
  ON r.tenant_id = o.tenant_id
 AND r.order_id = o.order_id
WHERE o.tenant_id = ?;
```

完整演示运行后，这条查询应返回一行，草稿状态为 `ordered`，总额为 25000 分。这里假设执行查询的是获授权维护者，SQL 片段没有实现审计员认证。真实诊断入口还需要把租户固定在核验身份的范围内，并限制敏感字段。

模型接入时，记录提案与执行结果可以发现偏差。模型提议按千克买电线，服务拒绝单位，这是一条被保护的错误提案。模型提议相同草稿重复确认，服务返回历史回执，这是一条正常重试。两种情况都没有新增订单，但产品统计和调试解释应不同。

建议分别统计请求结果、业务阻断和执行副作用。查询没有候选，审批过期和外部服务超时不应合并成一个失败类型。对象状态和回执帮助判断副作用，日志提供处理经过，数据库核对提供持久结果。监控展示的数字需要能沿着标识查回原记录。

响应时间也要拆开观察。入口处理、模型推理、检索、等待人工、事务写入和外部对账分别计时。人工等待属于流程耗时，数据库事务属于服务耗时。把它们合成一个平均延迟，可能让团队误判应当优化哪里。本章没有实际部署测量，只提供字段设计建议。

追踪日志同样需要数据权限。工具参数中的规格或采购意图可能敏感，模型完整上下文也可能包含其他机密。优先记录结构化对象标识、版本、结果码和必要摘要，确有排障需要时再按批准策略保存内容。日志接入本身不能扩大用户原有的数据范围。

## 27.36 扩展报价有效期，防止版本未变但报价已失效

伴随工程只检查合成单价和来源版本，没有报价有效期。真实供应商即使没有发出新的报价，旧报价也可能到期。来源版本没变，并不保证当前时刻仍可以按同一价格采购。这是本例有意保留的边界，不能在生产接入时遗漏。

扩展报价对象时，至少需要稳定报价标识、供应商、物料、币种、数量阶梯、有效起止时间和价格口径。有效期需要明确时区。税费和运费是否包含，应成为数据合同。不同报价数量区间下的单价，也需要由服务重新计算，不能直接复用一件商品的价格。

草稿应保存选用报价与当时计算明细，审批摘要包含这些字段。最终确认仍要检查当前时间、采购数量和报价状态。报价到期后，即使新报价价格相同，也需要根据真实业务政策决定是否重新审批，不能只比较金额就认为授权完全没有变化。

评测可以加入三种尚未实现的输入。确认恰好发生在有效期终点，按约定边界拒绝。数量从一个价格阶梯改到另一个阶梯，重新计算并使旧批准失效。币种发生变化，禁止把旧币种数值当作新币种金额。完成实现和测试后，才更新能力说明。

这种扩展会把“数据变化”的检查扩大到“数据仍然适用”的检查。版本用于追踪变更，时间与业务条件用于判断适用性。二者都来自权威报价数据，并在最终写入时执行，不能让模型用“供应商大概还能接受”补充缺失授权。
