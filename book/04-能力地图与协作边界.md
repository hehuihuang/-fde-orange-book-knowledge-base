# 第 4 章　能力地图与协作边界

FDE 会接触业务、软件、数据和组织协作。学习时很容易把自己需要掌握的工具列成无限长的清单。更实用的办法是从交付动作反推能力。

## 五种可以检验的能力

业务理解可以通过一张被用户认可的流程图检验。工程能力可以通过一条真实可运行的请求链路检验。数据判断要看你能否发现缺失、冲突和权限问题。评测能力要看错误能否被稳定复现。协作能力则要看跨部门决定是否有明确责任人与记录。

这些能力不要求平均发展。后端工程师可能先补用户观察和采用设计，业务顾问则需要补接口、数据库、测试与部署。选择自己的一个短板，用可交付的作品练习，比继续收集术语更有效。

| 能力 | 最低可见作品 |
| --- | --- |
| 业务理解 | 一页现状流程与问题说明 |
| 工程实现 | 可复现的应用、测试与部署说明 |
| 数据判断 | 字段定义、质量检查和权限范围 |
| 评测改进 | 失败分类、测试集、版本比较 |
| 协作交接 | 决策记录、运行手册和维护责任 |

## 知道何时请专业人员参与

了解安全概念不等于能够批准安全例外。懂一些财务指标不等于有权签署财务结论。FDE 的能力包含识别这些边界，并及时让相应负责人参与。

对每个重要决定，写下提议人、执行人、批准人和受影响的人。角色可以重叠，但批准权必须清楚。项目越接近写入生产系统，越不能依赖口头理解。

## 技术深度怎样生长

先把一条小流程做完整，再沿着暴露的问题深入。查询慢，就学习索引与缓存；权限复杂，就学习授权模型；模型经常引用错误，就检查检索与评测。这样的技术积累有具体问题作为检验。

本书不建议把熟悉框架数量作为能力指标。框架能帮助完成工作，也可能掩盖请求、状态和错误处理。至少选择一个项目，能够不依赖框架术语讲清楚它怎样运行。

## 让能力证据覆盖一条请求链

本章查阅了 OpenAI 的 FDE 岗位、Google Cloud 架构框架以及 AWS 的架构决策记录指导。它们提供职责、质量属性和决策留痕的不同视角。下面的能力检验与责任表由作者设计，不代表某家公司的考核标准。

选择一条采购草稿请求，从界面一直跟踪到数据库。用户身份怎样传到后端，后端怎样取得组织范围，资料怎样过滤，模型产出怎样校验，草稿怎样保存，再由哪个接口提交。能把整条链写出来以后，选择自己负责的部分深入。FDE 可以协调全局，不必在每个领域都达到同样深度，但不能让跨领域接缝无人负责。

一种实用的能力标尺有三个层次。能解释表示可以画出数据与动作路径，能验证表示能构造输入并观察结果，能维护表示能在出现故障或变化后安全修复。只会复述组件名称，还缺少验证证据。只会启动演示应用，还缺少维护证据。

| 能力范围 | 最低验证证据 | 深入时要回答的问题 |
| --- | --- | --- |
| 软件与接口 | 一条带鉴权和错误路径的请求 | 并发、超时及重复请求怎样处理 |
| 数据与查询 | 字段字典、质量检查及查询计划 | 权威来源、时效与关联条件怎样确定 |
| 模型与检索 | 可复现的样本及错误切片 | 缺失证据与错误答案怎样区分 |
| 安全与治理 | 越权测试及允许动作清单 | 权限撤销后缓存结果还能否访问 |
| 运行与交接 | 发布清单及恢复演练 | 没有原开发者时谁能恢复服务 |

这里的证据可来自合法的小项目。规模小可以简化设施，但不要删掉责任与异常。使用合成数据时明确标注，并解释哪些结论只覆盖演示范围。

## 一张责任表需要允许作出决定

责任表可以采用 RACI 的思路，区分执行、最终负责、需征询和需知会。实际项目中，最重要的是每一项关键决定有明确的最终接受者。多人参加安全会议，不等于有人已经接受上线风险。角色可以兼任，责任不能因为兼任而消失。

作者设计的采购项目中，业务负责人接受采购规则和质量评分，数据负责人接受主数据含义，技术负责人接受发布与恢复能力，安全负责人接受身份、数据路径和访问控制。FDE 负责准备方案、实现与验证材料，并把冲突送到有权决定的人。预算、合法依据及业务制度由相应负责人判断。

| 决定 | 准备材料的人 | 接受决定的人 | 无法决定时怎样继续 |
| --- | --- | --- | --- |
| 哪些物料允许自动匹配 | FDE 与领域专家 | 业务负责人 | 保留人工选择，不自动提交 |
| 哪些字段可以进入模型 | FDE 与数据团队 | 安全及数据负责人 | 使用允许的脱敏样本验证 |
| 是否增加写接口 | FDE | 接口与业务权限负责人 | 本期只保存草稿 |
| 是否扩大试点 | FDE 与运营团队 | 业务及技术负责人 | 维持当前范围继续观察 |

最终负责者不应只签一个笼统同意。他应知道接受了哪些条件，哪些范围未被覆盖，以及哪些变化会要求重新审核。记录决定及依据后，执行者才能把它转成配置、测试或操作手册。

## 把架构决定写成可以回读的记录

架构决策记录用于解释为什么选某个方案。AWS 的指导强调记录背景、决定与后果，并保留决定的生命周期。读者可以用以下自编例子练习。

采购助手选择保留固定工作流，仅在候选匹配和补充问题上调用模型。背景是提交规则已确定，而物料描述不完整。备选方案包括完全手动、固定程序匹配和模型自主选择全部动作。选择的后果是流程容易测试，但新增任务类型需要改工作流。触发重审的条件是任务种类明显扩大，固定流程的维护成本有证据地超过受控动作选择。

一项决定应列出被拒绝方案的优点。完全手动无需引入新技术风险，固定程序具备精确行为，开放动作选择可能降低面对复杂输入时的流程数量。把这些优点写清楚，后续维护者才能理解当时的限制。没有备选和后果的决策记录，容易退化成当前实现说明。

| 决策字段 | 应留下的内容 |
| --- | --- |
| 背景 | 任务、约束、现有证据及未知 |
| 选择 | 当前采用的机制和适用范围 |
| 备选 | 至少一个认真考虑过的方案 |
| 后果 | 额外工作、风险与限制 |
| 重审条件 | 哪种事实变化足以重新决定 |
| 责任与状态 | 谁接受、何时接受、是否被后续记录替代 |

## 沟通冲突要落到约束与证据

业务团队希望缩短周期，安全团队限制外部数据，工程团队希望减少定制。三种诉求可以同时成立。FDE 需要把它们变成可比较的方案。只发送公开字段能覆盖多少任务，在允许环境内运行需要多少资源，只提供草稿是否仍有价值，都可以通过小实验得到材料。

当安全要求暂时无法满足，先调整功能范围或环境，不能靠一次用户同意绕过正式授权。当业务评分规则不明确，先让专家独立标注同一批样本，整理分歧，不能把模型输出当成裁判。具体动作依赖具体限制，沟通无需堆砌技术术语。

跨部门等待也属于交付风险。记录申请日期、所需材料、接受条件及下一位处理者。若权限申请需要完成数据去向审核，而数据去向依赖尚未确定的架构，团队应先作架构范围决定，再提交申请。将依赖次序理清，往往比增加催办会议更有效。

## 学习深度与专业边界一起增长

从查询计划可以继续学习索引与事务，从工具接口可以继续学习网络及授权，从评测差异可以学习抽样和统计。选择学习内容时，写出当前无法解释或验证的一个具体问题。每次学习结束留下实验结果，确认理解能够处理实际变化。

遇到医疗、法律、财务及专门安全问题，应知道何时需要专家。工程师能实现控制，却不能借技术方案自行制定临床规则或法律结论。专业边界写进责任表，也写进系统的允许动作范围。团队在关键风险上需要帮助，属于正常协作条件。

## 用一次设计审阅发现责任接缝

设计审阅选一个正常任务和一个反例，按执行顺序走完。采购反例可以是用户预览后价格失效。业务专家说明是否允许继续，数据人员说明怎样识别失效，工程人员说明在哪里重查，支持人员说明用户怎样继续。每个人都提供自己领域的证据。

审阅记录包含未决问题、决定者、临时安全行为及再次确认条件。价格规则还没决定时，只保存未确认草稿，可以使部分验证继续。不能让前端自行隐藏价格问题，也不能让模型按经验猜测是否继续提交。

审阅结束以后，把决定写进规则、接口及测试，并检查三者是否一致。业务表里规定重新确认，而程序仍复用旧确认，就存在真实接缝。能力学习也可以从这种不一致展开，追踪问题究竟位于设计、实现还是证据。

## 本章练习

给自己的五种能力各选一个现有作品作证据。没有作品的项目不必打高分，直接写出下一次练习。再请一位与你背景不同的人审阅，看看你是否遗漏了对方最关心的责任。

为采购例子写一份固定工作流与开放工具选择的决策记录。参考答案至少包含明确规则的可测试性、模糊描述的处理需求、写入控制的风险，以及任务范围改变时的重审条件。再找出一个无人接受的决定，补足负责人和临时安全做法。
