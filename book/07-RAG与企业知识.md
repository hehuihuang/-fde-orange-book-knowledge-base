# 第 7 章　RAG 与企业知识

一个回答旁边有三个引用图标，仍可能完全答错。图标证明程序显示了链接，真正需要验证的是链接对应的资料是否有效、是否允许用户查看，以及资料是否支持回答中的具体结论。RAG 的交付单位应是一条可核查的证据路径。

本章对照 RAG 原始论文、RRF 论文与搜索引擎官方文档，独立设计采购与制度问答示例。这里的检索名单、数值与政策都是原创教学数据。它们用来演算机制，不是某供应商的基准结果。下面的短代码只实现排序融合与指标计算，真实系统还需连接索引、授权和数据更新。

## 7.1 先决定该查对象还是查文字

RAG 通常指先检索资料，再把证据送入生成过程。企业资料既包括自然语言，也包括有明确结构的当前对象。问“MAT-204 当前库存多少”适合查询库存服务，问“停用物料怎样申请例外”适合检索政策。把动态库存表转成文本向量索引，可能引入同步延迟与错误聚合；让 SQL 查询从长政策中找例外条件，又可能损失文字语义。

路由可以采用受信任规则与受限制的分类。精确物料编号触发对象查询，制度问题触发文档检索，混合任务分别查询再组织证据。分类失败应可观察并可补问。若一个问题同时需要库存和替代批准，单一语义相似段落不足以支持决策。应用需要把两种证据分别标注来源与截至时间。

RAG 原论文讨论参数记忆与外部检索结合的方法。今天工程系统可以采用不同生成模型、搜索器与索引，不必复制论文实现。可迁移的关键问题是证据从哪里来、如何选入、如何使用、怎样判断没有找到足够资料。换成向量数据库不会自动回答这些问题。

| 用户问题 | 主数据路径 | 需要保留的边界 |
| --- | --- | --- |
| 某编号库存 | 结构化对象服务 | 截至时间、单位与权限 |
| 两规格是否可替代 | 规格对象加批准记录 | 关系版本与批准范围 |
| 例外申请规则 | 政策文本检索 | 生效时间与适用组织 |
| 去年某申请为何被退回 | 历史状态加记录检索 | 当时版本与授权 |

## 7.2 解析失败会伪装成检索失败

PDF 可能是有文本层的文档，也可能是扫描图片。解析器需要识别页序、阅读顺序、表格、脚注与图注。OCR 把 0.5 识成 5，后面的向量检索可以准确找到这个错误数字，却无法恢复原始数值。数据接入验收应先抽查解析结果，尤其是数字、单位、否定词和表格关联。

解析产物保留来源位置。文本段落记录页码与段落编号，表格记录表名、列名与行位置。把整页直接拼成一句长文字，容易让表头、正文和脚注互相串联。对规则表，可以把行内容转换成带字段名的证据，同时保留原始页面链接，让审阅者能回看。转换逻辑应有单元测试与人工抽查。

同一资料具有多个表示。原始文件用于核查，规范文本用于切分，索引片段用于检索，生成证据用于回答。每个表示关联源标识、源版本与内容摘要。若解析器升级后数值变化，团队可以定位哪些片段受影响。只给片段生成一个随机编号，又不记录来源版本，会使重建与旧引用解释变得困难。

作者建议用接入报告记录文档数、解析异常数、关键字段抽查数和未覆盖格式。任务运行成功只代表流程结束，不能代表文字被正确读取。对未经质量验收的文件，可以允许用户直接打开原件，但不要让它们静默进入高风险回答路径。

## 7.3 切分单位取决于判断需要的背景

固定 token 长度切分容易实现，但条款可能跨边界，表格行可能失去列名。按章节或语义结构切分可以保留自然单元，却可能出现长度悬殊。实践中可以先按结构定位，再对过长单元做受控分段，并为每段带上必要标题与上下文。

采购例外规则中，标题是“紧急采购”，正文给出限额，下一段写“危险化学品不适用”。若限额与例外限制被分开，检索只命中限额段，生成就可能错误扩大适用范围。因此切分验收需要任务测试，检查关键条件与排除条件是否一起可用。重叠窗口可以减少部分断裂，却也会增加重复和索引体积，不能代替结构判断。

可以采用子片段检索、父片段返回。短子片段使匹配更精确，找到之后回取其所属条款或章节作为证据。父片段也要通过授权与长度预算，不能因为子片段匹配就读取整份敏感合同。返回过长父片段会重新引入第五章的上下文噪声，应保留必要边界和原件入口。

```json
{
  "chunk_id": "policy-v8-section4-part2",
  "parent_id": "policy-v8-section4",
  "source_id": "policy-approval",
  "source_version": 8,
  "section": "紧急采购适用条件",
  "effective_from": "2026-07-01",
  "tenant_id": "TEN-A",
  "acl_ref": "policy-reader-group-v3"
}
```

Anthropic 的 contextual retrieval 在索引前给片段增加背景，并报告了其特定实验中的检索改善。本书只采用“片段需要背景”这一可验证设计问题，不把报告中的改善比例当成读者必然获得的效果。生成背景可能引入未在原文出现的信息，应把自动补充文字与原文区分，检查公司、日期、单位等关键字段。

## 7.4 BM25 如何偏好精确词项

BM25 根据查询词在文档中的出现、稀有程度和文档长度计算相关分数。下面是常见形式的一个词项贡献。f 是词频，dl 是文档长度，avgdl 是平均长度，k1 控制词频饱和，b 控制长度归一化。IDF 的具体定义会随实现变化。

```text
term_score = IDF(term) * f * (k1 + 1)
             / (f + k1 * (1 - b + b * dl / avgdl))
```

词频增加时，贡献逐渐饱和，避免重复几十次的普通词无限占优势。长度归一化减轻长文档因包含更多词而天然占优。Elasticsearch 文档中的 BM25 默认参数是 k1 为 1.2、b 为 0.75，这是具体实现的默认值，不能直接写成所有语料的最优参数。

用原创数字演算，若 IDF 为 2，文档长度等于平均长度，f 为 1，贡献为 2；f 为 2，贡献为 2.75；f 为 10，贡献约为 3.93。词频提高十倍，分数没有提高十倍。若文档长度翻倍且 f 仍为 1，分母变大，贡献约为 1.42。读者可以通过调整 b 观察长度惩罚变化。

分词器决定哪些内容成为词项。物料号 MAT-204、错误码和带连字符规格可能被拆开，精确编号就需要专用 keyword 字段或恰当分析配置。中文分词和行业缩写同样需要评估。词项没有正确进入索引，调 BM25 参数往往不会补救。先查看分析结果，再做编号查询、同义词与口语查询测试。

词法搜索适合精确名称与编号，但用户可能说“漏油时用的那个环”，与文档词汇差别较大。向量检索可以提供语义候选，两者的互补应通过任务集验证。仅凭一个成功问题，无法确定应该采用哪种策略。

## 7.5 向量相似与业务正确性分开

Embedding 将文本表示为向量，查询与片段使用兼容的模型与预处理。常见相似度包括余弦相似和点积，模型训练方式决定适合的度量。余弦相似比较方向，规范化向量后点积与余弦相等。未规范化时，向量长度也影响点积，因此不能随意更换度量。

```text
cosine(q, d) = dot(q, d) / (norm(q) * norm(d))
```

相似度高说明表示接近，不等于答案正确，更不等于两个物料可替代。语义上接近的密封圈可能温度等级不同。检索后的业务约束需要检查尺寸、材质、批准和适用范围；高相似度只能帮助发现候选。模型更换时，旧文档向量与新查询向量通常不能直接混用，应重建或采用明确的兼容方案。

大规模向量索引常用近似最近邻搜索来减少计算。近似方法在速度、内存与召回之间取舍。为评估索引造成的损失，可以在小规模固定语料上先做精确搜索，再与近似搜索比较同一查询的候选。调整搜索参数时同时测召回与时延，避免把近似漏召误判为 embedding 模型不理解业务。

过滤位置也影响结果。如果先取全库前十，再移除无权结果，可能一个候选都不剩，即使用户有权的相关文档在全库第十一名。某些引擎支持在候选生成期间过滤，具体性能与召回语义要查文档并测自己的数据。无论使用何种过滤策略，未经授权内容都不应进入生成上下文。

## 7.6 用 RRF 融合不同排序

BM25 分数与向量分数处于不同尺度，直接相加需要校准。RRF 使用名次，避免直接比较原始分数。对于文档 d，把它在每个排名中的贡献相加；未出现在某名单的文档不获得该名单贡献。c 为平滑常数，名次从 1 开始。

```text
RRF(d) = sum over lists of 1 / (c + rank_list(d))
```

常用起点 c 为 60，但它是需要评估的配置，与检索返回数量 k 没有同一含义。若 c 很大，相邻名次差距变小，多份名单中共同出现的候选更容易获得优势；若 c 很小，各名单顶端贡献更突出。调整 c 不能修复所有检索器都没有发现的证据。

原创名单中，词法排序为 A、B、C，向量排序为 B、D、A。c 为 60 时，A 得到 1/61 加 1/63，约 0.03227；B 得到 1/62 加 1/61，约 0.03252；C 为 1/63，D 为 1/62。融合后 B、A、D、C。这个结果说明共同候选获得两次贡献，并不证明 B 业务上比 A 正确。

```python runnable
from collections import defaultdict

def rrf(rankings, c=60):
    if c <= 0:
        raise ValueError("c must be positive")
    scores = defaultdict(float)
    for ranking in rankings:
        if len(set(ranking)) != len(ranking):
            raise ValueError("duplicate document in list")
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += 1 / (c + rank)
    return sorted(scores, key=lambda d: (-scores[d], d))

assert rrf([["A", "B", "C"], ["B", "D", "A"]]) \
       == ["B", "A", "D", "C"]
```

融合前按稳定片段身份去重，避免同一片段在某个名单重复获得贡献。融合后再按源文档处理冗余，防止一个长文档的十个相邻片段挤掉其它必要证据。加权 RRF 可以表达来源偏好，但权重需要回归测试，不能用它悄悄把失效政策推到前面。

## 7.7 重排序处理更细的相关性

初检索快速取得候选，重排序用更昂贵的模型对查询与候选共同评分。常见 cross-encoder 把查询和片段一起输入，能够利用二者之间的细节匹配；bi-encoder 先独立编码，便于预计算文档向量。两种方法适用于不同性能位置。重排序数量越大，计算成本通常越高，需要测端到端关键路径。

重排序不能找回未进入候选的证据。如果正确条款根本没有入库，增加重排序模型只会重新排列错误材料。应分别记录初检索 recall、重排序后的排名和最终证据集合。若初检索包含正确条款，重排序却把它降到截断位置，检查语言、领域词汇、否定条件与模型适用范围。

证据选择还需要多样性与必要集合。用户问“是否允许紧急采购以及怎样走流程”，答案至少需要适用条件与申请步骤，不能只选三段相似的限额说明。可以在任务结构中要求不同证据类型，再按长度预算选择。多个同义片段的高平均相关性，不等于问题被完整覆盖。

## 7.8 引用到结论需要一个支持关系

证据进入上下文时用稳定编号，如 E1、E2，附来源、版本、位置与截至时间。生成输出用编号引用，服务端只允许引用本次授权集合中的编号，随后映射到原件。若模型自己编出 URL 或未提供的 E9，应拒绝该引用或重新生成，不能把看着合理的链接当有效出处。

支持关系可以按原子结论检查。“该物料已批准且当前库存为 30 件”包含两个事实，一条规格说明可能只证明规格，不证明批准与库存。将结论拆成可验证单位，再检查每项是否被有效证据支持。FActScore 的研究提供了原子事实评估的思路，本书把它用于设计检查，而不照搬其具体任务和评分器。

引文检查有三个不同问题。覆盖度问多少需要证据的结论给出了来源；有效性问链接或编号是否真实存在且用户有权查看；支持性问来源内容是否支持该项结论。引用覆盖率百分之百仍可能支持性很低。界面应展示具体来源片段，允许用户回看，不只提供一串文档名。

没有足够证据时，返回已查到的内容和明确缺口。找到规格但没有批准，回答可以说明规格候选并提示需批准记录，阻止采购提交。拒答阈值需要任务级评估，相似度低、高分差或模型自报确信均不能直接替代业务证据充分性。

## 7.9 更新与授权变化要同步到派生数据

索引是一份派生表示，应记录源版本与构建版本。更新路径由事件或批次触发，完成后核对文档、片段、向量与缓存的版本。源资料被撤回时，可先标记不可用并阻止服务继续返回，后续的数据处理按组织政策执行。本书的更新建议不涉及自动删除用户文件。

权限变化常常比正文变化更紧急。员工转岗或合同访问范围收缩后，旧检索缓存和会话中的旧片段不能继续成为授权依据。检索结果在进入模型前复核权限，引用展开时再次授权，执行时检查最新权限。缓存键应包含租户、授权范围或能够等价区分的策略版本，不能只以问题文字为键。

切换 embedding 模型或解析器时，可以构建新的索引版本，用相同查询做影子比较，再小流量切换。保留可回退的旧构建和版本映射，不能仅因新索引生成成功就覆盖所有可用查询。更新演练至少包含源新增、源修改、资料撤回、ACL 改变、消息重复和消息乱序。

## 7.10 检索与答案分别评测

给每个查询标注相关证据集合 G，检索前 k 个集合为 R_k。Recall@k 为找到的相关证据数除以相关证据总数。Precision@k 为前 k 个中相关数除以实际返回数，报告时明确少于 k 条结果的分母约定。若问题只要求其中任一证据，需采用对应的成功规则；不能把“找到一个就足够”误写为全部相关资料召回。

MRR 关注第一个相关结果的名次，其倒数在任务间平均。它适合关注首个可用结果的任务，不能衡量多条件证据完整性。nDCG 可以采用分级相关性并考虑位置折扣，其标注成本更高。选择指标应先看任务，避免用适合搜索点击的指标代替行动安全。

```python runnable
def recall_at_k(ranking, relevant, k):
    if k <= 0 or not relevant:
        raise ValueError("invalid evaluation input")
    returned = set(ranking[:k])
    return len(returned & set(relevant)) / len(relevant)

assert recall_at_k(["A", "C", "B"], {"A", "B"}, 2) == 0.5
assert recall_at_k(["A", "C", "B"], {"A", "B"}, 3) == 1.0
```

空证据问题要单独评测，相关集合为空时不把 recall 当一。越权问题需要确认不泄露内容，过期政策问题需要选择正确版本，冲突资料问题需要识别冲突并遵守业务裁决路径。最终答案还要评测事实、支持性、完整性和可执行性，检索成功与任务成功分开报告。

错误归因顺序从前向后检查。来源未接入，修接入；数字解析错，修解析；相关片段没有召回，修查询与索引；候选被降序，修排序；证据存在但答案误用，修生成与校验。每次只改变明确因素并保留失败样本，避免多个配置一起改后不知道哪项有效。

## 7.11 本章工作坊与答案线索

工作坊一为一条有排除条件的紧急采购规则设计切分。答案需保证限额、适用范围与危险化学品例外可以被同次任务取得，保留父条款、版本与来源位置。只增加固定重叠比例无法证明条件完整。

工作坊二使用 RRF 代码给第三份名单 C、A、D 融合，分别设置 c 为 1 与 60，比较结果与分数差。讨论 c 与候选数量 k 的区别，并解释为何融合无法补上未被任何检索器发现的批准记录。答案应给出复算结果，而非仅说混合检索更好。

工作坊三创建四类测试，分别是精确编号、口语别名、过期规则、无权合同。对前三类标注预期证据和答案；对无权合同标注禁止泄露，并检查生成上下文中是否已经出现正文。回答拒绝之前发生泄露，也属于失败。

工作坊四模拟用户转岗。先检索得到合同片段，再改变授权，随后尝试从缓存提问和展开旧引用。答案应包含授权版本失效与引用端复核。只在下一次登录时更新角色，会留出会话继续读取的风险。

本章交付物是一份来源接入报告、可回读的片段 schema、词法与向量对照、RRF 演算、检索和答案分层评测，以及更新演练记录。它们决定这套系统能否被维护，向量库品牌只是实现中的一项选择。
