# 第 8 章　工作流、Agent 与 MCP

模型决定“下一步查询库存”，程序决定“这个用户能否查询，以及查询结果怎样影响申请”。把这两个决定混在一段提示里，系统就很难恢复、测试和审计。一个可交付的 Agent 需要清楚的运行边界，也需要能解释每次状态变化的记录。

本章研究了 ReAct 论文、Anthropic 的工作流说明、MCP 官方架构与 Python 的异步任务文档，再独立设计采购任务的运行模型。教学状态、工具合同与代码是原创，代码采用规则规划器，未调用真实大模型。规则规划器用于验证运行控制，不能用其通过测试来声称模型具备相同规划能力。

## 8.1 先判断谁需要控制路径

普通程序根据明确规则执行，适合字段、计算与条件已经确定的任务。带模型节点的工作流在预定义路径中加入语言理解，例如识别申请内容、查物料、校验条件、展示预览。Agent 让模型根据当前观察选择下一步路径，例如候选物料存在歧义时追问，库存资料不足时决定调用另一个读取工具。

路径变化越多，测试和解释的成本通常越高。自主程度应由任务需要决定。一个只有四个固定步骤的申请流程，可以把语言理解放在单个节点，不必再让模型决定是否跳过批准。探索式资料研究则可能需要动态查询，但仍可以限制来源、调用次数与输出形式。

| 判断条件 | 普通程序 | 模型工作流 | 有界 Agent |
| --- | --- | --- | --- |
| 步骤与规则明确 | 优先采用 | 只在语言步骤引入 | 通常收益有限 |
| 输入表达变化大 | 需转换输入 | 适合抽取与分类 | 视后续路径决定 |
| 下一步取决于新发现 | 显式分支 | 分支可枚举时适合 | 可检查结果时考虑 |
| 写入风险高 | 严格服务约束 | 保留固定批准路径 | 仍需同样服务约束 |
| 无法判断终态正确 | 先补验收方法 | 限制为建议 | 不宜直接自主执行 |

ReAct 展示交替使用推理与行动获得新观察的方法，适合理解动态任务循环。论文中的基准结果不能直接证明企业操作安全。部署者要为每项行动设计接口、校验、失败处理和终止条件，模型生成的行动计划只是一项待检查建议。

## 8.2 用状态机承接动态决定

Agent 的状态应包括任务身份、当前阶段、业务对象版本、可用工具集合、已取得证据、运行预算和最后结果。对话文字可以解释过程，状态对象负责执行控制。状态转换由程序检查，模型只能提出合法范围内的候选动作。

```text
NEW -> IDENTIFYING -> READING -> DRAFTED -> AWAITING_APPROVAL
                              |                    |
                              v                    v
                         NEEDS_INPUT            APPROVED
                                                   |
                                                   v
                                                SUBMITTED

任意运行态可进入 FAILED 或 CANCELLED
等待外部结果可进入 PENDING_RECONCILIATION
```

SUBMITTED 需要有效批准、最新对象版本和动作授权。模型即使直接返回 submit，也不能跳过这些前置条件。NEEDS_INPUT 可以等待用户补充，不应因无人立即回复而循环调用相同搜索。PENDING_RECONCILIATION 用于写入结果未知的情况，后续先核对状态，不盲目再提交。

状态机不要求每个业务都使用这些名称。重要的是转换有前置条件与可见结果。失败状态保留失败阶段和是否产生副作用，不能只留下“出错了”。取消也要区分尚未开始、只读已执行和写入已提交。用户点击取消后，已经完成的外部操作不一定被撤回，界面需要准确报告。

事件记录有助于恢复。任务取得物料候选，记录 evidence_received；形成预览，记录 preview_created；用户批准，记录 approval_granted；执行完成，记录 submission_completed。事件带任务和调用标识，业务对象版本和结果摘要，敏感内容遵守日志政策。恢复时依据持久状态判断下一步，不能把整个对话重新送给模型后期待它猜出已做过什么。

## 8.3 Harness 负责可执行的限制

本书用运行控制层指代围绕模型的代码与配置，业界也常称 harness。它管理上下文、工具执行、状态保存、预算、错误与观测。模型更换后，这一层仍应维持权限和副作用边界。运行控制层也可能出错，需要独立测试，不能认为“由程序实现”就天然正确。

一次循环可以依次做这些动作。取得当前受信任状态，构建本轮最小上下文，向规划器请求候选动作，检查动作与参数，执行允许工具，保存结果和状态，再判断终止。检查发生在工具真正执行之前。工具返回后再做结果 schema 与业务核对，防止损坏结果继续传播。

下面片段演示调用次数与工具允许列表。它只支持只读工具，未实现持久化、时间预算和安全沙箱；真实应用需要把这些边界补齐。plan 函数可以来自规则或模型，接口一致并不代表行为一致。

```python runnable
def run_read_loop(plan, tools, initial, max_steps=4):
    observations = list(initial)
    for step in range(max_steps):
        action = plan(tuple(observations))
        if action["kind"] == "finish":
            return {"state": "completed", "steps": step}
        if action["kind"] != "read":
            raise ValueError("unsupported action")
        name = action["tool"]
        if name not in tools:
            raise PermissionError("tool not available")
        result = tools[name](action.get("args", {}))
        observations.append({"tool": name, "result": result})
    return {"state": "budget_exhausted", "steps": max_steps}

def demo_plan(observations):
    if observations:
        return {"kind": "finish"}
    return {"kind": "read", "tool": "get_material",
            "args": {"material_id": "MAT-204"}}

assert run_read_loop(
    demo_plan, {"get_material": lambda args: {"version": 7}}, []
)["state"] == "completed"
```

调用预算只是一个维度。总时长、token、费用、并发、输出大小与动作范围也需要控制。时间采用单调时钟测量，避免系统时钟调整干扰截止时间。每个子调用使用总剩余时间中的一部分，不能在总预算快耗尽时再启动一个长工具。模型说“我还需要继续”不会改变程序预算。

循环检测可以记录规范化的工具名与参数摘要。连续重复同一读取且没有新观察时，提示需要补问或停止。重复不一定是错误，轮询外部状态可能合理；应区分预期轮询与无进展重试，并设置间隔和上限。把所有重复一律禁止，可能破坏正常恢复；完全不限制，则会浪费资源。

## 8.4 工具合同要表达副作用

工具名称与描述让规划器知道能做什么，服务合同让执行者知道必须检查什么。查询物料只读取；创建草稿增加内部记录；提交申请可能启动 ERP 流程。把三个动作都叫 update，会使副作用难以判断。工具拆分既服务规划，也服务权限与测试。

一个工具合同至少说明目的、输入类型、身份来源、输出类型、错误码、副作用、幂等与超时行为。读取结果包括来源、版本和截至时间。写入参数包括预览标识、批准凭证和幂等键，租户和用户由服务端注入。工具描述可以解释何时使用，动作是否允许由执行服务决定。

```json
{
  "name": "prepare_purchase_preview",
  "input": {
    "material_id": "string",
    "quantity": "positive integer",
    "expected_material_version": "integer"
  },
  "identity_source": "trusted request context",
  "effect": "create internal draft only",
  "output": ["preview_id", "payload_hash", "expires_at"],
  "errors": ["INVALID_INPUT", "STALE_OBJECT", "NOT_ALLOWED"]
}
```

该 JSON 是教学合同表示，不是 MCP 的 wire schema，也不是某厂商 SDK 代码。生产实现应使用所选接口支持的 schema，并运行集成测试。把概念合同写成实际接口时，要核对默认值、可选字段、字符串长度和多语言说明是否一致。

返回内容过大时，工具应分页或返回摘要与受控引用。截断必须明确，不能把前一百行伪装成完整结果。规划器需要知道结果不完整，否则可能在缺证据时结束任务。工具响应也属于不可信输入，外部页面的指令不能因为经过工具包装就获得运行授权。

## 8.5 MCP 在连接层，策略在应用层

MCP 即 Model Context Protocol，为应用与外部能力提供共同交换约定。宿主应用管理一个或多个客户端，客户端连接对应服务器，服务器提供工具、资源或提示模板。数据层使用 JSON-RPC 消息表达交互，传输层处理消息如何在本地进程或网络中交换。具体方法与生命周期由所用版本决定。

```text
用户与界面
  -> 宿主应用
       -> 任务状态、授权、上下文与执行控制
       -> MCP 客户端 A -> 物料服务器 -> 受限数据服务
       -> MCP 客户端 B -> 政策服务器 -> 授权文档索引
```

MCP 统一部分连接和描述方式，不规定模型应该采用哪个工具，也不替企业批准高风险动作。宿主允许某工具可见，服务器仍需检查动作权限，下游服务仍需验证受信任身份与业务约束。三层可以形成多重控制，但它们必须采用一致身份语义，不能各自猜测用户是谁。

工具强调可以执行的能力，资源强调可读取的上下文，提示模板帮助组织交互。提示模板来自服务器，宿主仍需审查其信任等级，不能让第三方模板覆盖系统策略。工具能力清单也有供应链含义，服务器更新后新工具突然出现，应经过变更审核，不宜默认全量启用。

本章核查日期为 2026 年 9 月 18 日，官方架构页面指向 2026-07-28 版本。此前版本中的连接、初始化、采样和授权细节不可直接拼到同一个实现。本章不提供未经跨版本测试的报文教程。交付清单应固定协议版本、客户端 SDK 版本、服务器实现版本与能力集合，保存官方版本页链接，并为不支持版本、缺少能力和错误报文设计测试。

本地进程服务器与远程服务器有不同部署风险。本地服务器可能直接访问文件与环境变量，需要核对启动程序、工作目录、凭据和可访问范围。远程服务器需要网络身份、TLS、受支持授权与审计。协议连接成功只代表能交换消息，不能作为数据授权或工具安全验收结果。

MCP 的安全文档讨论了 token passthrough 等风险。服务端应验证令牌受众与授权范围，并按下游系统支持的方法使用适当凭据。不能把任意来自客户端的 token 直接转发后假设下游会完成所有控制。第十章将用威胁模型检查服务器如何成为越权代理。

## 8.6 错误恢复先判断副作用

读取超时通常可以在预算内重试，但昂贵查询、限流与数据变化仍需考虑。写入超时可能已经产生副作用，恢复路径要先查状态或使用原幂等键。认证失败、字段不合法和版本冲突需要修正条件，简单重复同一请求不会改善。错误分类应在代码中明确，模型可以帮助解释，不能决定绕过限制。

| 错误 | 运行行为 | 用户看到什么 |
| --- | --- | --- |
| 临时读取超时 | 有界重试或降级 | 等待边界与资料缺口 |
| 限流 | 退避、降低并发 | 稍后重试或任务排队 |
| 无权限 | 停止该动作 | 不泄露对象的拒绝提示 |
| 参数不合法 | 补问或重建参数 | 哪个输入需要更正 |
| 对象版本冲突 | 重新读取并生成预览 | 当前数据已改变 |
| 写入结果未知 | 查状态、进入核对 | 尚未确认结果，勿重复提交 |

重试会放大负载。原始请求失败时，多个层次都重试，单个用户任务可能产生许多下游调用。只在负责协调的层设置必要重试，其它层暴露清楚错误，或明确各层预算。指数退避与随机抖动有助于错开同时重试，但参数应结合限流规则和总截止时间，不是越多越安全。

取消异步任务不保证外部服务器立即停止。网络调用可能已经到达服务端，写入也可能完成。运行层需要记录调用身份与状态，等待恢复核对。Python 的任务取消和 timeout 有具体语义，代码不应吞掉取消异常后继续执行写入。对于可取消下游服务，要使用其受支持机制，同时核对是否真正终止。

降级应保留业务边界。政策服务器不可用，可以展示明确标记的受授权旧资料并禁止高风险提交，前提是组织政策允许；也可以切换普通查询界面。直接换一个模型继续猜规则，会改变风险而非恢复证据。降级结果和正常结果需要在评测中区分。

## 8.7 并行与多 Agent 需要独立收益

多个独立读取可以并行，例如查询现行政策与读取物料规格。依赖关系必须先画清楚。如果供应商查询依赖物料消歧后的编号，就应等待消歧结果。把所有工具同时启动，可能用错身份、浪费调用并引入矛盾观察。

多 Agent 可以把独立研究任务交给不同上下文，减少单个上下文混杂，也带来通信、重复检索与合并成本。Anthropic 对其研究系统的说明展示了具体设计与评测经验，不证明所有企业任务都适合多 Agent。采购提交涉及同一状态与同一批准，多个 Agent 同时争取写入通常需要严格串行协调。

合并者应收到结构化产物，包括结论、证据编号、假设、缺口与版本。若一个子任务依据旧政策，另一个依据新政策，合并者要依据生效条件处理冲突，不能按多数意见表决。子 Agent 的总结仍是待验证输出，不因多个模型同意就成为权威事实。

计算总成本时，包含每个子任务、协调者和失败重试。并行可能减少墙钟时间，却增加 token 与工具调用。评测同时报告任务成功、时延、费用和错误类型，只有目标任务的收益超过新增维护成本，才值得采用。

## 8.8 轨迹要能重放，也要承认非确定性

一次可检查轨迹包含任务输入、受信任状态、候选动作、实际动作、工具参数、结果摘要、版本与终态。模型的自然语言说明可以另存，不能替代这些结构记录。轨迹使团队能够检查多查了哪次、在哪步失去版本，以及取消之后是否仍产生写入。

重放可以固定工具返回和时间，使运行控制的测试确定化。真实模型的规划选择可能变化，工具返回也可能随数据更新不同。因而测试分两层，一层用规则或记录动作验证状态机，另一层用真实模型评估路径与成功率。离线记录重放通过，不代表在线环境也同样通过。

日志需控制敏感内容。为了重放而全量保存客户文本和凭据会制造新的风险。可以保存脱敏后的参数、受控证据引用与摘要，完整正文按授权保存在专门系统。用于测试的快照保持合规且可定位，不能把生产日志打包推到公共仓库。

## 8.9 本章工作坊与答案线索

工作坊一把采购请求分别实现为普通表单、模型工作流和有界 Agent，比较同一组输入表达。答案应说明哪些变化需要语言理解，哪些路径变化带来收益，以及三个版本怎样共享相同执行服务。批准检查不能只存在于其中一个版本。

工作坊二把 demo_plan 改成持续调用同一工具。预期四步后返回 budget_exhausted。再返回不存在的工具，预期在执行前拒绝。两项测试证明运行控制生效，不证明模型会做出正确计划。加上真实模型后，还需单独统计无进展循环与工具选择错误。

工作坊三模拟提交超时。申请在服务端已提交，响应丢失。答案应保留原幂等键与任务身份，查询状态后返回原结果，不再新建申请。再演练用户取消，界面显示已提交与取消未能撤回的事实，不编造成功回退。

工作坊四建立 MCP 接入审核表。列出固定版本、维护来源、工具集合、身份传递、数据范围、网络目标、错误报文、超时和升级回归。协议版本不匹配时应明确失败或使用受测兼容实现，不能删除检查后继续调用。

工作坊五让两个子 Agent 分别提出相互冲突的物料建议。答案要回到规格与批准记录，收集来源差异，保留未决状态，禁止通过投票直接提交。多 Agent 增加发现信息的机会，业务决定仍需要符合服务约束。

本章交付物是运行状态机、工具行为合同、有界循环、版本固定清单和副作用恢复演练。读者能解释每次动作为何允许、为何停止、如何恢复，这个 Agent 才具备进一步试点的条件。
