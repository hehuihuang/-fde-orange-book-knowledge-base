# 第 2 章　用业务流程理解问题

「做一个客服 Agent」已经包含了方案，却没有解释为什么要做。开始构建以前，先把客户正在处理的任务写出来。这样才能比较 AI、普通自动化和流程调整三种办法。

## 一项任务的完整描述

任务从一个触发事件开始。用户收到咨询、订单进入异常状态、设备发出告警，都可能触发后续工作。随后有人读取信息，作出判断，调用系统，再把结果交给下一位参与者。

记录流程时，至少写清触发条件、参与角色、输入资料、判断规则和最终输出。还要记录失败后的处理办法。只画成功路径，会漏掉最消耗人工的部分。

| 要观察的地方 | 要留下的证据 |
| --- | --- |
| 等待 | 等谁、等什么、等待起止时间 |
| 重复录入 | 相同字段出现在哪些系统 |
| 人工判断 | 判断依赖什么信息与经验 |
| 返工 | 错误何时被发现、由谁修正 |
| 例外 | 哪些情况不能按标准规则处理 |

## 区分工作量与限制条件

某一步花费很多时间，不一定是整条流程的主要限制。文书生成快了，审批仍然需要数天，端到端周期可能几乎不变。观察时应把执行时间与等待时间分别记录。

同样，自动化容易处理的任务，未必值得优先做。若一项任务每月只发生一次，维护成本可能超过收益。若它涉及不可逆写入，即使频率很高，也需要先解决权限和复核问题。

本书建议先选择一个高频、有明确所有者、可以取得样本的任务。它应当足够窄，能被完整测量；也应当连接真实工作，用户愿意继续使用其结果。

## 把人的动作和系统动作分开

流程图可以分成两条线。人的一条线记录阅读、判断、确认和交接；系统的一条线记录查询、计算、写入和通知。两条线相交的地方，就是界面和权限设计的重点。

如果一个结果需要人工确认，界面就必须给出足够证据。只显示「建议通过」不够，复核者还需要知道依据、缺失信息和影响范围。若系统自动发送通知，则要明确收件人、发送时机和重复发送的处理方式。

## 本章练习

选择自己能合法观察的一项工作，完整记录一次正常处理和一次异常处理。不要先画理想流程。把真实动作整理成一页图，再标出最希望改变的一个环节。交给实际操作者确认，直到对方能够按图复述工作。
