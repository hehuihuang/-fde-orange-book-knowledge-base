# 第 17 章　团队组织与复用

单个项目可以依靠少数人熟悉全部细节。项目数量增加以后，这种方式容易让支持、定制与交接相互挤占。团队需要决定哪些工作留在客户现场，哪些进入共享产品。

## 先划清共同责任

业务负责人确认价值与规则，FDE 负责跨系统构建与交付协调，平台团队维护共享服务，安全与运营人员负责相应控制。团队规模不同，一人可以兼任多个角色，但每项重要责任都要有人明确接受。

排期时应把上线后的支持计入工作量。若每位工程师同时启动多个项目，却没有维护容量，旧项目的故障会不断打断新项目。

## 哪些东西值得复用

身份接入、日志规范、工具接口、评测流程和发布检查通常容易形成共享能力。客户特有的政策、审批和数据定义则需要保留配置或扩展边界。

看到第二个相似需求时，可以先比较差异，再决定是否抽象。过早把一个客户的特殊流程做成平台规则，会让后来项目绕着错误假设工作。

| 候选内容 | 进入共享能力前要检查 |
| --- | --- |
| 连接器 | 身份、租户隔离和接口版本 |
| 工具封装 | 行为语义、权限与错误处理 |
| 评测集结构 | 可复用格式与客户数据隔离 |
| 交付模板 | 必填项、适用条件和责任人 |
| 产品功能 | 多个项目是否具有相同需求 |

## 项目经济性需要完整记录

除了建设时间，还要记录售前验证、集成、返工、培训和后续支持。若收入增长同时带来同样比例的人工支持，组织仍需面对服务成本。

可以定期比较各项目的定制工作量、交付周期、支持负担和共享组件使用情况。复用率也不能单独作为目标，复用了不适用的组件可能增加后续返工。

## 团队容量先包含已交付系统

本章阅读了 Palantir 的开发者入口、Google 的值班与重复运维工作资料，并参考 AWS 的架构决定记录方法。下面的容量与复用算例均为作者设计的教学假设，不代表真实团队人员配置或服务价格。

新项目会产生发现、开发、验收及上线工作，旧项目还会产生支持、数据更新和风险复测。排期需要把两种需求放在同一个容量表里。否则一个新项目的速度可能来自把旧系统维护移到无人负责的时间。

教学假设两位工程师每周各有四十小时，总容量八十小时，其中客户沟通十六小时、已有系统支持二十小时、共享组件维护八小时，剩余三十六小时用于新构建。这种分配只是说明完整计算。若新项目需要每周五十小时，就必须调整范围、人员或开始时间。把全部八十小时承诺给新项目，会形成可以预见的冲突。

支持量还存在波动。记录问题到达、处理时长、严重度和中断次数，留出合理余量。复用能减少部分开发，却不能自动减少所有支持。业务规则及数据变化仍有客户责任，团队应在交接和合同中说明。

| 工作类型 | 需要测量 | 计划中的表现 |
| --- | --- | --- |
| 新项目 | 发现、集成及验证工时 | 限制同时启动数与未完成任务 |
| 已交付支持 | 到达量、耗时及严重度 | 明确支持窗口与升级人 |
| 数据与政策维护 | 更新次数及复测成本 | 与负责人约定更新节奏 |
| 共享能力 | 构建、迁移及支持负担 | 保留专门维护容量 |

## 先比较语义，再决定抽象

两个客户都需要采购工具，仍可能有不同语义。一个接口只保存草稿，另一个直接建立外部申请；一个允许多次修改，另一个受理后内容固定。若用同一 submit 名称封装而不说明差别，复用会掩盖风险。

抽象前逐项比较输入、前置条件、最终状态、失败方式和授权。相同部分进入共同接口，差异留在适配器或政策配置。配置能够表达的差异也需要测试，不能把客户特有条件写进共享默认值。

作者设计的采购连接器可以对外提供查询物料、查看价格、保存草稿和查提交状态四类明确操作。每个适配器实现同样的语义合同，若下游没有最终状态查询，能力清单应声明不支持，调用方采用相应安全路径。接口名相同不等于行为相同。

## 共享能力具有维护与退出条件

一个组件进入共享范围，需要确定接口所有者、版本政策、客户隔离、发布与事故责任。组件升级会影响多个部署，兼容检查和迁移计划不能由各现场工程师凭经验完成。保存客户使用版本，出现问题时能找到影响范围。

| 共享工件 | 接口边界 | 必须保留的客户差异 |
| --- | --- | --- |
| 身份适配 | 身份到组织与角色的映射 | 组织结构及授权来源 |
| 工具网关 | 校验、预算和记录格式 | 具体允许动作及权限条件 |
| 检索处理 | 记录版本、引用与过滤接口 | 文档语义及访问规则 |
| 评测框架 | 样本及评分器的执行格式 | 客户评分、数据和风险切片 |
| 发布模板 | 工件版本及接受流程 | 环境限制、负责人及窗口 |

共享评测格式不意味着共享客户样本。不同客户的数据、商业规则和凭据不得因复用汇入同一公开材料。需要公开演示时使用明确标注的合成样本，并说明它无法证明各客户效果。

退出条件也要明确。组件长期只有一个使用者、通用接口迫使大部分客户绕行，或维护成本已超过直接适配，应重新讨论抽象。保留决定与后果，避免组件因曾经投入很多就永久存在。

## 用经济性核对复用是否值得

一个简化的复用模型可以写作收益 E=n×s-B-U。n 是预计适用部署数，s 是每个部署减少的适配成本，B 是共享组件建设成本，U 是观察周期内的维护与迁移成本。各项用同一单位并注明周期。若 s 只按工时计量，E 也先表示工时变化，不直接称为财务利润。

教学假设共享身份连接器建设耗时四十小时，一年维护二十小时，每个真正适用部署节省十五小时，五个部署的 E 为十五小时。若只有三个部署适用，E 为负十五小时。这个比较还没包括风险和质量收益，应独立记录。不能把所有潜在客户都当作必然适用。

再比较共享组件带来的新工作。升级、迁移、支持、兼容和测试会消耗时间。组件使接入更快但事故影响更多客户时，团队需要投入更强的控制。复用率与交付周期要和支持负担、质量及可维护性一起看。

## 产品反馈与客户交付之间有明确通道

现场问题进入共享产品，需要最小复现、脱敏依据、影响和现有变通成本。产品团队判断是否形成通用需求，现场团队判断本项目如何继续。两项决定可以有不同时间尺度，短期安全适配与长期产品改动都应留下记录。

定期回读多个项目，查哪些工作反复出现、语义是否相同、哪些失败可以用共同测试阻止。看到第二个例子可以开始比较，不能仅因数量到二就宣布适合平台化。某些政策差异具有长期稳定理由，保留明确扩展边界更有用。

## 项目评审记录真实定制成本

每个项目结束时，按发现、连接器、规则、页面、评测、培训及支持归类工时。记录估计与实际差异，也记录已有共享工件节省了什么。若同一适配器在各项目都需大量修改，检查它是否覆盖了真正共同的语义。

教学采购项目可以将字段映射保留在适配器，将单位规则保留在客户配置，将幂等结果和版本检查保留在共同控制层。新客户改变了审批流程，就新增适配和测试，不把该客户特例推给所有部署。

评审结论包括可复用候选及明确不复用部分，再由共享组件负责人接受。预计收益由下一次真实接入验证，不能在抽象完成时直接宣告节省。团队据此调下一周期容量，并将维护义务写回排期。

## 本章交付物

从一个已完成项目里选出三项候选复用材料，分别写明适用条件与不可复用部分。至少保留一个明确不抽象的客户特例，并解释这样做怎样减少误用。

按本章假设重新计算三、五、八个适用部署的工时收益，参考答案为负十五、十五及六十小时。再为一个共享工具写语义合同与不支持能力说明。验收时请另一位工程师用说明实现适配器，观察是否仍需猜测下游行为。
